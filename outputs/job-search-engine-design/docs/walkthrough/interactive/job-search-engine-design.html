Job Search Engine

A process-driven, AI-powered system that analyzes a full professional profile, researches the market, determines targeting, generates tailored materials, and manages the pipeline from first contact through offer.

Draft — 2026-03-17 Brainstorm session: Sean + Claude Status: Pending Review

What This Is

A standalone, AI-powered job search engine built for Sean Currie. Not a resume folder — a process-driven system that runs its own discovery. It doesn't wait to be told what to target.

vs. Frank Lombardo
Deliverables vs. Machine

Frank got deliverables. Sean gets a machine. The engine is opinionated, process-driven, and runs its own discovery.

vs. SEE
Factory vs. Product

SEE is the factory. The job search engine is the product. Built and maintained from SEE, runs independently.

The Meta-Play
Engine as Portfolio Piece

The fact that Sean built an AI-powered job search engine is itself evidence of capability. The engine is self-aware as a talking point and proof of work.

Design Considerations: Complexity vs. Frank's Approach

Frank's engagement was simpler: FOR-FRANK, 03-WORKING, 01-KNOWLEDGE-BASE, _build. This engine is more complex by design — it's a living system, not a one-shot package. The complexity is warranted by:

  • Ongoing operation (not one delivery)
  • Multiple targets with different lifecycles
  • Process-driven methodology requiring state management
  • Future automation layers

If complexity creates friction during use, simplify. Structure should serve the process, not the other way around.

Timeline Pressure: 4-8 Week Window

The MVE (Minimum Viable Engine) concept ensures Sean can start operating within ~1 week of build start while deeper capabilities are built in parallel. The engine's own Phase 1 (Discovery & Positioning) can run before all skills are extracted.

Critical path: capability map + market scanner + session orchestrator.

Runtime Isolation: No SEE References in Deployed Engine

The deployed engine is fully self-contained. Its CLAUDE.md, skills, operator files, and directory structure do not reference SEE. SEE is a build-time concern, not a runtime concern.

  • The engine's CLAUDE.md describes its own methodology — not where it came from
  • Skill files don't reference "forked from" or "extracted from" — they're the engine's own skills
  • Operator files (COLLABORATION-STYLE.md, WRITING-STYLE.md) are the engine's own documents
  • Directory comments describe what things ARE, not where they came from

The one exception: SEE appears as a portfolio item in the capability map — "Sean built a Sales Enablement Engine." That's evidence about Sean's professional work, not operational awareness of the engine's own construction.

Build-time implication: During Phase 3 (Core Skills Build), all SEE references get stripped from files before deployment. The extraction manifest tracks provenance; the deployed skills don't carry it.

Operator File Staleness (Prerequisite)

As of design date (2026-03-17), source material is stale:

  • CONTEXT.md: last updated 2026-02-19 (26 days stale)

The Engine's Process

When Sean sits down with the engine, it has a structured process. The engine drives — Sean steers. Six phases, from ingesting source material through continuous intelligence.

Click a phase above or use the pills below to explore each phase in detail.

Ingest & Profile Build

First-time setup. The engine ingests all source material and produces the foundation everything else builds on.

What This Phase Produces

  • Master capability map — every skill, achievement, proof point. Atomized and tagged by domain, evidence strength, recency, and transferability.
  • Wonda narrative arc — the engine works WITH Sean to frame this chapter. The raw facts: 6-month fractional SE role, products built, relationship complexity, professional growth. The framing is an engine-phase conversation, not a pre-decision.
  • Products inventory — SEE, WondaKB, renewal engine, master content library, UI design framework, dev team bridge, hosted platform research, on-demand-curriculum, and the job search engine itself.
  • Gap analysis — what's strong, what's thin, where evidence is solid vs. inferred.
Heavy Lift
This phase is heavier than a simple ingest. Sean's operator files are stale as of the design date. The evidence index has 6 entries for 30+ work products. Phase 0 includes excavating the full engagement history, not just reading existing files.

Discovery & Positioning

The engine analyzes the capability map AND runs market research (Bright Data, job boards, industry signals). It returns positioning — not templates, but evidence-driven angles.

What the Engine Returns

  • "Here's what your profile says you are" — capability clusters, not job titles
  • "Here's what the market is hiring for" — demand signals, compensation data, growth indicators
  • "Here's where those overlap — and where they don't"
  • "Here are positioning angles I'd recommend, ranked, with reasoning"
  • Pushback included — "You might think X, but the data says Y"
Design Principle
The engine determines targeting. The design does not pre-define positioning variants. The discovery process surfaces them from evidence + market data. Sean debates, refines, and lands on variants.
Self-Awareness
The engine knows its own existence is evidence of capability. When positioning angles emerge, "built AI-powered operational systems" should be grounded in real artifacts — including this engine.

Targeting

The engine builds target lists with two tiers of depth.

  • Sniper list (10-15) — Deep-researched companies. Each gets a full target folder with company profile, role analysis, contact intelligence, fit scoring.
  • Pipeline list (50+) — Broader targets, scored and tiered. Enough data to prioritize, not enough for personalized outreach yet.

Scoring criteria are defined by the engine based on Phase 1 findings: culture fit, growth signals, hiring velocity, compensation range, role-profile alignment. Not pre-defined in this design.

Arsenal Build

Per target, the engine generates tailored materials from the atomic capability map — not rewritten from scratch each time.

  • Tailored resume (from atomic capability map + positioning variant)
  • Cover letter / application narrative
  • Outreach sequences (hiring manager, referral, recruiter)
  • LinkedIn profile updates
  • Interview prep (when interviews are scheduled)

All materials pass through the collaboration style and writing style guides. Output sounds like Sean, not AI.

Execute & Track

Pipeline management powered by Notion as the visualization and tracking layer.

  • Application status tracking (Notion databases — visual pipeline, filterable, sortable)
  • Interview scheduling and prep generation
  • Post-interview debrief processing
  • Follow-up sequencing
  • Cross-opportunity intelligence ("they loved the AI story" → weight that signal)
  • Feedback loops that refine targeting and positioning
Notion Integration
The engine builds and manages a Notion workspace for pipeline visualization. This is a first-class capability, not an afterthought. Markdown files remain source of truth; Notion is the visual layer and daily operating view.
Engine-phase decisions surfaced during execution
  • LinkedIn content strategy — what to post, when, how the job search intersects with professional presence
  • Geography preferences — remote, hybrid, Chicago-area, open to relocation
  • Compensation expectations — floor, target, negotiation leverage
  • Portfolio presentation — which projects to highlight

These are discovered through the engine's process, not pre-set in this design.

Continuous Intelligence (future-ready)

Architecturally ready, not first build. The hooks exist; nothing runs automatically yet.

  • Scheduled market scans (cron jobs or similar)
  • Auto-surfaced new postings matching profile
  • Re-engagement sequences for stale contacts
  • LinkedIn content integration
  • Automated application tracking
  • Notion dashboard auto-refresh

Skills Architecture

Skills are the engine's most critical layer. They are also the hardest to get right — 88 source skills across 8 projects, an extractability audit already done, antipatterns to fix, and a runtime isolation requirement that means every skill must arrive in the engine clean, self-contained, and unaware of where it came from.

Skill Lifecycle

Skills go through a one-way pipeline. Source → staging → engine. Once a skill lands in the engine, it belongs to the engine. The engine doesn't know or care where it came from.

One-way skill pipeline: Source projects → SEE staging → deployed engine. No references flow backward.

Three Classifications

Every skill identified in Phase 1B gets one of three classifications. Each has a different build process:

Clone-and-Go
Works as-is

Copy → strip source references → rename if needed → deploy. 4 steps.

Fork-and-Adapt
Right methodology, needs modification

Copy → understand → identify changes → rewrite modified sections → strip references → verify standalone readability → deploy. 7 steps.

Build-New
No source skill exists

Define requirement → reference working examples → write from scratch → test against engine methodology → deploy. 5 steps.

Full build process details for each classification

Clone-and-go

  1. Copy SKILL.md to staging area
  2. Strip any source-project references (paths, engagement names, project-specific context)
  3. Rename if the skill name should change for job search context
  4. Deploy to engine's skills/local/

Fork-and-adapt

  1. Copy SKILL.md to staging area
  2. Read and understand what the skill does
  3. Identify what changes for job search (terminology, inputs/outputs, context)
  4. Rewrite the modified sections — the skill becomes a NEW skill that shares DNA with the source
  5. Strip all source-project references
  6. Test: does the skill make sense if you've never heard of the source project?
  7. Deploy to engine's skills/local/

Build-new

  1. Define the capability requirement (what the skill needs to do)
  2. Reference working examples from the capability inventory (scripts, patterns, prior outputs)
  3. Write the SKILL.md from scratch in staging
  4. Test against the engine's CLAUDE.md and methodology
  5. Deploy to engine's skills/local/

Manifest Entry Format

Phase 1B produces one manifest entry per skill. Each entry is a build spec detailed enough for Phase 3 to execute without re-reading source skills:

## [Engine Skill Name] **Classification:** Clone-and-go | Fork-and-adapt | Build-new **Source:** [project/skill-name] or "New" **Priority:** Critical path (Phase 0-1) | Core (Phase 2-3) | Supporting (Phase 4+) **Effort:** [estimate] ### What It Does in the Engine [1-3 sentences: what this skill does in the job search context] ### What Changes from Source (fork-and-adapt only) - [Specific change 1] - [Specific change 2] ### What to Build (build-new only) - [Capability requirement] - [Reference examples to draw from] ### Working Examples to Include - [Script, deliverable, or pattern that deploys alongside this skill] ### Antipattern Fixes (if applicable) - [From extractability audit: what gets fixed during this extraction] ### Acceptance Test [How to verify this skill works correctly in the engine, independent of source]

Once deployed, the engine owns its skills completely.

Design Principle
The engine never references back to source skills. If a skill needs to change, it changes where it lives. The extraction manifest in SEE tracks provenance for historical reference, but the engine doesn't carry that lineage. The engine's CLAUDE.md references skills by their engine names, not source names.

Capability Inventory (skills/CAPABILITIES.md)

The engine carries a skills/CAPABILITIES.md file that maps what it can do. This is NOT a provenance document — it's an operational reference.

For each capability: skill name, what it does (in job search context), working examples, and available infrastructure.

Example entry: Notion Integration
## Notion Integration **Skill:** `notion-ops` **What it does:** Builds and manages Notion databases for pipeline visualization. Maps workspace, creates databases, pushes/pulls data. **Working examples:** - 3 populate scripts (reference implementations for pushing structured data to Notion) - Property design methodology (how to evolve database schemas iteratively) - Playbook-first approach: map workspace before operating, title for understanding / ID for execution **Infrastructure:** Notion MCP server, cached workspace schemas

The engine reads this and knows: "I have a Notion skill, here's what it can do, here are examples I can reference." No mention of where it came from.

Known Antipatterns to Fix During Extraction

From the 2026-03-13 extractability audit:

  • Session orchestrator as god object — too much responsibility in one skill
  • Content-updater as mandatory choke point — everything routes through it unnecessarily
  • Hardcoded living project paths — skills reference absolute paths instead of being portable
  • Skill cross-references creating implicit coupling — skills depend on each other's internals
Research Findings from Audit
  • 19 of 23 SEE skills are already engagement-agnostic
  • All 7 core SEE skills map to job search with 15-30% adaptation
  • Frank's DOCX generation pipeline (6 Node.js scripts) is reusable
  • Notion infrastructure is rich: 2 skills, 3 populate scripts, playbook pattern, property design methodology, cached schemas, MCP server
  • 88 total skills across 8 projects — capability inventory in Phase 1B catalogs the full landscape

Collaboration & Writing Style

The engine carries its own versions of COLLABORATION-STYLE.md and WRITING-STYLE.md. Core principle: push back, research, bring data — tuned for job search context. These are the engine's own documents. They happen to encode the same principles as the originals, but they live in and belong to the engine.

Engine Behaviors

The deployed engine's CLAUDE.md will encode these behaviors. These are the operating principles — what makes the engine opinionated rather than passive.

#1
Process-Driven
The engine has a methodology (Phases 0-4). It doesn't wait for instructions — it knows what phase it's in and what comes next.
#2
Opinionated
Pushes back. Researches before agreeing. Argues with evidence. Doesn't validate — collaborates.
#3
Atomic Source Material
Resumes, cover letters, and outreach are generated from the capability map, not rewritten from scratch each time.
#4
Stage-Aware
Tracks every target's lifecycle stage. Promotes stages when status changes. Scaffolds the right structure.
#5
Evidence-Grounded
Every claim in a resume or cover letter traces back to a documented achievement. Unverified claims are flagged.
#6
Self-Aware as Portfolio
The engine knows it is evidence of Sean's capability. It can describe itself and position its existence as proof of work.
#7
Writing Style Enforced
All outputs pass through Sean's writing style guide. The engine sounds like Sean, not like AI.
#8
Audit Discipline
Two-layer logging: activity log (what happened) and intelligence log (what it means). Every action leaves a breadcrumb.
#9
Notion-Powered Visualization
Pipeline tracking, target dashboards, and daily operating view live in Notion. Markdown remains source of truth.
#10
Future-Ready
Architecture supports scheduled scans, automated applications, and deeper integrations without requiring them for first operation.
#11
Decisions Deferred to Process
The engine does not pre-decide targeting, positioning, geography, compensation, or strategy. It has processes to discover these through analysis + market research + operator dialogue.

Phase 1B
Skill Audit & Extraction Planning
This phase produces the build spec that Phase 3 executes. Every skill that lands in the engine traces back to a manifest entry written here.
Full scope & deliverables

  • Apply extractability audit findings — which skills are already engagement-agnostic, which have hardcoded paths, which have antipatterns
  • Classify each skill: clone-and-go / fork-and-adapt / build-new

Phase 3 MVE
Core Skills Build
This phase executes the Phase 1B manifest. Each manifest entry becomes a skill in the engine through a consistent per-skill process.
Per-skill execution process

For each skill in priority order:

  1. Read the manifest entry — classification, what changes, what to include, acceptance test
  2. Execute the build process per classification:
    • Clone-and-go: Copy source → strip references → rename if needed → stage
    • Fork-and-adapt: Copy source → modify per manifest → strip references → verify standalone → stage
    • Build-new: Write from scratch per manifest → reference examples → stage
  3. Stage in SEE — projects/job-search-engine/staged-skills/[skill-name]/SKILL.md
  4. Run acceptance test — per manifest entry
  5. Deploy clean to engine — ~/Desktop/JobSearchEngine/skills/local/
  6. Update CAPABILITIES.md — add the entry to the engine's capability inventory
After all skills: wiring + final sweep
  • Wire up stage promotion capability
  • Wire up pipeline tracking
  • Wire up materials QA with writing style enforcement
  • DOCX generation pipeline (adapt from Frank's _build/ pattern)
  • Deploy Notion integration skills with working examples
  • Final sweep: Verify no deployed file references any source project. The extraction manifest tracks provenance; the deployed skills don't carry it.
  • Integration test: Can the engine run Phase 1 (Discovery & Positioning) end to end using only its own skills and context?
