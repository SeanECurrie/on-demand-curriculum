Job Search Engine

A standalone, AI-powered job search engine built for Sean Currie. Not a resume folder — a process-driven system that analyzes Sean's full professional profile, researches the market, determines targeting, generates tailored materials, and manages the pipeline from first contact through offer.

vs. Frank Lombardo
Frank got deliverables. Sean gets a machine. The engine is opinionated, process-driven, and runs its own discovery. It doesn't wait to be told what to target.
vs. SEE

The Engine's Process (Methodology)

When Sean sits down with the engine, it has a structured process. The engine drives — Sean steers.

Phase 0: Ingest & Profile Build

First-time setup. Engine ingests all source material and produces:

  • Master capability map — every skill, achievement, proof point. Atomized and tagged by domain, evidence strength, recency, and transferability.
  • Wonda narrative arc — the engine works WITH Sean to frame this chapter. Raw facts: 6-month fractional SE role, products built, relationship complexity, professional growth. Framing is an engine-phase conversation, not a pre-decision.
  • Products inventory — SEE, WondaKB, renewal engine, master content library, UI design framework, dev team bridge, hosted platform research, on-demand-curriculum, and the job search engine itself.
  • Gap analysis — what's strong, what's thin, where evidence is solid vs. inferred.
IMPORTANT
This phase is heavier than a simple ingest. Sean's operator files (OPERATOR-PROFILE.md, CONTEXT.md, evidence-index.md) are stale as of the design date. The evidence index has 6 entries for 30+ work products. Phase 0 includes excavating the full engagement history, not just reading existing files.

Phase 1: Discovery & Positioning

Engine analyzes the capability map AND runs market research (Bright Data, job boards, industry signals). It returns:

  • "Here's what your profile says you are" — capability clusters, not job titles
  • "Here's what the market is hiring for" — demand signals, compensation data, growth indicators
  • "Here's where those overlap — and where they don't"
  • "Here are positioning angles I'd recommend, ranked, with reasoning"
  • Pushback included — "You might think X, but the data says Y"
DESIGN PRINCIPLE
The engine determines targeting. The design does not pre-define positioning variants. The discovery process surfaces them from evidence + market data. Sean debates, refines, and lands on variants.
META-AWARENESS
The fact that Sean built an AI-powered job search engine is itself evidence of capability. The engine should be aware of its own existence as a talking point and proof of work.

Phase 2: Targeting

Engine builds target lists:

  • Sniper list (10-15): Deep-researched companies. Each gets a full target folder with company profile, role analysis, contact intelligence, fit scoring.
  • Pipeline list (50+): Broader targets, scored and tiered. Enough data to prioritize, not enough for personalized outreach yet.
  • Scoring criteria: Defined by the engine based on Phase 1 findings — culture fit, growth signals, hiring velocity, compensation range, role-profile alignment. Not pre-defined in this design.

Phase 3: Arsenal Build

Per target, engine generates:

  • Tailored resume (from atomic capability map + positioning variant)
  • Cover letter / application narrative
  • Outreach sequences (hiring manager, referral, recruiter)
  • LinkedIn profile updates
  • Interview prep (when interviews are scheduled)

All materials pass through the collaboration style and writing style guides. Output sounds like Sean, not AI.

Phase 4: Execute & Track

Pipeline management powered by Notion as the visualization and tracking layer:

  • Application status tracking (Notion databases — visual pipeline, filterable, sortable)
  • Interview scheduling and prep generation
  • Post-interview debrief processing
  • Follow-up sequencing
  • Cross-opportunity intelligence ("they loved the AI story" → weight that signal)
  • Feedback loops that refine targeting and positioning
NOTION INTEGRATION
Markdown files remain source of truth; Notion is the visual layer and daily operating view. The engine gets its own Notion integration tuned for job search tracking — using Python API, not MCP.

Engine-Phase Decisions Surfaced During Execution:

  • LinkedIn content strategy
  • Geography preferences
  • Compensation expectations
  • Portfolio presentation

These are discovered through the engine's process, not pre-set in this design.

Phase 5: Continuous Intelligence (future-ready)

Architecturally ready, not first build:

  • Scheduled market scans
  • Auto-surfaced new postings matching profile
  • Re-engagement sequences for stale contacts
  • LinkedIn content integration
  • Automated application tracking
  • Notion dashboard auto-refresh
TIP
Consider on-demand-curriculum's OpenClaw patterns for scheduling.

Skills Architecture

CRITICAL
Skills are the engine's most critical layer. 88 source skills across 8 projects, an extractability audit already done, antipatterns to fix, and a runtime isolation requirement that means every skill must arrive in the engine clean, self-contained, and unaware of where it came from.

Skill Lifecycle

The key principle: Skills go through a one-way pipeline. Source → staging → engine. Once a skill lands in the engine's skills/local/, it belongs to the engine. The engine doesn't know or care where it came from.

Three Classifications

Clone-and-Go
Source skill works as-is. Copy, strip source references, rename if needed, deploy. Minimal effort.
Fork-and-Adapt
Right methodology, needs modification. Becomes a NEW skill that shares DNA with the source. Self-test: does it make sense without knowing the source?
Build-New
No source skill exists. Define capability requirement, reference working examples, write from scratch, test against engine's CLAUDE.md.

Engine Behaviors (CLAUDE.md Core)

The deployed engine's CLAUDE.md will encode these behaviors:

#1
Process-Driven
The engine has a methodology (Phases 0-4). It doesn't wait for instructions — it knows what phase it's in and what comes next.
#2
Opinionated
Pushes back. Researches before agreeing. Argues with evidence. Doesn't validate — collaborates.
#3
Atomic Source Material
Resumes, cover letters, and outreach are generated from the capability map, not rewritten from scratch each time.
#4
Stage-Aware
Tracks every target's lifecycle stage. Promotes stages when status changes. Scaffolds the right structure.
#5
Evidence-Grounded
Every claim in a resume or cover letter traces back to a documented achievement. Unverified claims are flagged.
#6
Self-Aware as Portfolio
The engine knows it is evidence of Sean's capability. It can describe itself and reference its own architecture.
#7
Writing Style Enforced
All outputs pass through Sean's writing style guide. The engine sounds like Sean, not like AI.
#8
Audit Discipline
Two-layer logging: activity log (what happened) and intelligence log (what it means). Every action leaves a breadcrumb.
#9
Notion-Powered Visualization
Pipeline tracking, target dashboards, and daily operating view live in Notion. Markdown remains source of truth.
#10
Future-Ready
Architecture supports scheduled scans, automated applications, and deeper integrations without requiring them for first operation.
#11
Decisions Deferred to Process
The engine does not pre-decide targeting, positioning, geography, compensation, or strategy. It has processes to discover these through analysis + market research + operator dialogue.

The Engine as Portfolio Piece

The job search engine is itself evidence of Sean's capability — AI systems design, operational methodology, product thinking. The engine should:

  • Have an "about this engine" document ready to share or reference in interviews
  • Be aware of its own existence as a talking point
  • Be able to describe its own architecture if asked

These must be updated before or during Phase 2. The engine's quality depends on the quality of its source material.

Complexity vs. Frank's Approach

Frank's engagement was simpler: FOR-FRANK, 03-WORKING, 01-KNOWLEDGE-BASE, _build. This engine is more complex by design — it's a living system, not a one-shot package. The complexity is warranted by ongoing operation, multiple targets, process-driven methodology, and future automation layers.

If complexity creates friction during use, simplify. Structure should serve the process, not the other way around.

Runtime Isolation (No SEE References)

The deployed engine is self-contained. Its CLAUDE.md, skills, operator files, and directory structure do not reference SEE.

  • CLAUDE.md describes its own methodology, not where it came from
  • Skill files don't reference "forked from" or "extracted from"
  • Operator files are the engine's own documents
  • Directory comments describe what things ARE, not provenance

One exception: SEE appears as a portfolio item in the capability map — "Sean built a Sales Enablement Engine." That's evidence about Sean's work, not operational awareness.

Timeline Pressure

4-8 week window. The MVE concept ensures Sean can start operating within ~1 week of build start while deeper capabilities are built in parallel. Critical path: capability map + market scanner + session orchestrator.

Antipatterns to Fix During Extraction

These are identified failure patterns from the Wonda extractability audit that must be fixed during skill extraction:

Implementation Plan

Date: 2026-03-18  |  Tasks: 21  |  MVE target: ~4-5 working days

Goal: Build a standalone, person-agnostic, process-driven job search engine at ~/Desktop/JobSearchEngine/ that ingests any operator's professional profile, researches the market, determines targeting, generates tailored materials, and manages the pipeline from first contact through offer.

Architecture: Factory/product separation with three layers. SEE (projects/job-search-engine/) is the factory — designs, audits, stages skills. The engine (~/Desktop/JobSearchEngine/) is the product — operates independently, owns its own skills, and drives the job search process through Phases 0-4. The engine is person-agnostic: operator/ ships with structure and defaults, personalized at runtime through Phase 0 onboarding. Skills flow one-way: source → staging → engine. Once deployed, the engine owns them completely.

Three-Layer Model
  1. Process layer (person-agnostic): Phases 0-4 methodology, target lifecycle, audit logging, QA discipline
  2. Capability layer (person-agnostic): skills, infrastructure, tool integrations — informed by the builder's expertise but usable by anyone
  3. Operator layer (personalized at runtime): PROFILE.md, evidence, positioning, style preferences, targets — populated during Phase 0 from operator-provided source material

Tech Stack: Claude Code skills (SKILL.md), Node.js + docx npm package (DOCX generation), Python + Notion API (pipeline visualization), Bright Data MCP (market research), document-skills:docx marketplace skill (reading .docx input during Phase 0).

Design Doc Divergence
This implementation plan diverges from the design doc's build sequence. The design doc puts constitution before skills; this plan puts constitution AFTER skills (per Constraints #1 and #11). The design doc remains the reference for WHAT the engine does; this plan is the reference for HOW to build it.

Critical Constraints

These are binding. Violating any of them means the plan wasn't followed.

1
Design before build. The capability architecture and manifest must exist before any skill is deployed or any constitution document is written. The audit and design synthesis (Phase 1) are the foundation everything else depends on.
2
MVE includes resume-generator and company-researcher. These are critical-path skills alongside profile-builder, market-scanner, and positioning-engine. They are NOT deferred to a later phase.
3
Notion uses Python API, not MCP. Requires a Notion API token. No Notion MCP server.
4
Manifest entries include Required Infrastructure. MCP servers, API tokens, runtime deps per skill. Without this, Phase 2 can't set up acceptance tests.
5
Session orchestrator is build-new. The SEE orchestrator is a god object (Antipattern #1). The engine gets a lean, phase-aware orchestrator built from scratch. It still gets a manifest entry.
6
One-way pipeline, runtime isolation. Source → staging → engine. No SEE references in deployed files. The engine is self-contained.
7
Engine determines targeting. 10 decisions are deferred to the engine's runtime process (see design doc “Engine-Phase Decisions” table). The plan builds process, not answers.
8
One subagent per skill in Phase 2. Prior experience: subagents stall on tasks requiring 20+ file reads. Keep tasks small.
9
Marketplace skills are available, not extracted. superpowers:brainstorming, writing-plans, executing-plans, document-skills:docx/pptx/pdf, d3js — these work in any Claude Code session. The engine uses them directly; they don't appear in the manifest. Note them in the capability architecture as available infrastructure.
10
The deployed engine is person-agnostic. operator/ ships with directory structure, templates, and reasonable defaults — not personal content. Skills and engine documents reference “the operator” and read from operator/ for all personalization. No skill hardcodes operator-specific assumptions about industry, role, geography, or career. Operator content arrives through Phase 0 onboarding, not through the build process.
11
Constitution from deployed reality. CLAUDE.md, session orchestrator, and README are written AFTER skills are deployed. They describe what the engine IS, not what it was planned to be. The capability architecture document (from the design synthesis) provides development context during skill building; CLAUDE.md encodes the finished product.

Skill Deployment Pipeline (Phase 2 Reference)

Clone-and-Go Pipeline

  1. Copy SKILL.md from source to staging: staged-skills/[engine-name]/SKILL.md
  2. Strip all source project references (paths, engagement names, project-specific context)
  3. Rename if the engine name differs from the source name
  4. Verify: reads as standalone? No references to SEE, WondaKB, Wonda, or any source project?
  5. Copy any working examples listed in manifest to staging
  6. Run acceptance test per manifest entry
  7. Deploy to engine: ~/Desktop/JobSearchEngine/skills/local/[engine-name]/SKILL.md

Fork-and-Adapt Pipeline

  1. Copy SKILL.md from source to staging
  2. Read the manifest entry's “What Changes” section — it lists every modification
  3. Apply each modification. The skill becomes a NEW skill that shares DNA with the source.
  4. Strip all source project references
  5. Self-test: read the skill as if you've never heard of the source project. Does it make sense?
  6. Copy working examples to staging
  7. Run acceptance test per manifest entry
  8. Deploy to engine

Build-New Pipeline

  1. Read the manifest entry's “What to Build” section
  2. Read the capability architecture document for how this skill fits the whole
  3. Read listed reference examples (scripts, prior outputs, working patterns)
  4. Write SKILL.md from scratch in staging
  5. Verify against the engine's directory structure and the capability architecture's methodology description
  6. Run acceptance test per manifest entry
  7. Deploy to engine

Post-Deploy (all classifications)

  • Verify no SEE references leaked into the deployed file
  • Log to projects/job-search-engine/CONTEXT.md
