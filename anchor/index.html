Protect · 01

Rotate the database key — today

This is the one genuinely time-sensitive item. It protects your whole database — which means every tester's data.

One of your test scripts has a full database connection string (with the password) written directly into the file, as a fallback. security Because it was there in the very first commit, it lives in your git history — so deleting the line now isn't enough on its own. Anyone who ever had a copy of the repo has the key.

Good news: this is the only leaked secret in the whole repo. Everything else correctly reads from environment variables. So this is a quick, contained fix — not a sign of a sloppy codebase.

Step A — rotate the password (a few minutes, in Supabase)

  1. Open your Supabase project → Project Settings → Database.
  2. Reset / rotate the database password. Copy the new connection string.
  3. Update DATABASE_URL in your Vercel project environment variables (and your local .env).
  4. Redeploy. The old key is now dead even though it's still in history.

Step B — get the key out of the code (your agent can do this)

▣ Prompt for your agent
In scripts/smokeTestOvertrader.ts, the database connection string is hardcoded as a fallback default (around line 18). Change it so the script reads the connection string ONLY from process.env.DATABASE_URL — exactly the way scripts/smoke-query.ts and scripts/smoke-test.ts already do it. If DATABASE_URL is not set, throw a clear error and exit; do NOT fall back to any literal string. Remove the old connection string completely, including from any comment.

Then scan the whole repo to confirm there are no other hardcoded credentials: search for "postgresql://", "supabase.com", and "password" and report anything that looks like a real secret.

Note for the human: rotating the actual database password is a separate manual step in the Supabase dashboard — this change only fixes the code so it can't happen again.
Protect · 02

Verify the webhook — close the open door

Your Clerk webhook endpoint currently trusts whatever is POSTed to it. It protects against someone forging signups and abusing your email sending.

The endpoint reads the incoming request and acts on it without checking that it actually came from Clerk. security That means anyone who knows the URL could send a fake “new user” event and trigger emails. The good part: you already have the svix library installed (it's literally the tool for this) — it just isn't wired up yet.

▣ Prompt for your agent
In src/app/api/webhooks/clerk/route.ts, the handler calls request.json() and trusts the payload without verifying the webhook signature. The svix package is already a dependency.

Add Svix signature verification using Clerk's current Next.js App Router pattern:
- Read the RAW request body as text (not request.json()).
- Read the "svix-id", "svix-timestamp", and "svix-signature" headers.
- Verify with new Webhook(process.env.CLERK_WEBHOOK_SIGNING_SECRET).verify(rawBody, headers).
- Return a 400 response if verification fails OR if the signing secret env var is missing.
- Only parse and use the payload AFTER verification succeeds.

Add CLERK_WEBHOOK_SIGNING_SECRET to .env.example (no value). Then verify by sending a request with a bad signature and confirming it returns 400, and confirm a correctly-signed Clerk event still works.
Protect · 03

Trust your trade data — three silent bugs in import

These are the most important to your testers, because they quietly corrupt the numbers your whole product is built on. None of them crash — they just make the data subtly wrong, which is the hardest kind of bug to notice.

Your broker-import layer is genuinely well-designed (one clean parser shape for every broker — see Section 7). These three are the kind of thing that only surfaces once real, varied CSVs show up.

3a · Timestamps shift depending on the server data integrity

Most parsers read a broker time like 2024-01-15 09:30:00 with plain new Date(...), which interprets it in the server's timezone. So the same CSV can import with different times on different machines, and broker-local times get stored as if they were UTC. For a product whose whole point is when and how someone trades, that's the data foundation moving under you.

▣ Prompt for your agent
In src/lib/brokerImport/parseCSV.ts, the dt() helper (around line 122) parses zone-less broker timestamps like "2024-01-15 09:30:00" with new Date(...), which resolves in the SERVER's local timezone. This means the same CSV imports with different timestamps depending on where it runs, and broker-local times are stored as if they were UTC — corrupting session-of-day and hold-time analysis.

Make timestamp parsing timezone-explicit and deterministic:
- First ask me to confirm the intended source timezone for zone-less broker exports (most US broker CSVs are in US/Eastern or exchange-local time). Do not guess silently.
- Parse zone-less timestamps into a correct UTC instant using that explicit timezone, never the server's local TZ.
- Audit every date helper (dt, dtMT4, dtNinjaTrader) and every parser so they are all timezone-explicit and consistent.
- If a broker's export DOES include a timezone offset, honor it rather than overriding it.
- Add a unit test that asserts a known broker timestamp parses to the same UTC instant regardless of process.env.TZ.

3b · European number formats get mangled data integrity

The main number parser strips commas, so a European-formatted value like 1,50 becomes 150. There's a separate European-aware parser, but it's only used in a few places. Any EU-format export through the wrong parser silently produces prices and P&L that are off by 100× (or fractions).

▣ Prompt for your agent
In src/lib/brokerImport/parseCSV.ts, num() (around line 92) removes commas, so European-format numbers like "1,50" become 150 and "1.234,56" becomes 1.23456. There's a separate numEuropean() used at only ~5 sites, while num() is used at ~58 sites. Any EU-locale export routed through a non-FTMO parser silently produces prices and P&L that are 100x off or fractional.

Make number parsing locale-unambiguous: detect or configure the decimal/thousands convention per broker or per file rather than assuming US format, OR normalize numbers at each parser's boundary so every parser passes correctly-typed values downstream. Keep the existing numEuropean call sites working. Add unit tests covering both "1,234.56" (US) and "1.234,56" (EU) and confirm both produce the same numeric value where they represent the same amount.

3c · Re-imports can drop (or duplicate) real trades data integrity

Duplicate detection keys on timestamp + instrument + size + price. But scaled or algo entries legitimately repeat that exact combination, so real fills can be discarded as “duplicates” — and re-importing the same file isn't reliably safe either.

▣ Prompt for your agent
In src/lib/brokerImport/reconcile.ts (around line 160), the duplicate-trade check keys on {entry_timestamp, instrument, size, entry_price}. Because matchFills splits one lot into multiple trades sharing the same timestamp/instrument/price, and scaled/algo entries legitimately repeat that tuple, real trades can be dropped as false duplicates — and re-importing the same file is not reliably idempotent.

Switch dedup to a stable unique key: prefer a broker-provided execution or order id when the CSV has one; otherwise add a deterministic import fingerprint (e.g. a hash of the source row plus the file) so identical re-imports are caught while legitimately-repeated fills are kept. Make re-importing the same file a no-op. Add tests for: (a) importing the same file twice creates no new rows, and (b) two legitimate same-price/same-size/same-time scaled entries are BOTH kept.

Small protective hygiene

Quick, low-risk items that still touch what testers see or what your logs store. Each is a small agent prompt.

4a · Stop logging raw CSV rows to the console security

The import code prints raw CSV headers and rows to the server log. Broker exports can include account labels, so this can quietly put personal data into your log storage — which contradicts the privacy promise written into that same file.

▣ Prompt for your agent
Across src/lib/brokerImport/parseCSV.ts (and any other import code), remove or gate the console.log statements that print raw CSV headers or row values. Broker exports can contain account labels and PII, and these logs land in serverless log storage, which contradicts the privacy contract written at the top of that file. Replace them with either nothing, or counts-only diagnostics (rows parsed / rows skipped) that NEVER print raw cell values, behind a DEBUG env flag. Also remove the leftover debug console.log lines in src/app/(onboarding)/onboarding/actions.ts.

Understand · 05

How anchor works

Here's the whole system in one picture. A trader tells you their system, imports their trades, and at the end of each session anchor measures where their execution drifted — then shows them their own pattern.

A nice detail worth calling out: the whole detection step is deterministic math, not an AI call. The “prompt” files in your repo (overtrader, rule-drifter) are the instructions you fed your coding agent to write the detectors — they're build notes, not something that runs live. That's actually a strength: your scoring is reproducible and debuggable, with no model-in-the-loop surprises.

Understand · 06

The four archetypes — your detection engine

Each archetype is a different way execution breaks down. They all share the same clean shape in code: a gate to even consider it, then weighted signals that decay over time, then a tier (none → state → pattern → archetype).

Revenge Trader
timing

Re-entering too fast after a loss. Gate: at least one loss in the session. Looks at compressed re-entry, size bumps after losses, and loss streaks.

Overtrader
frequency

Trading more than the system calls for. Gated on a maturity index plus participation deviation; seven signals, five subtypes.

Rule Drifter
procedural

Quietly stopping following the rules. Your most sophisticated one — it scales what it can detect to how completely the trader declared their rules.

Risk Drift
magnitude

Size creeping with emotion. Gate: a real correlation between size and P&L over recent trades. Detects reward-chasing vs. threat-compensation.

The thing I'd most want you to know: all of the weights, thresholds and decay windows live in your database config, not hardcoded in the logic. well done That means you can re-tune the whole model during beta with a data change instead of a deploy. That's a design decision most people don't make until much later.

Understand · 07

What you did really well

Not flattery — these are specific, and they're the things that are expensive to retrofit later. You did them up front.

  • No data leaks between users. Every single query is scoped to the logged-in person, and the routes that take an id double-check ownership before doing anything. This (an “IDOR” hole) is one of the most common ways small apps leak data, and you have zero of it.
  • Your detection model is configuration, not code. Weights, thresholds, decay — all in the database. You can recalibrate during beta without shipping.
  • A real safety gate on the thing that matters most. Your “show the trader their distribution, never diagnose them” rule isn't just a principle — there's a runtime filter that blocks prohibited language before anything reaches a user. Defense-in-depth on your core ethic.
  • One clean shape for every broker. Adding a broker is one function, not a rewrite. The way you disambiguate near-identical CSV formats is unusually thoughtful.
  • Input validation everywhere. Allow-lists, range checks, safe JSON handling. Better than most funded pre-launch apps.
  • You leave an audit trail. Every scoring run records which signals fired — exactly what you'll want when you're calibrating against real beta data.
  • You're tracking the framework's edge. You're on Next.js 16 / React 19 and using the new conventions correctly (your proxy.ts isn't a mistake — it's the current pattern). That's ahead of most.

Dig in · 09

Structural notes

Bigger than quick fixes — worth a decision before launch, not an emergency. Expand any you care about.

Pick one source of truth for your database schema

Right now your schema lives in three places at once: the root .sql files, the numbered migrations/, and the Prisma schema (which is a snapshot of the live DB). There's no Prisma migration history, so spinning up a fresh database means knowing the exact manual order to apply things. And Prisma vs the raw SQL disagree on a few “is this allowed to be empty” rules. Decide which one is canonical and make the others follow it — before you ever need to rebuild the DB under pressure.

Your scoring spec has drifted from your scoring code

The math doc and the actual detectors disagree in a few real ways — most notably the Rule Drifter “conflict” adjustment (the doc says add 0.10; the code multiplies by 1.10 — these diverge meaningfully at low scores). A couple of specced features (co-dominant patterns, tier protection, continuous volatility) aren't built yet. None of this is broken, but the code is the working truth — so re-sync the doc to the code, or ticket the gaps, so future-you isn't calibrating against a doc that lies.

You have two “which card to show” engines

There's the main intervention engine (capped, logged, language-gated) and a separate ~600-line insight-card generator that does its own version of the same job — and the second one doesn't have the prohibited-language safety filter. Both render to the dashboard. This is the kind of parallel code that drifts apart over time. Decide which is the future and fold the other into it — and make sure the safety gate covers both paths.

The single highest-leverage investment: a few tests

There are no automated tests yet, and your last several commits are all “fix parser X.” One small fixture CSV per broker, with a snapshot of the expected parsed output, would stop those regressions cold — and the timezone/locale/dedup fixes above all come with natural test cases. This is the cheapest reliability you can buy right now.

Add a way to delete a trader (before real users)

Your data model is careful about not losing data by accident — but that also means there's currently no clean path to delete a trader and everything attached to them. Once you have real users, you'll want that for privacy requests. Worth designing deliberately rather than improvising later.
