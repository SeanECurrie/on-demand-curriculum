Second Brain

“Capture without retrieval is a write-only system.”

– methodology/memory-architecture.md § Retrieval Surfaces

This document is the canonical reference. Architecture (docs/source/architecture.md), governance (docs/source/governance.md), and methodology (docs/source/methodology.md) cross-link here for depth.

What It Is¶

The second brain is a two-pipeline system layered on top of EngineOS:

  • Capture pipeline (write-side) – Two hook firing points (SessionEnd, PreCompact) spawn scripts/flush.py, which uses the Claude Agent SDK to compress the session arc into a structured daily-log entry. scripts/compile.py periodically promotes high-signal daily-log content into a knowledge-base of compiled concept articles. scripts/ingest.py ingests external source material into the same KB structure.
  • Retrieval pipeline (read-side) – Three layers (SessionStart injection, UserPromptSubmit mid-work hook, manual /recall skill) read a six-surface corpus in the same priority order. The hook handles ~90% of retrieval mechanically and silently; the skill handles the 10% the operator wants to drive explicitly or wants deeper than the hook’s 1024-char cap.

Both pipelines are observable: append-only health logs at scripts/hook-health.jsonl (capture-side) and scripts/retrieval-health.jsonl (retrieval-side) are summarized by scripts/health-review.py and scripts/retrieval-review.py for operator-driven keep/tune/kill decisions.

The principle holding it together is simple. Anything that must survive across sessions or compaction lives on disk at a predictable path. The context window is working space, not storage.

Capture Pipeline¶

The capture pipeline turns transient session conversation into durable disk state. It runs in three stages: hook-driven extraction (session-end.py, pre-compact.py), SDK-driven summarization (flush.py), and SDK-driven KB compilation (compile.py). External documents enter the same KB via ingest.py.

Firing Points: session-end.py + pre-compact.py¶

Two hook events fire flush.py:

Hook Script Fires when Min turns
SessionEnd hooks/session-end.py Claude Code session ends (any source: /exit, idle timeout, client close) 1 turn
PreCompact hooks/pre-compact.py Claude Code is about to auto-compact (context window filling) 5 turns

Both hooks read a JSONL transcript, extract the recent conversation as markdown, write it to a temp file at scripts/session-flush-<id>-<ts>.md, and spawn flush.py as a background subprocess. The hooks themselves do no API calls – they finish in under 10s of local file I/O. All API work happens in the spawned flush.py process so the agent’s session-close path is never blocked.

Both hooks have a recursion guard: if CLAUDE_INVOKED_BY is set in the environment (meaning the parent process was flush.py calling the Agent SDK, which runs Claude Code, which would fire SessionEnd again), they exit immediately. Without this guard the capture pipeline would loop on itself.

Shared Module: hooks/_flush_common.py¶

D29 (2026-06-04) extracted the duplicated extraction/spawn logic from session-end.py and pre-compact.py into a shared module. This is anti-drift discipline. The two hook scripts both call:

  • parse_hook_input() – read JSON from stdin, repair Windows backslash issues
  • extract_conversation_context(transcript_path) – read JSONL transcript, return (markdown_text, turn_count)
  • spawn_flush_process(context_file, session_id, turn_count, context_len) – cross-platform Popen of uv run python scripts/flush.py

The constants live at the top of _flush_common.py:

MAX_TURNS = 90     # 60 -> 90 2026-07-02 (telemetry gardening)
MAX_CONTEXT_CHARS = 60_000  # ... -> 40_000 2026-06-12 (L-V4) -> 60_000 2026-07-02 (73% of sessions cap-bound)

These were bumped from MAX_TURNS=30/MAX_CONTEXT_CHARS=15_000 in D29 after the 2026-06-01 session-capture experiment showed marathon sessions were silently truncating their substantive arc, then MAX_CONTEXT_CHARS was bumped to 40_000 on 2026-06-12 (fix-ledger L-V4) when health review showed >50% of sessions still hitting the 30_000 cap, and to 60_000 (with MAX_TURNS 60→90) on 2026-07-02 when the telemetry-gardening review found 73% of sessions still cap-bound and 9 flush errors whose records now also carry the exception text. Both firing points share the same caps automatically – bumping one in the future propagates without the next person having to remember the other.

scripts/flush.py – session-arc summarization¶

Spawned as a background process, flush.py reads the pre-extracted conversation context and uses the Claude Agent SDK (claude_agent_sdk.query() with allowed_tools=[], max_turns=2) to produce a structured daily-log entry. The prompt template (scripts/flush.py:115-145) requests:

**Context:** [One line about what the user was working on]

**Key Exchanges:**
- [Important Q&A or discussions]

**Decisions Made:**
- [Any decisions with rationale]

**Lessons Learned:**
- [Gotchas, patterns, or insights discovered]

**Action Items:**
- [Follow-ups or TODOs mentioned]

Skip rules are explicit: routine tool calls, trivial back-and-forth, content too obvious to record. If nothing is worth saving, the SDK returns FLUSH_OK and no entry is appended.

The summary is appended to daily/YYYY-MM-DD.md as a timestamped ### Session (HH:MM) block. If the daily-log file doesn’t exist yet for today, it’s created with skeleton headers (## Sessions, ## Memory Maintenance).

Retry layer (D30, 2026-06-04): _run_flush_attempt is wrapped in a 2-attempt loop with a 3s sleep between attempts. Transient SDK errors (concurrent-session lock, rate, OAuth refresh) usually succeed on retry. The retry attempt count is recorded in the health log.

Failed-flush safety net (2026-06-22, a2ff20e): the 60s dedup that prevents a double-flush only records its state on a successful save. A flush that errored is deliberately left un-recorded, so the next SessionEnd re-fire retries it instead of the dedup silently suppressing the safety-net re-flush. (Found after a real near-loss: a session’s first flush errored, recorded state, and the re-fire skipped — 60 turns survived only by manual recovery.)

Health observability: every invocation emits one JSON record to scripts/hook-health.jsonl (see Observability section below).

Per-close compile trigger (2026-06-22, lean-compile-sustainability): after flush.py completes a successful save, maybe_trigger_compilation() spawns compile.py on every qualifying close, so whatever you just closed lands in the KB immediately. It skips only when today’s daily log is unchanged since its last compile (hash check against scripts/state.json) or when a compile is already running. This replaced an earlier 18:00–06:00 time-of-day gate that caused a 4-day backlog when late/overnight closes fell outside the window. A pid-liveness lock with a 30-min TTL (scripts/.compile.lock) serializes concurrent compiles and debounces clustered closes into a single run of accumulated changes; the lock frees itself when the pid dies, the file is absent, or the TTL expires (no explicit unlock).

scripts/compile.py – KB promotion¶

compile.py is the LLM compiler: daily logs are source code, KB articles are the executable. Each daily-log entry is read once, passed through the Agent SDK with the schema in knowledge/AGENTS.md and the current knowledge/index.md catalog as prompt context, and produces zero or more updates to knowledge/concepts/*.md and knowledge/connections/*.md.

Lean compile (2026-06-22, COMPILE_CONTEXT_K=20): the original implementation inlined the entire KB (full text of every article) into every compile prompt, so cost scaled with KB size, not session size — fine at zero articles, unsustainable at a few hundred (per-log cost had risen from ~$2.50 in April at ~0 articles to ~$10–14 in June at ~280). Compile now sends the full index (cheap) plus only the top-K=20 articles most relevant to the log being compiled by keyword overlap; the agent keeps Read/Grep and pulls any other article on demand. Context per compile is now bounded by K, flat as the graph grows, instead of climbing with it (live-proven at ~$2.56/run vs the $10–14 trend).

Compile state lives at scripts/state.json. Each ingested daily log is tracked with its content hash, so a log that hasn’t changed since its last compile is skipped. Force-recompile is available via --all or --file <path>.

Recursion guard + buffering fix (D31, 2026-06-04): compile.py sets os.environ["CLAUDE_INVOKED_BY"] = "knowledge_compile" BEFORE any import that could trigger Claude Code – without this, compile.py’s internal Claude Code sessions recursively fire SessionEnd → flush.py, adding noise entries to today’s daily log. The same fix added sys.stdout.reconfigure(line_buffering=True) to the main entry point so compile.log reflects activity in real time instead of being silently block-buffered. The misdiagnosis of “compile.py broken since 2026-05-12” was actually just buffering – compile.py was running fine, the log file just looked frozen.

scripts/ingest.py – external source ingestion¶

Companion to compile.py with the same output format. Where compile.py reads conversation logs, ingest.py reads curated source documents (methodology docs, patterns, reference material). Usage:

uv run python scripts/ingest.py source.md                   # single file
uv run python scripts/ingest.py file1.md file2.md ...        # multi-file grouped ingest
uv run python scripts/ingest.py --dir methodology/           # all .md in directory
uv run python scripts/ingest.py --dry-run source.md          # preview
uv run python scripts/ingest.py --all                        # force re-ingest tracked

The prompt template signals to the SDK that these are polished references, not conversation – “Extract concepts with the depth the source deserves.” Use this when adding new methodology or patterns to the KB so the LLM treats them with appropriate weight.

Daily Logs (daily/)¶

Append-only per-day session arcs. The directory currently contains 50 files spanning 2026-04-12 → present (with backfilled gaps). Each file has the structure:

# Daily Log: YYYY-MM-DD

## Sessions

### Session (HH:MM)
[flush.py-generated structured entry]

### Session (HH:MM)
[next session]

## Memory Maintenance

Daily logs serve three pipelines: they are the compile.py input that feeds the KB; they are surface #4 in the retrieval corpus; and the last 30 lines of today’s log are injected at every session start via Layer 1.

Knowledge Base (knowledge/)¶

The compiled output. Current state:

Path Purpose Current size
knowledge/index.md Catalog of all KB articles with one-line summaries – the cheapest retrieval surface. GENERATED from article frontmatter since 2026-07-03 (A1) – never hand-edited 544 indexed articles
knowledge/concepts/*.md One-concept-per-file articles produced by compile.py and ingest.py 443 files
knowledge/connections/*.md Cross-concept articles capturing relationships between concepts 101 files

knowledge/qa/ Q&A-flavored sub-collection present, currently empty

The KB is the second brain’s long-term memory. It is read by retrieval Layers 1-3 (the index is injected at SessionStart; the concepts are grepped by the UserPromptSubmit hook; the full articles are read by /recall when matches surface).

Retrieval Pipeline¶

The retrieval pipeline (D32, 2026-06-04) is the read-side complement to the capture pipeline. It has three layers, all reading the same six-surface corpus in the same priority order.

Layer Mechanism Fires when Coverage target Cap
1. Session-start injection hooks/session-start.py Every session start Orientation – full KB index + last 30 lines of today’s daily log ~20K chars
2. Mid-work retrieval hook hooks/prompt-retrieval.py (UserPromptSubmit) Every prompt matching the heuristic gate ~90% – silent, mechanical, top-3 matches ≤1024 chars, ≤1s
3. Manual escalation .claude/skills/recall/SKILL.md Operator or agent invocation ~10% – explicit, ranked, deeper sweep unbounded

Layer 1 establishes orientation at session start. Layer 2 fills in mid-work context mechanically before the prompt reaches Tier 3 skill loading. Layer 3 escalates when the hook misses or the decision is load-bearing.

Phase C — the hybrid index behind Layer 3 (D57, 2026-07-03; measured, not default)¶

An optional on-device hybrid retrieval layer now sits BEHIND /recall: scripts/retrieval-index.py builds one portable, gitignored SQLite cache (retrieval-index.db — FTS5 BM25 + sqlite-vec dense embeddings via a local MLX bge-m3 model, reciprocal-rank fusion, mechanical “Doc: title > heading” chunk headers) over the full corpus; scripts/retrieval-query.py serves queries and --selftest runs a pre-registered probe battery. Grep remains the default — D32 is not overridden. /recall escalates to the hybrid path only on weak grep yield for paraphrase-shaped queries, and every escalation logs to scripts/retrieval-ab.jsonl (the “Retrieval A/B” dashboard tile); the operator adjudicates keep/tune/kill from that ledger after 10-20 sessions. The index is a rebuildable cache — markdown stays the only source of truth; refresh is wired into session-end and the nightly Gardener. Zero API cost (fully on-device). Degrade mode: FTS5-only when the embedding model is unavailable. Day-one measurement (pre-registered battery, reported honestly per D57): the big win over naive grep is BM25 itself (paraphrase hit@5: naive-grep 0/5 — a floor, not the full six-surface /recall — vs FTS5 4/5); dense fusion added nothing yet and diluted one hit. The hybrid layer was on probation by design — and D63 (2026-07-06) closed it. The recall-eval harness (scripts/recall-eval.py, gated in os-ci as m17) put the first hard recall@k/MRR/nDCG numbers on the stack and confirmed BM25 (FTS5) is the best mode at our scale (Success@10 0.821 vs hybrid 0.786; MRR 0.640 vs 0.477) — dense RRF fusion tanks keyword queries and lifts only paraphrase recall@10. So retrieval-query.py now defaults to --mode fts and /recall escalates via BM25; the dense path is repaired + pinned but retired as the escalation (opt-in via --mode hybrid for re-measurement). The harness also caught, on its first run, that the dense path had been silently degrading to FTS-only (a transformers dep drift swallowed by a broad except) — the exact silent-failure class a retrieval-quality ruler exists to expose.

Layer 1 – SessionStart Injection (hooks/session-start.py)¶

Fires once per session, before any user interaction. Reads two surfaces:

  • knowledge/index.md – the full KB catalog. Injected verbatim so the agent knows what articles exist before deciding what to look up.
  • Today’s or yesterday’s daily log – last MAX_LOG_LINES=30 lines of the most recent existing daily-log file. Restores in-flight context that compaction or session-close stripped.

The combined context is wrapped with date headers and emitted as hookSpecificOutput.additionalContext (Claude Code SessionStart convention). Hard cap at MAX_CONTEXT_CHARS=20_000 – truncates with ...(truncated) if exceeded. Configured in .claude/settings.json under SessionStart with a 15s timeout.

Compile legibility / confidence loop (2026-06-22): before the index, session-start.py also injects proof that recently-closed sessions actually compiled into the KB — it parses the last few ## [...] compile | <log> entries in knowledge/log.md and surfaces them as “your closed sessions, landed in the KB → +N new concepts, M updated ✓”. This addresses an observed trust gap: the operator kept sessions open and bloated because the capture→compile loop was invisible, so closing felt lossy. Making the payoff observable at the next session start is the fix — not more compiling.

Layer 1 is the orientation layer. It cannot answer specific queries – those need Layer 2 or 3 – but it ensures the agent never starts cold.

Layer 2 – UserPromptSubmit Mid-Work Hook (hooks/prompt-retrieval.py)¶

The mechanical retrieval layer. Fires on every prompt the operator submits. Configured in .claude/settings.json under UserPromptSubmit with a 3s timeout.

Heuristic gate – the hook only does work when the prompt looks like it might benefit from prior-context injection. Two conditions trigger the gate:

Condition Default config
Prompt contains a trigger word we, our, before, prior, previous, remember, similar, again, last time
Prompt’s first word is a question-form start have, did, what, how, why, when
Prompt is long enough min_prompt_chars=20

If neither trigger fires, the hook records gate_skipped in the health log and exits silently. Configuration lives at hooks/retrieval-triggers.json – edits are picked up on the next invocation, no restart needed.

Query-term extraction – once gated through, the hook tokenizes the prompt, drops stopwords (large built-in list at hooks/prompt-retrieval.py:69-83), and keeps up to 8 distinctive terms of length ≥4. A regex OR pattern over those terms is the search pattern for all six surfaces.

Corpus sweep – the hook searches surfaces in priority order, stopping when the exec budget (max_exec_ms=1000) is exhausted:

  1. logs/intelligence-log.md – per-row scoring, weight 3 * len(hits) + 5
  2. knowledge/index.md – per-row scoring, weight 2 * len(hits) + 3
  3. knowledge/concepts/*.md – slug match against query terms, weight 2 (cheap stem match, not full-file grep)
  4. daily/*.md (last daily_lookback_days=14) – file-level first-hit, score capped at min(len(hits), 5) + 1 so file-level surfaces don’t overwhelm per-row surfaces
  5. run-plans/*.md (last runplan_lookback_days=60) – same scoring as daily

Methodology is not swept by Layer 2 – it’s surface #6 and only enters via Layer 3 /recall when the query is methodology-flavored.

Rank, dedupe, format – matches are deduplicated by path (keep highest-scoring per path), ranked, top 3 selected. Output is a <prior-context> block:

<prior-context>
EngineOS retrieval -- top matches from the second brain (silent; ignore if not relevant):
1. logs/intelligence-log.md [2026-06-04]
   > [excerpt up to 220 chars]
2. knowledge/index.md
   > [excerpt up to 240 chars]
3. daily/2026-06-04.md
   > [first matching line, up to 200 chars]
</prior-context>

Hard caps + silent recovery – everything is bounded:

  • max_inject_chars=1024 – truncated with ... if exceeded
  • max_exec_ms=1000 – best-effort; surfaces stop being swept past deadline
  • Every error path is swallowed; the hook never blocks the user’s prompt cycle. On any failure it emits a health record with the failure mode and exits 0.

Health observability – one record per invocation appended to scripts/retrieval-health.jsonl. See Observability section.

Layer 3 – Manual /recall Skill (.claude/skills/recall/SKILL.md)¶

The operator-driven escalation layer. Pure Read/Grep/Glob, zero API cost (the skill’s allowed-tools frontmatter restricts it to Read, Grep, Glob). Invoked when:

  • Operator types /recall <query> explicitly
  • Operator language matches: “have we seen”, “what’s our prior thinking”, “what did we decide about”, “do we have notes on”, “remember”, “look up”, “search the second brain”
  • Layer 2’s <prior-context> injection arrived but looked thin or off-target
  • The agent is about to make a load-bearing decision in a domain where prior intelligence likely exists – per patterns/frameworks/retrieval-before-decide.md

Same six-surface corpus as Layer 2, same priority order, but no caps. Returns 3-7 ranked hits with paths and 2-3 line excerpts. Honest “nothing found” when corpus is empty.

Explicit non-behaviors (from .claude/skills/recall/SKILL.md:107-113):

  • Does NOT invoke scripts/query.py – that uses the Agent SDK and has API cost. /recall is pure-grep, near-zero cost.
  • Does NOT read whole concept articles unless the query specifically matches the article’s main subject – headers and first paragraphs are sufficient to decide relevance.
  • Does NOT add interpretive commentary – the skill is a search tool, not a research tool. The operator does the synthesis.
  • Does NOT hallucinate hits – “nothing found” is the correct answer when nothing matches.
  • Does NOT search across engine tenants by default – OS-level corpus only unless the query names an engine.

Why No Vector DB¶

At personal-KB scale (currently 544 indexed, against a <500-article research threshold), structured markdown index + ripgrep + LLM-reads-relevant-files outperforms vector retrieval on precision and is dramatically simpler. Pure Read/Grep/Glob – zero API cost, no infrastructure, no embeddings drift.

D32’s Phase C deferral carried explicit revisit conditions; as of 2026-07-03 (D57) the hybrid layer is BUILT but NOT the default — it sits behind /recall as a measured escalation while grep remains the answer path (see “Phase C — the hybrid index behind Layer 3” above). The original revisit conditions, which govern the HOOK and the eventual keep/tune/kill adjudication:

  • KB exceeds 2000 articles
  • Retrieval-health log shows gate hit rate >60% sustained AND injections judged useful (justifies always-on hook with larger cap) — the >60% half is now firing (first gardening brief, 2026-07-03); usefulness is what the A/B ledger accumulates
  • Gate hit rate <10% sustained (justifies killing hook entirely; keep only /recall)
  • Operator notices semantic misses that grep can’t surface (justifies hybrid vector layer)

External research synthesis in run-plans/2026-06-04-retrieval-layer.md Layer 3 (Karpathy + Cole Medin + Mem0 benchmarks) confirms grep + markdown index beats vector retrieval at this scale.

Six-Surface Corpus¶

All three retrieval layers read the same corpus in the same priority order. Higher surfaces have higher signal-to-noise. The stopping rule for /recall and the discipline pattern: if surfaces 1-2 yield 3+ strong hits, don’t sweep the lower surfaces.

Observability¶

Both pipelines emit append-only health logs reviewed periodically by the operator.

The fireable health process: kb-health (2026-07-01, D51)¶

One argless command composes the whole health picture — never duplicating the deep reviewers, only tailing them:

uv run python scripts/kb-health.py             # full report + refreshes scripts/kb-health.json
uv run python scripts/kb-health.py --verify-kb # the clearing motion: re-verify the ENTIRE KB

It composes: utils.compute_kb_stats() (live structural truth — notes, links, broken, orphans, index-desync, merge %), lint.py’s state checks (uncompiled + stale daily logs), and one-line vital signs from the five jsonl logs (flush, retrieval, usage, reviewer, compile-guard), each pointing at its deep-dive reviewer. Verdict: HEALTHY or NEEDS ATTENTION with an actionable fix-list. Since 2026-07-03 it also watches hot-file size: CONTEXT.md, DECISIONS.md, and registry files that grow past the whole-file Read budget (~20k tokens) get a flag pointing at the CONTEXT-HISTORY archival pattern — the check that would have caught CONTEXT.md at 144KB before three sessions tripped over it. The conversational trigger is the kb-health skill (“check the second brain”); the SessionStart hook surfaces a one-line 🧠 flag when the cached verdict degrades (silent when healthy; cache refreshed at session end alongside people-heat, capability-snapshot, and the living health dashboard).

One of those five vital signs deserves its own explanation, because this page tails it without saying what it is: scripts/reviewer-health.jsonl is the telemetry of the federated-reviewer layer (patterns/frameworks/federated-reviewer.md, D36) — a ladder of reviewers at increasing independence (sanity-check’s same-context self-check → output-self-test’s binary gates → the adversarial-evaluator’s independent context → outside reviewers). Every firing appends one record via scripts/reviewer-health-emit.py: reviewer, surface, verdict, flagged count, leads_surfaced. Read it as a LIVENESS log, not an impact scoreboard — all-pass is its architecturally expected shape, because real catches route to the run plan’s Layer 5 and the intelligence log (Category=Review). scripts/reviewer-review.py runs the periodic keep/tune/kill review over it, and kb-health tails its last record as one vital sign.

scripts/kb-stats.py is the single source of truth for any “by the numbers” claim about the second brain (--json for machine use). Nothing downstream hand-types a KB number — hand-typed state rots (D46; an investor-diligence engagement explainer drifted 373-vs-320-vs-actual before this existed).

The derived index (A1 description single-sourcing, 2026-07-03): knowledge/index.md is a GENERATED artifact. Every article carries type: + description: frontmatter (backfilled across the whole KB by harvesting the existing index rows verbatim); scripts/generate-index.py derives the index from frontmatter (--check verifies freshness), and compile.py, ingest.py, and query.py all regenerate it mechanically after every run — including failure paths, so a mid-run SDK death after partial article writes still lands in the index. The producer LLMs write the summary ONCE, in the article; nothing hand-writes index rows anymore. This made the historical index-desync class (docs/known-issues/compile-index-write-desync.md — article on disk, index row never written) impossible by construction, the same derived-over-hand-duplicated move as the D52 census tokens. Run plan: run-plans/2026-07-03-a1-description-single-sourcing.md; adopted from the OKF review’s one load-bearing finding (run-plans/2026-07-03-okf-adoption-review.md).

The post-compile guard (compile.py::_verify_compile_output → scripts/compile-verify.jsonl): after every compile, mechanically verifies each touched article carries the description:/type: frontmatter the derived index needs (a missing field = an empty Summary cell, visible but useless to /recall) and every emitted link resolves in the vault. Detection, not prevention. Its former index-desync check retired with A1 (desync now impossible by construction; kb-stats’ index-sync stat remains as a staleness backstop). Warnings accumulate in kb-health’s compile-guard vital until a clean full-KB verification record supersedes them (--verify-kb, run only after reconciling).

The retrieval-quality ruler: scripts/recall-eval.py (2026-07-06): a pre-registered eval harness (28 cases, recall@k/MRR/nDCG, gated in os-ci as m17) that puts hard numbers on the retrieval stack instead of vibes. It earned its keep on day one twice: it exposed that the dense/embedding path had been silently degrading to FTS-only (a dependency drift swallowed by a broad except), and after that repair it falsified the “repair will help” assumption — measured hybrid underperforms pure BM25 at this corpus scale, which produced D63 (see the Phase C section above). Any future retrieval change is adjudicated against this baseline, not intuition.

Graph diagnostics: scripts/kb-graph-analysis.py (2026-07-08): the second-brain graph as a diagnostic instrument, not decoration. A networkx pass over the wikilink graph (importing the same canonical compute_kb_stats walk — one implementation, no drift) computes real communities (greedy modularity, replacing an earlier keyword heuristic), islands (connected components), community-to-community structural gaps (“blind spots”), semantic missing-bridge candidates (on-device embedding cosine, with keyword degrade), conceptual gateways (betweenness), and a diversity band summarizing the graph’s shape. Results are cached JSON consumed by the console’s 3D graph globe (recent/hubs/communities/islands/bridges modes) and a diagnostics drawer. Everything it surfaces is a lead the operator adjudicates — nothing is ever auto-linked. This formalizes a motion the operator had been doing by eye in Obsidian: catching real KB gaps by staring at the graph’s shape.

Link-truth model (2026-07-01): utils.wiki_article_exists resolves vault-wide — the Obsidian vault root is the repo root, so cross-layer links to methodology/, patterns/, logs/, engine files etc. are valid edges (hidden dot-directories excluded, matching what Obsidian indexes); extract_wikilinks ignores code spans and fences (Obsidian doesn’t link inside code). All graph tools (kb-stats, kb-audit, lint) consume the ONE walk in utils._walk_kb_links — a single implementation, no drift.

Capture-side: scripts/hook-health.jsonl¶

One record per flush.py invocation. Schema:

ts, session_id, chars_input, turn_count, cap_hit, attempts, result, response_chars
  • cap_hit – which cap bound the extraction: chars, turns, or none
  • attempts – 1 if first attempt succeeded, 2 if retry was needed
  • result – saved (entry written), flush_ok (nothing worth saving), flush_error (SDK failure after retry)

Summarized by scripts/health-review.py:

uv run python scripts/health-review.py              # full summary
uv run python scripts/health-review.py --recent 20  # last N records
uv run python scripts/health-review.py --since 2026-06-01

The script reports result distribution, retry usage (and retry success rate), cap-hit distribution, and input/output character distributions. Heuristic: if more than half of sessions are hitting a cap, the script suggests another bump.

Retrieval-side: scripts/retrieval-health.jsonl¶

One record per UserPromptSubmit invocation. Schema:

ts, session_id, prompt_chars, query_terms, gate_triggered, gate_reasons,
corpus_searched, matches_found, matches_returned, chars_injected, exec_ms, result
  • gate_triggered – did the heuristic gate fire?
  • gate_reasons – which triggers fired (trigger_word:we, question_start:what, etc.)
  • corpus_searched – which surfaces were swept before the deadline ran out
  • result – injected, no_matches, gate_skipped, empty_prompt, stdin_error, search_error, no_terms

Summarized by scripts/retrieval-review.py:

uv run python scripts/retrieval-review.py             # full summary
uv run python scripts/retrieval-review.py --recent 25
uv run python scripts/retrieval-review.py --since 2026-06-04

The script reports gate fire rate, injection size distribution, exec-time distribution (flagging invocations that exceeded the 1000ms budget), top query terms, and top gate-fire reasons.

Usage / token-delta: scripts/usage-log.jsonl (2026-06-23)¶

A third health log, parallel to the two above, recording the token footprint of each interactive session alongside whether the second brain was actually engaged. The point (operator ask) is to distinguish second-brain-engaged sessions from cold ones, so the system can eventually measure whether the brain changes a session’s footprint — the data foundation behind the otherwise unmeasured “it roughly doubled my output” intuition.

hooks/session-end.py spawns scripts/usage-emit.py as a background process after the flush spawn — fully isolated, every error swallowed, so usage logging can never delay or affect memory capture. usage-emit.py re-parses the transcript independently and appends one record:

ts, session_id, cwd, duration_min, turn_count, models,
input_tokens, output_tokens, cache_creation_tokens, cache_read_tokens, total_tokens,
subagent_tokens, web_search, web_fetch,
second_brain: { retrieval_injections, kb_reads, recall_invoked, engaged }

engaged derives from real evidence — retrieval injections for this session_id in retrieval-health.jsonl, transcript reads of knowledge/ paths, or a /recall invocation. The always-on SessionStart index injection does not by itself count as engaged (or every session would look engaged). Token totals sum per-assistant-message usage, so total_tokens is the session’s true tokens-processed footprint (cache reads recur each turn and dominate long sessions) — not new generation.

Summarized by scripts/usage-review.py:

uv run python scripts/usage-review.py              # full summary
uv run python scripts/usage-review.py --recent 15

The headline is now the economy lens (2026-07-02, D53). Our own telemetry redefined what this instrument is for: session cost ≈ context-size × turn-count, re-paid every turn — one measured session ran ~96% cache reads across its hundreds of turns. So usage-review.py --economy leads with the levers that actually move cost — tokens/turn, ctx/turn (the always-loaded context floor = cache_read ÷ turns), cache-hit%, cache-rebuild tax, model mix, subagent share, and the prior-vs-recent trend — all correctness-neutral. The dashboard’s “Usage / Tokens” tile mirrors it (yellow when tokens/turn rises >10%; it went yellow on day one — the instrument working). The disciplines it enforces (memory feedback_usage_economy_disciplines, concept knowledge/concepts/session-usage-cost-structure): fewer/denser turns, protect the ~5-min cache on stalls, match model+effort to task, sequential-near-limit.

The original engaged-vs-cold comparison is retired (2026-07-02, D54). At a degenerate 26-engaged-to-1-cold ratio (and the one cold session a 3-turn stub) it had no baseline, so print_comparison now self-suppresses to a one-line honest note below a minimum-cold floor and auto-restores the full table if a real cold baseline ever accumulates (self-healing, never-delete). The founding “does the second brain change a session’s footprint?” question is recorded as unanswerable by observation at this engagement ratio — it would need a deliberate KB-off A/B nobody is likely to run. See run-plans/2026-06-23-session-usage-delta-log.md and DECISIONS.md D53/D54.

Keep / Tune / Kill Cadence¶

Both review scripts encode decision rules. The operator runs them periodically – weekly is a reasonable default; after major load shifts (KB doubling, hook-config changes) is mandatory.

Capture-side decision rules (from scripts/health-review.py):

  • flush_error rate >5% after retries → real signal worth escalating beyond retry layer
  • Cap-hit rate >50% → consider bumping MAX_TURNS / MAX_CONTEXT_CHARS in hooks/_flush_common.py
  • Thin saved responses (<800 chars) dominant → flush is extracting little substance, possibly because conversation context is low-signal

Retrieval-side decision rules (from scripts/retrieval-review.py + DECISIONS.md D32):

  • Gate hit rate <10% sustained → too quiet; loosen triggers or kill hook (rely on /recall)
  • Gate hit rate >60% sustained → too noisy; tighten triggers OR keep if injections are useful
  • Healthy band: 10-60%
  • Mean chars_injected near 1024 cap → consider bumping max_inject_chars
  • Operator subjective: injections judged irrelevant >50% of the time → tighten or kill

First decision pass is after ~10 sessions live. Subsequent reviews are ad hoc when suspecting drift.

Discipline Patterns¶

The pipelines have mechanical backing, but mechanical backing alone does not guarantee the agent uses them well. Two framework patterns encode the discipline layer:

Write-Side: patterns/frameworks/session-end-audit-before-flush.md¶

Before /exit on any substantial session, audit the second-brain coverage gap and close it manually. flush.py’s extraction window misses substance in marathon multi-day sessions – the audit-before-flush discipline closes the gap that the hook architecture cannot.

The audit covers 8 surfaces: daily/, logs/intelligence-log.md, logs/activity-log.md, knowledge/log.md, engine CONTEXT.md files, engine DECISIONS.md files, memory/MEMORY.md, and the patterns directory. The discipline fires reflexively on close-out signals – “wrap up”, “before I exit”, “did this get captured?”, session crossings 50+ tool calls, run plan marked COMPLETE.

Validated 2026-05-23 (a client-engagement marathon): 9 deliverables captured, full hook chain validated end-to-end, governance hook fired mid-execution to enforce the same discipline mechanically.

Read-Side: patterns/frameworks/retrieval-before-decide.md¶

Before recommending or implementing in a domain where EngineOS has prior intelligence, query the second brain first. Don’t trust the agent to remember to look – fire the lookup mechanically (Layer 2 hook) or invoke it deliberately (/recall, Layer 3).

The pattern names internal-archive retrieval as a first-class part of “research before agreeing” (CLAUDE.md Core Behavior #1). The instruction targets external sources by default – Bright Data, Context7, web search – and does not reliably trigger internal-archive lookup. The discipline pattern closes that category gap.

Trigger signals: operator prompts containing we, our, before, prior, previous, remember, similar, again, last time; question-form prompts; about to recommend architecture/methodology/pattern in a known-domain; about to defer something (check first if it’s been considered before).

Composition¶

The two patterns are sister disciplines. Capture without retrieval is a write-only system. Retrieval without capture is a read-empty system. Both need their respective discipline layers because the mechanical hooks are best-effort, not exhaustive:

  • audit-before-flush – ensures substance lands in the second brain (write-side)
  • retrieval-before-decide – ensures the agent reads the second brain before deciding (read-side)

Memory-feedback files (~/.claude/projects/.../memory/feedback_*.md) provide the auto-fire triggers so the disciplines self-fire on natural operator language without requiring the operator to remember to invoke them.

How To Use¶

Looking something up (/recall)¶

When you want to know if EngineOS has prior thinking on a topic:

/recall <query>

Or use natural language that triggers the skill: “have we looked at X”, “what’s our prior thinking on Y”, “what did we decide about Z”. The skill returns 3-7 ranked hits with paths and 2-3 line excerpts from the six-surface corpus. Zero API cost (pure Read/Grep/Glob).

If /recall returns nothing satisfying and you want LLM-ranked deeper search, run:

uv run python scripts/query.py <question>

This has API cost (uses the Agent SDK) but can synthesize across many hits. Use when grep alone isn’t enough.

Reading the health logs¶

After ~10 sessions of any new hook configuration, or weekly as a default cadence:

# Capture pipeline
uv run python scripts/health-review.py

# Retrieval pipeline
uv run python scripts/retrieval-review.py

# Session usage / token-delta (engaged-vs-cold)
uv run python scripts/usage-review.py

Decision rules are baked into the scripts’ output hints. The retrieval review will flag if your gate fire rate is outside the 10-60% healthy band; the capture review will flag if more than half of sessions are hitting a cap.

Tuning the retrieval hook¶

If scripts/retrieval-review.py says the gate is too quiet (<10%) or too noisy (>60%), edit hooks/retrieval-triggers.json:

{
  "trigger_words": ["our", "before", "prior", "previous", "remember", "similar", "again", "last time"],
  "trigger_starts": ["have", "did", "what", "how", "why", "when"],
  "max_inject_chars": 1024,
  "max_exec_ms": 1000,
  "max_matches_returned": 3,
  "daily_lookback_days": 14,
  "runplan_lookback_days": 60,
  "min_query_term_len": 4,
  "min_prompt_chars": 20,
  "people_close_scan": true
}

Changes are picked up on the next invocation. No restart needed. Common tunings:

  • Too quiet → loosen trigger_words (add domain-specific terms), drop min_prompt_chars, drop min_query_term_len
  • Too noisy → remove generic trigger words (we, our), raise min_prompt_chars
  • Injections feel thin → bump max_inject_chars to 1500-2048
  • Hook timing out → cut runplan_lookback_days and daily_lookback_days

What to do if retrieval misfires¶

Hook injected but content was irrelevant → ignore it. The <prior-context> block is silent; the agent is instructed to ignore if not relevant. If this happens >50% of the time over a review window, tighten triggers or kill the hook (rely on /recall).

people_close_scan is the one non-retrieval key in the same config: it gates the session-orchestrator’s close-out “these new people came up — capture?” scan (Profiling Layer B). Set false to silence it; the always-on people surface (Layer A, prompt-retrieval.py) is unaffected.

Hook didn’t fire and you wanted it to → invoke /recall <query> directly. The skill is the manual escalation by design. After several manual escalations on similar phrasings, consider adding the operator’s natural trigger phrasing to hooks/retrieval-triggers.json.

Hook fired but found nothing → either the corpus genuinely doesn’t have the answer (/recall will confirm) or your query terms don’t match how the corpus indexed the concept. Try synonym rephrasing, or treat the gap as a signal to compile new KB content.

Hook is silently failing → check scripts/retrieval-health.jsonl for stdin_error, search_error, or invocations missing entirely. The hook never blocks the prompt cycle; silent failure is by design but observable through the health log.

Compiling the KB manually¶

The per-close auto-compile (flush.py:maybe_trigger_compilation) fires after every session close that saved content, when today’s daily log has changed since last compile (skipping when a compile is already running). To force-compile:

# Compile new/changed logs only
uv run python scripts/compile.py

# Force recompile everything
uv run python scripts/compile.py --all

# Compile a specific log
uv run python scripts/compile.py --file daily/2026-04-01.md

# Preview without writing
uv run python scripts/compile.py --dry-run

Compile state lives at scripts/state.json. Each daily log is tracked with its content hash so unchanged logs are skipped.

Ingesting external source material¶

To pull methodology docs, patterns, or other curated reference material into the KB:

uv run python scripts/ingest.py source.md
uv run python scripts/ingest.py --dir methodology/

ingest.py uses the same output format as compile.py but signals to the SDK that the input is polished reference, not conversation – the LLM gives the source the depth it deserves.

When the discipline patterns fire¶

You’ll feel the read-side discipline (retrieval-before-decide) in moments like:

  • About to recommend an architecture choice in a domain EngineOS has explored
  • Operator asks “should we X” or “what’s our typical approach to Y”
  • About to defer something to a future session (“we can decide this later” – check if the corpus has already decided it)

You’ll feel the write-side discipline (audit-before-flush) in moments like:

  • Operator says “wrap up” or “let’s exit”
  • Session has produced a deliverable that lives outside CONTEXT.md
  • Session crosses 50+ tool calls or spans multiple days
  • A run plan is marked COMPLETE

Both patterns fire reflexively via memory-feedback triggers (feedback_lookup_before_decide.md, feedback_audit_before_flush.md) without requiring the operator to explicitly invoke them.
