Engines are the reason EngineOS exists. The OS layer (Layer 1) holds shared capabilities – skills, methodology, governance, design system, operator identity. Engines (Layer 2) are the domain-specific workspaces where those capabilities get applied to real problems. A job search, a client engagement, a curriculum deliverable, a competitive analysis – each runs inside an engine that inherits the OS toolkit and adds what the domain requires.

This document explains how engines work, what they inherit, what they own, and where the nine known engines currently stand. As of 2026-06-05 there are four active tenants in engines/ (job-search, job-search-arnett, on-demand-curriculum, sales-enablement) and six engines still operating at their Desktop source locations.

What Engines Are¶

An engine is a Layer 2 tenant at engines/<engine-name>/. The term “tenant” is deliberate: engines are isolated from each other but share a common platform. They are peers – no engine outranks another – and none is a peer to the OS itself. The OS serves engines; engines do not modify the OS.

Each engine is a self-contained domain workspace. It has its own engagement data, its own knowledge bases, its own CONTEXT.md tracking session state, and (optionally) its own domain-specific skills that encode workflows unique to that domain. What it does not have is its own copy of the shared infrastructure. Governance, methodology, patterns, design system, operator identity, and the 29 OS-level skills are inherited from Layer 1.

This separation serves two goals:

  1. No capability duplication. When a skill improves at the OS level, every engine benefits. When a methodology doc is updated, the update is global. There is one source of truth for shared capabilities, and it lives at Layer 1.

  2. Domain isolation. An engine’s engagement data, client knowledge bases, and domain workflows are its own. Work in the job search engine does not leak into the sales enablement engine. Cross-engine operations require explicit operator confirmation.

What Engines Do NOT Duplicate¶

This is a hard rule, not a suggestion. If an engine needs a capability that lives at Layer 1, it references the OS version. No local copies of:

  • Operator identity – use operator/
  • Logging specification – use .claude/rules/logging.md
  • Methodology docs – use methodology/
  • Patterns – use patterns/
  • Design system – use design-system/
  • Governance skills – use OS-level .claude/skills/

The only exception: if an engine has a domain-specific variant that genuinely differs from the OS version, it keeps that variant locally and documents why it diverges. ODC’s methodology/three-tier-hardening.md is an example – it classifies walkthrough security steps into essential/educational/operational tiers, which has no OS-level equivalent. That methodology stays in the engine.

Starting a New Engine¶

Four steps. Not optional, not flexible.

1. Create the directory structure.

engines/<engine-name>/
  README.md       -- Engine identity: what it does, what it owns, what it inherits
  CONTEXT.md      -- Session state: what's happening now, what changed, what's next
  DECISIONS.md    -- Decision log: context, options, decision, why

These three files are the minimum viable engine. README.md is the engine’s self-description. CONTEXT.md is the handoff mechanism between sessions (same role it plays at the OS level). DECISIONS.md records choices with their reasoning so future sessions understand why things are the way they are.

2. Add domain-specific directories as needed.

There is no mandatory directory structure beyond the three files. Each engine adds what its domain requires:

  • engagements/ for client work (SEE)
  • targets/, arsenal/, lanes/, market/, evidence/ for job search data (JSE)
  • templates/, intake/, outputs/ for curriculum delivery (ODC)
  • knowledge/ for accumulated domain intelligence (any engine)
  • config/ for integration configuration (JSE has Notion config here)

The structure follows the domain, not a template.

3. Register the engine in registry/engines.md.

The engine registry maps engine names to their current locations (source and tenant), migration status, and domain. This is the OS’s awareness layer – session-orchestrator reads it to detect which engine context is active.

4. Domain-specific skills stay in the engine.

Skills that do not generalize across engines belong at engines/<engine-name>/.claude/skills/, not at the OS level. The test: would any other engine ever use this skill? If no, it is a domain skill. If yes, it belongs at Layer 1.

See Skill System for how domain skills differ from OS skills in discovery, allowed-tools scoping, and chain participation.

Active Tenants¶

Four engines have migrated to EngineOS tenants. They range from a fully self-contained active engine (JSE) to a sibling tenant scoped to a second operator (job-search-arnett) to a test configuration validating OS capabilities (SEE).

Job Search Engine (JSE) – Active¶

Location: engines/job-search/ Status: Self-contained after 5-phase migration. The most data-rich tenant. Real use: The operator’s live job search, Phase 2 (Targeting) in active execution.

The JSE is the system’s proof that EngineOS works as a daily operating environment. It runs a 9-lane pipeline architecture with tiered compensation strategy ($80K-$220K+ across 4 tiers), maintains live Notion integration (3 databases: Pipeline, Contacts, Outreach), and has a Node.js DOCX build pipeline for resume generation.

8 domain skills at engines/job-search/.claude/skills/:

Skill Purpose
target-builder Scored, tiered target company lists. Lane management, JD verification, contact identification.
contact-profiler Person profiles for hiring managers, recruiters, referrals. Working style taxonomy, duplicate prevention.
positioning-engine Career positioning synthesis. SWOT, gap analysis, Four Key Stories, vertical positioning, resume angles.
outreach-builder Personalized outreach sequences. 5 frameworks (warm intro, cold professional, recruiter response, post-interview, networking nurture).
resume-generator Atom selection to markdown to DOCX. Unverified claims discipline. Requires the _build/ Node.js pipeline.
materials-qa 8-phase quality gate for all external materials. Fact-checking, inflation detection, cross-document consistency. Complements the OS qa-pipeline.
html-deliverable-generator Career-specific HTML deliverables. Portfolio pages, project showcases, HTML resumes.
interview-processor Interview debrief to structured intelligence. Tag, contextualize, chain, extract, route to target folders and contact profiles.

What makes JSE notable as a tenant: - It carried the governance innovations (phase-controller, depth governor, sanity-check) that became EngineOS’s governance stack. The JSE was the first engine to enforce skill chains mechanically. - Its Desktop source location (~/Desktop/JobSearchEngine/) now holds 15 symlinks pointing back to the tenant – the migration inverted the dependency. - It has its own activity log (94+ entries) and intelligence log (30+ strategic insights) – engine-local logs that predate the OS-level logging consolidation. The OS logging spec now routes new entries to root logs/ with engine tags.

Job Search Engine – Arnett (job-search-arnett) – Active¶

Location: engines/job-search-arnett/ Status: Bootstrapped 2026-06-04. Sibling tenant to JSE. Real use: Live job search for Arnett McMurray, run as a second operator inside EngineOS.

The Arnett tenant is the first proof that the engine model supports multiple instances of the same engine type. It is a peer to engines/job-search/ (Sean’s), not a child of it. Mechanical isolation comes from the PreToolUse scope-matching hook: writes to engines/job-search-arnett/... require an active run plan at this tenant’s scope (or root), and writes targeting Sean’s JSE will fail and force the agent to redirect.

0 tenant-local skills. This tenant inherits all 8 JSE domain skills from engines/job-search/.claude/skills/ – target-builder, contact-profiler, positioning-engine, outreach-builder, resume-generator, materials-qa, html-deliverable-generator, interview-processor. If a skill needs adaptation for Arnett’s shape, the convention is to capture the gap as an intelligence-log entry and propose OS-level (or JSE-level) changes via a separate run plan rather than fork the skill locally.

Shared build pipeline. The Node.js _build/ pipeline used by resume-generator lives at engines/job-search/_build/ and is referenced by absolute path. Tenant-scoped outputs land in engines/job-search-arnett/arsenal/.

What makes the Arnett tenant notable: - It is the first sibling-tenant configuration in EngineOS. Same engine type (JSE), different operator profile, mechanically isolated data, shared skill surface. - Cross-tenant attribution flows through the engine tag on activity log entries – no multi-user module activation was required. The existing logging spec already supports it. - It validates that domain skills generalize across operators when they were built to read from configurable evidence and profile sources rather than hardcoding to a single person.

On-Demand Curriculum (ODC) – Portfolio¶

Location: engines/on-demand-curriculum/ Status: Portfolio engine. 8 completed outputs. Stable, available for new work. Real use: Produces interactive HTML walkthroughs and structured documentation – including the documentation you are reading right now.

ODC is an interactive curriculum delivery engine. It takes a person, a topic, and an operator brief, and produces large-format, single-file HTML walkthroughs tailored to the specific recipient. The operator (Sean) is the proxy for all intake – the engine talks to Sean, not end users.

2 domain skills at engines/on-demand-curriculum/.claude/skills/:

Skill Purpose
pipeline-start Run controller with 6-type classification (A through F). Type A is new output from scratch (full pipeline). Type F is review artifact (document-to-HTML, skips research/synthesis). Builds run plans, forces skill invocation, gates on operator approval.
review-artifact Transforms dense markdown documents into interactive single-file HTML walkthroughs. The execution skill for Type F operations.

Domain methodology: methodology/three-tier-hardening.md – classifies walkthrough security steps into essential/educational/operational tiers. This is the one domain methodology doc that stays local because it has no OS-level equivalent.

What makes ODC notable as a tenant: - It was the primary donor for editorial methodology. The credibility tiers, editorial standards, and section construction approach that now live at the OS level were reverse-engineered from ODC’s production process. - Its 8 completed outputs include the Derek Hargens EngineOS walkthrough (live at GitHub Pages), the JSE design showcase, and this documentation project. - The pipeline-start skill is a domain-specific orchestrator that parallels phase-controller at the OS level but is tuned for curriculum delivery workflows. It handles the 6-type classification that determines which skill chain runs.

Sales Enablement Engine (SEE) – Test Configuration¶

Location: engines/sales-enablement/ Status: Test fixture for Phase 5 validation. All production capabilities lifted to OS. Real use: Validates that EngineOS can serve a real SEE engagement using OS-level skills.

The SEE is the ecosystem’s original engine and its most prolific OS donor: 49 skills and 37 patterns were lifted from SEE source to EngineOS Layer 1 during the build. As a tenant, the SEE is deliberately lightweight. It carries no domain skills of its own because every capability it needs now lives at the OS level.

0 domain skills. Everything is inherited.

What makes SEE notable as a tenant: - It serves as the acid test for the tenant model. If an engine that donated 49 skills to the OS can operate using only OS-level skills against its own engagement data, the architecture works. The B-chain validation test (B1-B8) ran an 8-step engagement chain through session orientation, integration discovery, research, knowledge buildup, transcript processing, deliverable production, and QA validation – all using OS skills. B7 QA found 12 issues (1 critical) across 4 deliverables, demonstrating the composited QA pipeline catches real defects. - Its source engagement data stays at ~/Desktop/SalesEnablementEngine/engagements/, not copied into the tenant. The tenant points to source data. Full migration is future work after the validation gate passes. - Test fixtures (engagement brief, transcript, Attio export, Notion export) are staged at engines/sales-enablement/test-fixtures/.

Provenance – Where Capabilities Came From¶

EngineOS was not designed top-down. It was built bottom-up from an ecosystem audit that read 11 source projects, produced 89 finding files and 7 cross-cutting analyses, and traced each capability to its origin through skill genealogy. The build principle was best-version-wins compositing: when multiple engines carried a capability, the most mature version was lifted, preserving provenance.

The capability registry (registry/capabilities.md) tracks the source of every OS-level capability with stable identifiers. Here is the source distribution across major capability domains:

Governance¶

Primary source: JSE. Genuine innovation with no predecessor.

The governance stack – phase-controller, depth governor, output self-test, sanity-check – originated in the JSE. No earlier engine had forced skill chains, disk-persisted run plans, or binary quality gates. The JSE built these because it needed them: a live job search with real stakes and no room for sloppy outputs. Phase-controller’s 11 forcing function rules, the iteration envelope (produce-evaluate-retry, max 3), and contract hardening (Step 2.5) were all JSE innovations.

Supporting contributions: WondaKB (content-updater routing), SEE (audit-trail logging, session orientation patterns).

Research¶

Primary source: JSE, drawing from SEE + ODC.

Market scanning capability lives at the JSE lineage. The structured findings system (7 types: Discovery, Confirmation, Contradiction, Comparison, Gap, Risk, Recommendation) came from the JSE’s findings-formatter, which preserved ODC’s earlier findings patterns. Credibility tiers (the 5-tier source classification) came from ODC. Research cadence methodology came from ODC. The compositing took JSE’s execution rigor and ODC’s methodological framework.

Integrations¶

CRM (Attio): SEE. The full 5-skill Attio chain (mapper, ops, qualify, optimizer, refiner) originated in the SEE, which was built as a sales enablement tool with CRM at its center.

Notion: WondaKB + SEE. Notion mapping originated in WondaKB’s multi-user architecture (workspace discovery across team boundaries). Notion operations (the data operation skill with direct API scripts) were built in SEE and enhanced during JSE migration. The composited version carries WondaKB’s mapping patterns with SEE’s operational capabilities.

Content Production¶

Composited from MLR + ODC + SEE.

This is where compositing matters most. No single engine had the full content production stack: - MLR contributed enterprise CSS, HTML-to-PDF pipeline, and the programmatic QA approach - ODC contributed section construction (incremental large-output generation), render-validate (Puppeteer visual verification), and the editorial methodology that governs content quality - SEE contributed campaign building, lead building, transcript processing, and framework explanation

The OS-level production pipeline draws from all three.

Methodology¶

ODC (editorial, credibility) + JSE (governance, depth) + MLR (QA).

The 15 methodology docs at the OS level trace to three primary donors: - ODC: Credibility tiers, editorial standards, research cadence, section construction methodology, findings patterns - JSE: Depth assessment (binary Scan/Deep-Dive classification), planning enforcement, anti-patterns catalog, binary self-test methodology - MLR: QA pipeline methodology (composited verification stages)

The memory architecture methodology (2-layer logging model) drew from SEE + WondaKB operational logging patterns, formalized through Grafana/Datadog/Azure/OpenTelemetry external research on tenant-tagged logging.

How Domain Skills Differ from OS Skills¶

Both OS-level and domain-level skills use the same technical format: a SKILL.md file with YAML frontmatter (description, allowed-tools) and markdown body (trigger, instructions, output spec). Native discovery surfaces both. The differences are in scope and governance:

Aspect OS Skill Domain Skill
Location .claude/skills/ engines/<engine>/.claude/skills/
Visibility All sessions Only when working in that engine’s context
Generalization Useful across multiple engines Useful only within its domain
Governance Can be governance/orchestration skills Typically execution skills; orchestration skills (like ODC’s pipeline-start) are domain-scoped
Chain participation Phase-controller forces OS skill chains Domain skills are invoked within OS-governed chains but are not themselves governance

The practical effect: when phase-controller builds a skill chain for a JSE operation, it chains OS governance skills (session-orchestrator, depth-governor, qa-pipeline) with JSE domain skills (target-builder, resume-generator, materials-qa). The governance skeleton is OS; the domain execution is engine-local.

See Skill System for complete coverage of skill architecture, chain maps, and frontmatter specification.
