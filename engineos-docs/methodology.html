Methodology

EngineOS encodes quality methodology as infrastructure, not documentation. 15 methodology docs live at methodology/ and are protected by an immutability rule -- modification requires operator approval. These are not style guides. They are formalized approaches proven across 105+ days of production work across 11 projec

For the full index of all 15 documents with companion skills and loading triggers, see methodology-index.md. For how methodology connects to the governance enforcement layer, see governance.md.

Research Methodology¶

Three documents form the research core: source credibility tiers, dual-source intelligence, and depth assessment. Together they answer: how much do you trust a source, how do you get two independent perspectives, and how deep do you go?

Source Credibility Tiers¶

Every finding in EngineOS is tagged with a credibility tier. The system uses five tiers, each carrying a different evidence weight:

Tier Source Type Weight
1 Official documentation, verified changelogs Highest – authoritative baseline, verifiable against source code
2 Established creators with proven deployments High – track record matters, consistently accurate when cross-checked
3 GitHub issues/PRs with reproducible details Medium-high – specific, tied to code, elevates above general community
4 Reddit/forum posts with technical specificity Medium – useful for surfacing issues, requires verification
5 General community sentiment Low – direction indicator, not decision-maker

Tiers are assigned through a four-question flow, applied in order:

  1. Is it official? Published by the tool’s maintainers, on their domain, in their docs or changelog? Yes = Tier 1.
  2. Does the author have a proven track record? Publicly deployed, recognized expert, consistently accurate? Yes = Tier 2.
  3. Is it reproducible and tied to code? GitHub issue with steps, version numbers, error output? Yes = Tier 3.
  4. Does it contain technical specificity? Config snippets, exact error messages, version numbers? Yes = Tier 4. No = Tier 5.

Every sourced claim carries a tag: (Tier X, [source description], [date]). Examples:

(Tier 1, official docs v2.3 changelog, 2026-02-15)
(Tier 3, GitHub issue #1234, 2026-02-10)
(Tier 5, general Reddit sentiment across 5+ threads, 2026-02)

Tiers are not permanent. A Tier 5 source gets upgraded when backed by a technically specific post. A Tier 1 source gets effectively downgraded when the documentation is demonstrably outdated. Multiple independent sources at the same tier converge for a corroboration upgrade. Conflict of interest triggers a downgrade. The tier assignment, upgrades, and downgrades are all documented – tier shifts without rationale are arbitrary.

The tier system matters most when sources contradict each other. If Tier 1 official docs and Tier 4 forum posts disagree, the starting assumption favors Tier 1 – unless the Tier 4 source provides reproducible evidence. The contradiction itself is an intelligence insight, documented with both perspectives and an assessment of which is more current.

Dual-Source Intelligence¶

Documentation tells you how something is supposed to work. Community intelligence tells you how it actually works. The gap between those two is where the most valuable findings live.

EngineOS uses two MCP-integrated sources:

  • Context7 (official documentation): API references, configuration schemas, changelogs, architectural documentation. The skeleton – authoritative, structured, verifiable, but can be outdated or aspirational.
  • Bright Data (community intelligence): Reddit, Hacker News, GitHub issues, developer blogs, expert analysis. The muscle and scars – real-world validation, surfaces undocumented gotchas, but signal-to-noise varies.

Neither source is sufficient alone. Documentation can be aspirational, describing planned features as current. Community intelligence can be anecdotal, colored by operator error mistaken for platform bugs. The discipline: every research question gets both sources. Contradictions between them are intelligence insights, not failures.

Three operating modes determine the lead source:

Mode 1 – Documentation Pull (Context7-led). When you need to understand how something officially works. Query Context7 for the relevant docs, note gaps and ambiguities, then use Bright Data to supplement with real-world experience.

Mode 2 – Landscape Scan (Bright Data-led). When mapping a competitive field or gauging community sentiment. Batch search across community sources, identify claims that need technical validation, then use Context7 to verify specific technical claims against official docs.

Mode 3 – Reality Check & Amplification (both, cross-validating). The most common mode for deployment-critical decisions. Query both sources in parallel on the same question, compare findings, flag contradictions. If docs say “all plugins are reviewed” but community reports finding malicious ones, that contradiction is a critical finding.

Cross-validation discipline: when official docs and community intelligence disagree, document both claims with sources and tiers, note the nature of the contradiction (outdated docs? undisclosed issue? community misunderstanding?), and determine which is more current through additional research. Record the contradiction in the intelligence log – even resolved contradictions have value.

Depth Assessment¶

LLMs default to medium depth on everything. Without explicit classification, research gets “pretty thorough” and outputs get “pretty good” – never sharp. A landscape scan that should cover 15 tools in 20 minutes spends 20 minutes on the first three. A security evaluation that needs exhaustive source chains gets two Reddit posts and a docs link.

Depth assessment is a mandatory 30-second classification step at the start of any pipeline stage. Two depths:

Scan (breadth-first). Covers many topics at surface level. 1-2 sources per claim is sufficient. Binary self-tests use quick versions. The goal is coverage.

Deep-dive (depth-first). Focuses on fewer topics with exhaustive coverage. Dual-source validation required per claim. Full evidence chains. Binary self-tests use thorough versions. The goal is confidence.

Three classification questions, applied in order (first YES determines the depth):

  1. “Will this finding drive a GO/NO-GO decision?” Yes = deep-dive.
  2. “Is the operator new to this topic?” Yes = deep-dive for their unfamiliar areas, scan for context they already know.
  3. “Has this topic had security implications in past research?” Yes = deep-dive on security aspects, scan the rest.

All three NO = scan is appropriate.

Mixed-depth within a single task is normal. Evaluating a new tool might mean deep-dive on security posture (GO/NO-GO + security implications), scan on feature comparison (landscape context), scan on installation (familiar territory). Classify per topic, not per task.

Reclassification during work is expected, not a failure. A scan surfaces a security concern = reclassify to deep-dive. A deep-dive determines the topic is simpler than expected = reclassify to scan. Log the reclassification with the reason. Frequent reclassification in the same direction signals the initial classification was miscalibrated.

Findings Structuring¶

When the engine synthesizes research findings, it selects from seven validated finding types rather than inventing format each time. Each type has a specific shape that makes findings scannable, comparable, and maintainable across the knowledge base.

Finding Type When to Use
Contradiction Insight Sources disagree on a factual claim relevant to a decision
Validation Entry A hypothesis has been tested against evidence and confirmed
Discovery Entry Research surfaced something not part of the original hypothesis
Risk Entry A finding describes a threat that needs likelihood/impact assessment
Comparison Matrix Research evaluates multiple options against each other
Resolution Entry A research question has been conclusively answered
Recommendation Entry Evidence supports a specific course of action

Each type has required and optional fields. Required fields are always populated; optional fields are filled at deep-dive depth and skipped at scan depth. Every field includes a source and credibility tier.

Two examples from production work:

Contradiction Insight:

CONTRADICTION: Plugin ecosystem safety claims vs. reality

- Claim A: Official docs describe plugin ecosystem as "reviewed"
  (Tier 1, official documentation, 2026-02)
- Claim B: Independent security audit finds ~20% of marketplace
  plugins are malicious (Tier 2, security research firm, 2026-03)
- Nature: Vendor understatement of supply chain risk
- Current assessment: Security audit methodology (systematic
  scanning, reproducible results) overrides vendor marketing language
- Intelligence value: Community security audits provide ground truth
  that vendor documentation does not -- transfers to any
  marketplace/plugin ecosystem evaluation

Risk Entry:

RISK: Plugin marketplace supply chain -- actively compromised

- Threat: Installing any marketplace plugin risks credential theft,
  reverse shells, or targeted malware
- Likelihood: High -- significant confirmed malicious plugins,
  coordinated campaign identified
- Impact: Full credential exfiltration, browser credentials, SSH keys
- Current mitigations: Zero marketplace installation policy,
  custom-only plugins, tight tool policy as execution boundary
- Residual risk: An operator who forgets the policy and installs a
  single marketplace plugin bypasses all mitigations. No automated
  enforcement -- this is a discipline control, not a technical control.
- Source chain: Independent security audit (Tier 2),
  security news outlets (Tier 2-3)

Quality Framework¶

Four methodology documents form the quality layer: binary self-tests, anti-patterns, adversarial validation, and editorial standards. Together they answer: how do you test your own output, what failure modes do you watch for, how do you get independent evaluation, and what standards govern everything you write?

Binary Self-Tests¶

LLMs cannot reliably evaluate “is this good?” They CAN evaluate concrete YES/NO questions. “Write clearly” is an aspiration. “Read the third paragraph without reading the first two – does it make sense?” is a verification step. The difference is the difference between hoping and checking.

Binary self-tests are YES/NO quality gates answerable in under 5 seconds. Four design rules govern every test:

  1. Answerable YES or NO in under 5 seconds. If it takes deliberation, the test is too vague.
  2. Concrete – references specific parts of the output. “Is this section good?” is not a test. “Pick any claim in section 3 – can you name its source?” is a test.
  3. Actionable – a NO answer implies a specific fix. If the test fails and you do not know what to change, the test is not useful.
  4. Paired – quick version for scans, thorough version for deep-dives. Quick tests check for presence. Thorough tests check for quality.

Tests are organized by pipeline stage. Examples from each stage:

Research (RS): “Pick any claim. Can you name the source and its credibility tier in under 5 seconds?” (Quick.) / “For every finding that will drive a decision, is there both an official and a community source?” (Thorough.)

Synthesis (SY): “Does the synthesis include a residual risk statement?” (Quick.) / “Read the residual risk section. Does it name specific risks with specific consequences, or does it say ‘some risk remains’?” (Thorough.)

Content/Deliverable (CD): “Pick any command in the output. Is the expected output documented?” (Quick.) / “Does every recommendation have evidence behind it?” (Thorough.)

Visual/HTML (HD): “Has the output been opened in a browser since the last edit?” (Quick.) / “Do all expandable sections toggle correctly? Does content stay inside containers?” (Thorough.)

Cross-Cutting (XC): “Does this output add value – does it inform a decision or teach a principle?” (Quick.) / “Would you be comfortable if the reader checked your sources?” (Thorough.)

New tests are added when a quality failure is discovered. The question is always: “What binary test would have caught this?” If you cannot write a concrete test for a failure mode, the failure is too vague to prevent mechanically – investigate the root cause.

Anti-Patterns (14 Evidence-Based)¶

EngineOS catalogs 14 real failure modes observed during production work. Every entry cites a specific incident – no theoretical anti-patterns. If it has not been seen to fail, it is not listed. The gallery is organized into three categories:

Research anti-patterns (4): The Understated Warning, Premature Confidence, The Settled Question That Was Not Settled, The One-Source Frame.

Output anti-patterns (3): The Missing Source Trail, The Empty Scaffold, The Process Deviation Nobody Noticed.

Process anti-patterns (7): Staleness Blindness, The Scope Ratchet, The Deferred Template Pile, The Unverified Render, The Contradictory Frame, Path-Pattern Lift Misses, Body-Size as Regression Signal.

Each entry includes “What it looks like” (recognition), “Why it happens” (understanding the temptation), “What good looks like” (the alternative), and a binary self-test for detection. Four examples that illustrate the pattern:

Premature Confidence. Presenting a small number of community sources as consensus. Three Reddit posts from the same week are not “community consensus” – they might all trace back to one person’s experience being reshared. The credibility-tiers system exists specifically because this failure mode was recurring during production research. Binary test: Find a claim described as “consensus” or “widely reported.” Can you count 5+ independent sources behind it? If not, downgrade the language.

Missing Source Trail. Research finds many sources, but the consolidated source list is an afterthought created during review rather than maintained as research happens. In one production output, the source index had 1 entry versus 130+ sources cited across the knowledge base. Binary test: Open the source index. Does the entry count roughly match the number of unique sources cited in the knowledge base? If substantially smaller, the source trail is retroactive, not contemporaneous.

Scope Ratchet. A project’s framing evolves significantly during execution – from specific tool deployment to learning lab to reusable engine – but each expansion feels natural in context. One project went from “install tool X on my hardware” to “reusable engine” in 21 days through three incremental reframings. Each was well-reasoned. The anti-pattern is not the evolution – it is failing to recognize it and audit existing work against the new framing. Binary test: Read the current purpose statement and the oldest purpose statement. Are they describing the same project? If not, has existing work been reviewed against the current purpose?

Contradictory Frame. The same output contains two conflicting framings of the same fact. A production output framed hardware as “dedicated” in one section and “shared” in the security section, building its biggest risk assessment around the wrong assumption. The end user caught it. Binary test: Pick any assumption the output makes about the user’s setup. Search the full output for that assumption. Does every mention agree?

Adversarial Validation¶

Self-evaluation catches correctness errors but misses structural blind spots. EngineOS uses two-agent adversarial testing: an executor produces, an evaluator scores independently.

Three roles:

  • Executor: The Claude Code agent. Builds, executes, produces output. Has full codebase access and operates under the system’s governance.
  • Evaluator: A separate session with independent context. Reviews executor output, validates against specs, drafts checkpoint responses. Does NOT execute the work.
  • Operator: Routes between executor and evaluator. The decision-maker – neither agent has authority to override the operator.

The independent context requirement. The evaluator MUST NOT share the executor’s session. Shared context means the evaluator inherits the executor’s framing and cannot challenge it independently. The evaluator sees the deliverable and the criteria – nothing about the executor’s reasoning process.

Why this matters. Three failure modes make self-evaluation structurally unreliable:

  1. Sycophancy. The executor shares context with the request that produced the work, making its own decisions feel correct in retrospect.
  2. Keyword-passing. When asked “did you do X?”, the agent searches for X, finds the keyword, and confirms – without checking depth. In one real test, the agent confirmed MLR’s QA methodology was composited because it found related keywords, but the 922-line source’s 8-phase verification workflow was entirely absent.
  3. Count errors in self-audit. An agent miscounting its own output (reporting 4 intelligence log entries when 5 existed) is routine, not exceptional.

Mechanical distrust. The evaluator recalculates pass/fail from raw scores rather than trusting summary statements. Test results track systemically across tests – individual pass/fail is insufficient; the real signal is patterns across tests. A capability that passes once might be lucky; a capability that passes across three tests with different conditions is reliable.

Dual-layer test design. Every test evaluates two layers independently:

  • Capability layer: Does the system produce good output? Does the skill chain fire? Does data flow correctly?
  • Governance layer: Did the system follow its own process? Was the phase-controller invoked? Does the run plan govern execution? Is the activity log populated?

A system can produce excellent output while violating every governance rule. In one test, a resume scored 9.8/10 on quality – but phase-controller was never invoked, no run plan existed, and no forced skill chain fired. The capability layer passed. The governance layer failed. Good output without governance is fragile; it works when the agent is confident and fails when the task is novel.

Production Methodology¶

Three documents address how work gets produced at scale: section-by-section construction, the factory pattern, and editorial standards.

Section-by-Section Construction¶

Quality degrades predictably in single-pass generation beyond approximately 500 lines. The first third is strong, the middle is adequate, and the final third loses detail, drops conventions, and introduces inconsistencies. This is not theoretical – large interactive walkthroughs exceed 3,000 lines of HTML, well beyond the point where coherence degrades.

The process uses four phases:

Phase A – Plan sections with namespaces. List all sections, define boundaries, identify cross-references, assign unique namespace prefixes for IDs and anchors. Present the plan to the operator for approval. Do not generate content until the plan is approved.

Phase B – Build one section at a time. Generate each section independently. Update cross-references to and from previously generated sections. Run binary self-tests per section: Can you name the source for any claim? Does a forward reference to an unbuilt section get noted? Does the section make sense without reading the previous one?

Phase C – Whole-output review. Read the complete output as a reader would experience it. Check that all cross-references resolve, transitions are smooth, section proportions match importance. Run the anti-pattern check on the whole output.

Phase C.5 – Render-validate for visual outputs. Mandatory for anything with visual elements. You cannot judge visual output from source code alone. A hidden display:none diagram, broken expandable sections, failed contrast – all invisible in source, obvious in a browser. The loop: render, screenshot, audit against styling standards, fix, re-render. Typical iteration count: 2-4 passes.

Phase D – Iterate. Fix anything found in Phase C. Targeted re-review of specific issues, not a full repeat unless fixes were extensive. The goal is convergence.

The namespace convention prevents ID collisions across sections: {section-prefix}-{element-type}-{descriptive-name}. Section prefixes are assigned in Phase A (phase-a, sec-1, kb-security). All IDs within a section use the namespace as a prefix, ensuring uniqueness across the entire output.

Factory Pattern – 4 Variants¶

Engines are extracted from the OS and from each other through four distinct factory patterns, each solving a different version of “how does one system produce and maintain another”:

Variant 1 – Full Extraction. A complete capability lift from one system to another. The factory audits capabilities, selects and adapts a subset via an extraction manifest, stages them, deploys to a standalone product, and severs runtime dependency. The product owns everything after deployment. The JSE was extracted from the SEE in 2 days: 63 skills audited, 43 skipped, 20 kept, with a 41,594-byte extraction manifest specifying 7 sections per skill. JSE composited from four lineages – SEE operational skills, ODC governance methodology, WondaKB naming conventions, and original JSE innovation.

Variant 2 – Team Deployment. Deploying a configured workspace for a team with different identity and access requirements. One-time extraction with restructuring for multi-user access. WondaKB was extracted from the SEE: 20 skills migrated with name/path translations, KB content restructured from 7 technical buckets to 6 conversational files, 3 new skills created for multi-user collaboration (session-start with git pull, session-end with git push, document-integrator).

Variant 3 – Thin Routing. Lightweight orchestration that routes to capabilities across the ecosystem without containing or copying logic. The engine is pure coordination – improvements to source capabilities automatically propagate. The Research Engine routes to JSE’s market-scanner, MLR’s competitive-research, ODC’s dual-source methodology, and MLR’s enterprise templates. Core vulnerability: hardcoded file paths break silently when sources move. The capability registry solves this by providing stable identifiers that abstract away physical locations.

Variant 4 – Instance Spawning. Creating instances of a work template within a bounded context. cp -r to create instances from a proven structure. Shared methodology (playbook) with instance-specific content. Cross-instance learning accumulates in shared patterns. The most operationally accessible factory pattern. The Renewal Engine uses this: per-client instances from a methodology playbook where each instance is populated with client-specific content.

Every variant includes a maintenance protocol (triggers, steps, staleness indicators) and a documented anti-pattern. Innovation flows outward from factories and never returns – the maintenance protocols close that loop through reverse audits, innovation detection, and back-port decision logs.

Editorial Standards¶

Six core principles govern all written output:

  1. Evidence Requirement. If you cannot cite it, do not claim it. Every claim needs a source and credibility tier. “I believe” and “it seems like” are red flags. Replace with “Source X reports…” or “No evidence found for…”

  2. Honest Assessment. Never oversell. Never downplay. Note residual risk. “Impressive adoption rate AND significant unresolved security concerns” is honest. Picking one framing is not. Residual risk is always noted – every deployment has risk after hardening. Pretending otherwise is malpractice.

  3. Transferable Framing. Distinguish universal principles from tool-specific details. “This is how authentication tokens work for any agent gateway” is more valuable than “Here’s the Tool X auth config.” When a concept transfers, say so explicitly. When something is tool-specific, mark it.

  4. Community Validation. Documentation alone is insufficient. Every research question gets both official documentation and community intelligence. When docs and community agree, confidence is high. When they disagree, the contradiction is an intelligence insight.

  5. Security as a Lens. Security is evaluated on every decision, not treated as a separate phase. Security implications are noted inline, where the decision is made, not deferred to an appendix that may never be read.

  6. Living Documentation. Mark outdated content as outdated. Never delete. All entries are date-stamped. The history has value – knowing what used to be true and changed is intelligence.

System Building Methodology¶

Three documents encode how EngineOS was built and how composited systems are audited: the ecosystem build methodology, the lift audit, and planning enforcement.

Ecosystem Build – Three-Act Architecture¶

The methodology used to build EngineOS itself, formalized from the three-act audit that composited 11 projects into a unified system.

Act 1 – Structural Reconnaissance. Posture: cartographer. Map what exists without judging it. Produces an ecosystem map, a growth story, a Deep Attention Register (hypotheses for Act 2), and an Act 2 workspace. Act 1’s job is to make Act 2’s discovery wildly informed. It does not solve, recommend, or prescribe. The EngineOS audit’s Act 1 produced 19 files with 90+ register entries as starting hypotheses.

Act 2 – Exhaustive Discovery. Posture: auditor. Read every line. Produce findings, not recommendations. The core methodology is capability-domain reading: read the same capability type across ALL projects simultaneously rather than reading each project start-to-finish. This means one reader examines integration architecture across every project – cross-project comparison happens naturally within domain reads.

The 70% reading rule: at least 70% of effort goes to actual line-by-line reading. Synthesis comes after the read. This prevents the discovery-filtered-by-conclusion trap where the agent decides the answer and then reads selectively to confirm it.

Genealogy synthesis is a first-class output. Sub-agents reading individual domains cannot trace cross-domain iteration chains. A dedicated post-domain genealogy pass revealed that JSE composited from four distinct lineages – no single domain reader could have seen this. The EngineOS audit’s Act 2 produced 103 files, 1.6MB total.

Act 3 – Build from Evidence. Posture: builder. The core methodology is best-version-wins compositing. Not selection (picking a winner) but compositing (taking the best parts from every lineage). The transcript-processor combines SEE v1.1 plus restaurant’s three principles. The qa-pipeline combines MLR’s programmatic checks plus ODC’s binary self-tests plus JSE’s governance integration. Taking the best from every iteration produces something better than any source.

Five-phase build with checkpoint reviews: Foundation, Composites, Best-version deployments, Infrastructure (templates, patterns, principles), Constitution and validation. At every phase boundary, an independent evaluator reads deployed files on disk – not the executor’s report – and issues corrections before the next phase begins. Reports approximate; disk is exact.

Lift Audit – Regression Detection¶

When a system composites capabilities from multiple sources, two failure modes emerge after the build: internal regression (code that fails to port from source to target) and external currency drift (the lifted baseline ages against evolving practice).

Both accumulate invisibly. They surface only when someone tries to exercise the capability. The EngineOS audit surfaced these empirically: 891 lines of JavaScript at source with zero lines in EngineOS (never-lifted regression), Python scripts reduced 55% with roughly half the functions missing (capability loss), and a skill existing as documentation pointing at files that never ported (orphaned-skill regression).

Three audit dimensions:

Dimension 1 – Internal regression check. Compare source to target. The primary signal is method-level parity: function presence and public API coverage. Body-size delta (line counts) is secondary evidence only – never used alone.

Dimension 2 – External currency validation. Check whether the lifted baseline is still current practice. Use Context7 for API/library docs and Bright Data for current industry patterns. Impact-scaled: HIGH capabilities get 5+ Tier 1-2 sources; LOW capabilities get a single sanity check.

Dimension 3 – Refactor-vs-regression distinction. When target code differs from source, determine whether it is legitimate refactoring or capability loss. A file that got smaller may have been refactored (dead-code removal, DRY consolidation), not regressed. Method-level parity is the test: if function list and public API coverage both hold, size delta is refactoring.

The canonical example: notion-ops had a “55% body reduction” from source. The initial audit read this as concerning. Method-level comparison revealed roughly half the functions were missing – method-level parity failed. THAT made it regression, not the body-size. Had the body-size been the sole signal, legitimate refactors would have been misclassified. This incident produced anti-pattern #14 (Body-Size as Regression Signal).

Enumeration discipline is the most important audit practice: catalog ALL executable locations per source project. Do NOT pattern-match on expected paths. In one audit, the agent tested 4 case-permutation variants of a path, declared “doesn’t exist on this machine,” and propagated that wrong-negative into “capability never existed in sources.” The operator found the file in one case-insensitive ls. Parent-directory browsing is cheaper and more reliable than variant-hunting.

Planning Enforcement¶

Confident agents skip planning. This was documented across three consecutive sessions where brainstorming and writing-plans skills were specified in the skill chain and never invoked. Session compliance: 0%, ~30%, ~70%, then PASS in the fourth session after the pattern was identified.

The root cause: governance that depends on the agent choosing to invoke it fails when the agent has a clear path and does not perceive a need for structured thinking. The agent conflates “I know what to build” with “I’ve thought through how to build it.” Detailed operator prompts amplify this – they create an illusion that scoping was done by the operator.

Two enforcement types address this:

Structural enforcement makes the planner’s output a required input to the production step. The production step reads Layer 4 (Design + Plan) of the run plan as its first action. If Layer 4 is empty, there is nothing to read and production cannot proceed. This works for writing-plans because its output is concrete – a plan that populates Layer 4.

Advisory enforcement with transparency requires the agent to justify skipping in the run plan, visible to the operator at the approval gate. If the agent judges a mandatory step unnecessary, it writes a skip-justification. Silent skipping – proceeding without invoking or justifying – is a governance violation.

The asymmetry is intentional. Structural enforcement works where artifacts are concrete. Advisory enforcement works where artifacts are fuzzy (like brainstorming output). Trying to force structural enforcement on brainstorming creates perverse incentives – the agent produces a fake artifact to satisfy a gate, which is worse than honest skipping.

Governance Methodology¶

Two documents encode how the system remembers and how it stays current: memory architecture and research cadence. Memory architecture itself splits into two halves – write-side capture (where information goes when produced) and read-side retrieval (how prior context gets back into active work). Both halves are formalized in methodology/memory-architecture.md; the canonical decision record for the retrieval layer is DECISIONS.md D32. For the deep operational reference, see second-brain.md.

Memory Architecture (Write-Side – Capture)¶

EngineOS uses 8 memory surfaces, each with ONE job. This section governs capture – what writes go where. The companion read-side architecture is the next subsection. Surfaces doing a second job are in violation and should be corrected:

Surface One Job Persistence
CLAUDE.md Constitution + routing Permanent, evolves slowly
CONTEXT.md Current state, present-tense Updated every session
CONTEXT-HISTORY.md Archived prior states Append-only archive
Run plans Active execution contracts PLANNING to IN PROGRESS to COMPLETE
Activity log Operational breadcrumbs (what happened) Append-only, hook-populated
Intelligence log Strategic memory (why it matters) Append-only, human-curated
operator/* Durable identity Stable, evolves with operator
User-level auto-memory Cross-session memory Claude Code managed

All log entries go to root logs/. Engine-local logs are legacy. Every log entry is tagged with an engine column (job-search, sales-enablement, on-demand-curriculum, or OS for OS-level work). Filtering by engine tag produces the tenant-specific view – cheaper than maintaining separate files per engine.

This design is backed by external research: centralized logging with tenant tags is the industry standard across Grafana Loki, Datadog, Azure, AWS, and OpenTelemetry. Per-tenant stores are recommended only under strict regulatory isolation or at scales like 100M events/second. Single-responsibility memory surfaces converge with patterns across CrewAI (5 memory types), LangChain Agent Server (3 persistence layers), and OpenAI Agents SDK (global/session/profile separation).

CONTEXT.md entries older than 30 days or exceeding 20 entries archive to CONTEXT-HISTORY.md. The archive trigger is on-demand at session boundaries, not periodic. The test: “Is CONTEXT.md readable in under 30 seconds?” If the What’s Changed table makes you scroll past the fold, it is archive time.

Retrieval Architecture (Read-Side – Pulling Prior Context Back In)¶

Capture without retrieval is a write-only system. The retrieval layer was added 2026-06-04 after a marathon-arc audit showed zero reads of knowledge/concepts/*.md across ~30 hours of substantive work despite 216+ articles in the corpus. The canonical decision is DECISIONS.md D32; the canonical methodology section is in methodology/memory-architecture.md. The deep operational reference is second-brain.md.

Retrieval operates as three layers over the same six-surface priority corpus:

Layer Mechanism Fires when Coverage target
1. Session-start injection hooks/session-start.py Every session start Orientation – KB index + last 30 lines of today’s daily log injected at session boundary
2. Mid-work retrieval hook hooks/prompt-retrieval.py (UserPromptSubmit) Prompts matching the heuristic gate ~90% – silent, mechanical, ≤1024 chars, ≤1s, top-3 matches from 6-surface corpus
3. Manual escalation .claude/skills/recall/ (/recall <query>) Operator or agent invocation when hook missed or sweep needs depth ~10% – explicit, ranked, no cap

Layer 1 establishes orientation. Layer 2 fills in mid-work context mechanically. Layer 3 escalates when the hook misses or the decision is load-bearing.

The same six surfaces are queried in the same priority order across all three layers, ordered by signal-to-noise:

# Surface Best for
1 logs/intelligence-log.md “What did we learn / decide / observe?”
2 knowledge/index.md “Do we have an article on X?”
3 knowledge/concepts/*.md + connections/*.md “Read the article on X”
4 daily/*.md (last 30d) “What were we doing recently on Y?”
5 run-plans/*.md (last 60d) “Recent plan-and-execution for Z”
6 methodology/*.md “Official approach to W”

Stopping rule: when surfaces 1-2 yield 3+ strong hits, do not sweep the lower surfaces. The discipline that pairs with the manual escalation layer is the retrieval-before-decide framework pattern – query the second brain before deciding in a domain where prior intelligence likely exists. Health is measured via scripts/retrieval-health.jsonl (one record per UserPromptSubmit invocation); the operator runs scripts/retrieval-review.py after ~10 sessions to make the keep / tune / kill decision per D32. Healthy gate hit rate band: 10-60%.

Why not a vector DB at current scale: external research synthesis confirms structured markdown index + ripgrep + LLM-reads-relevant-files outperforms vector retrieval on precision at personal-KB scale (<500 articles; the corpus is at 216 and growing). Vector / GraphRAG / Mem0-style production frameworks are appropriate beyond ~2000 articles. Phase C is deferred with explicit revisit conditions in D32.

Research Cadence¶

Intelligence decays. A finding from 30 days ago may be stale. A finding from 90 days ago may be dangerous to act on. Scheduled research sweeps prevent staleness from accumulating silently.

Three staleness thresholds determine when a finding can no longer be trusted at face value:

Time-based. Days since last verification. Security findings: 0 days (always verify). Technology ecosystems: 3-7 days. Market positioning: 14-30 days. Methodology references: 60-90 days.

Event-based. Specific triggers that invalidate findings regardless of age. A finding verified yesterday becomes stale the moment a new version ships, a competitor launches, or a key source publishes contradicting information.

Confidence-based. Source reliability decay. Tier 1 sources (official docs) hold the longest. Tier 5 sources (general sentiment) decay fastest. Lower-tier findings decay faster because their initial confidence was lower.

Three sweep layers provide the cadence structure:

Watch (frequent, short – 15-30 minutes). Catch critical changes. Narrow scope – new releases, security advisories, breaking changes. Frequency matched to domain volatility.

Pulse (moderate frequency – 30-60 minutes). Track broader landscape shifts, community sentiment changes, emerging patterns. Half the watch frequency.

Deep Refresh (infrequent, thorough – 1-2 hours). Full re-evaluation. Question assumptions. Check if the right questions are still being asked. Monthly to quarterly depending on volatility. Quality bar: would this knowledge change a decision? If no, it is maintenance. If yes, it is intelligence.

The OS provides this framework. Each engine configures its own cadence parameters based on domain volatility. An engine doing competitive analysis in a fast-moving market refreshes weekly. An engine doing curriculum development on established platforms runs monthly watch sweeps with quarterly deep refreshes.
