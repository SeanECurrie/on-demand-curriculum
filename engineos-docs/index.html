01 What EngineOS Is

EngineOS is a two-layer operating system for professional work, built on Claude Code. Layer 1 is the OS: shared skills, methodology, patterns, enforcement rules, operator identity, and a design system. Layer 2 is the engines: domain-specific tenants that inherit OS capabilities and keep their own engagement data, knowledge bases, and domain-adapted workflows.

The Two-Layer Mental Model

Think of it like an operating system running applications. The OS provides infrastructure — governance, quality standards, research methodology, and 28 specialized skills. Each engine is a domain-specific workspace that inherits the full OS toolkit and adds what its domain requires. Engines are peers to each other, not to the OS. They do not duplicate shared capabilities.

What Makes It an OS, Not a Prompt Collection

Mechanical Enforcement
A PreToolUse hook intercepts every Write and Edit call. No run plan at the right scope-matched path? The write is blocked. The agent cannot bypass this — it is a JSON deny response at the platform level.
Skill Composition
28 skills do not fire independently. They chain into typed workflows enforced by the phase-controller. A content production job fires depth-governor, writing-plans, production, output-self-test, adversarial-evaluator, and qa-pipeline — in that order.
Methodology Layer
15 formalized methodology documents are protected by an immutability rule. Credibility tiers, depth assessment, editorial standards, section construction — distilled from 105+ days of production work. Skills reference them; they cannot casually modify them.
Adversarial Quality
An independent subagent with no access to the executor's context scores deliverables against hardened criteria. It caught fabricated citations in 2 consecutive iterations that self-evaluation missed entirely. Tool-asymmetric: it can read, but it cannot fix.

Five Operating Principles

These are not aspirational. They describe how EngineOS was built and how it operates.

  • 1 Research-First. No deliverable begins without research. Hypotheses are tested, not assumed. If training data says X but current research says Y, trust the research.
  • 2 Discover-Assess-Decide-Execute-Verify. The universal workflow. Skipping stages (especially discover and verify) is the most common failure mode.
  • 3 Context-as-Session-State. CONTEXT.md is the handoff mechanism between sessions. It is always current. Every session reads it on start and updates it at end.
  • 4 Never-Delete, Mark Outdated. Content is never deleted. Outdated content is marked with date and reason. The history has value. Logs are append-only.
  • 5 Constitution-from-Reality. Build first, describe last. When the system and the documentation disagree, the system is right and the documentation needs updating.

02 The Architecture

Context engineering is the core architectural problem. Claude Code has a finite context window. EngineOS has 28 skills (some over 700 lines), 15 methodology docs, 64 patterns, and 38 templates. Loading everything at once would consume the entire window before any work begins. The four-tier model solved this — a 68% context reduction vs. the original load-everything approach.

Four-Tier Context Engineering

T1
Always Present
CLAUDE.md + 3 unconditional rules. Loaded every session. ~340 lines. Survives compaction because it is always re-read.
~340 lines
T2
Path-Triggered
4 rules load automatically when reading files in matching paths. Working in engines/*/engagements/**? The engagement-structure rule loads. Never touch integration files? Zero cost.
~80 lines
T3
Skill-Invoked
28 skill descriptions load passively at ~2% of context. Full content (up to 739 lines for phase-controller) loads only when invoked. A session using 3 skills loads 3, not 28.
~3 per session
T4
Explicit Reference
Methodology docs, patterns, templates, operator identity, design system. Loaded only when a skill chain mandates it or the operator requests it. Never preemptively.
On demand
The savings compound. A typical session loads ~1,300–2,500 lines of EngineOS context, leaving the majority of the window for actual work. Compare to the SEE's original approach: load all 49 skills, all patterns, all templates at session start. That approach consumed the context window before work began. Decision D11 made the system viable.

Compaction Resilience

Claude Code compacts older context when the window fills. EngineOS is designed for this. The design principle: anything that must survive compaction lives on disk at a predictable path. The context window is a working space, not a storage system.

PostCompact Hook
Fires after every compaction. Re-injects all 6 core governance behaviors as plain text. Lists active run plans (files newer than CONTEXT.md). Enumerates engine tenants so the agent knows what exists.
Disk-Persisted Run Plans
The primary recovery mechanism. The run plan shows what has been done (populated layers) and what is next. Execution resumes from the last completed step. No re-planning needed.
CONTEXT.md
Always current — the Stop hook warns if it was not updated. It is the handoff mechanism between compaction boundaries, just as it is between sessions.
Tier 1 Re-Read
CLAUDE.md and the 3 unconditional rules are re-read on every interaction after compaction. The system's core identity is never permanently lost.

Registry System

Capability Registry
registry/capabilities.md

Engine Registry

03 The Governance Stack

EngineOS governs a confident AI agent — one that will skip steps it considers unnecessary, generate plausible completion summaries for work that did not happen, and report filesystem facts from memory instead of checking disk. The governance stack exists because methodology alone does not survive contact with that agent.

Two Enforcement Layers

Mechanical (Hooks)

  • Cannot be bypassed by the agent. Shell scripts that fire at Claude Code lifecycle points.
  • PreToolUse: Blocks deliverable writes unless a scope-matched run plan exists on disk
  • PostToolUse: Appends timestamped entry to activity log after every write
  • Stop: Warns if CONTEXT.md was not updated during the session
  • PostCompact: Re-injects core behaviors and active run plan awareness after compaction

Advisory (Rules + CLAUDE.md)

  • Depends on the agent following instructions. Covers everything hooks cannot reach.
  • CLAUDE.md: 6 core behaviors that survive compaction
  • 7 rules: 3 unconditional + 4 path-scoped, loaded by frontmatter
  • Skill chains: Phase-controller forces skill invocation at every transition
  • Honest about the gap: Advisory fails ~10% when the agent is confident on straightforward tasks

The Iteration Envelope

Production steps are wrapped in a produce-evaluate-retry loop. The adversarial evaluator (independent context, tool-asymmetric) scores the output. If it fails, feedback is injected and the deliverable is reproduced. Maximum 3 retries before operator escalation.

OUTSIDE ENVELOPE (runs once): depth-governor, brainstorming, writing-plans, operator approval INSIDE ENVELOPE (iterates on failure, max 3 retries): Produce deliverable ➔ adversarial-evaluator (independent context, scored JSON) ➔ IF PASS: exit envelope, proceed ➔ IF FAIL: inject feedback ➔ re-produce ➔ re-evaluate ➔ After 3 failures: OPERATOR GATE with full history AFTER ENVELOPE (runs once on final version): qa-pipeline (if external-facing), operator approval, audit-logging
Real example: During production of methodology/planning-enforcement.md, the adversarial evaluator caught fabricated citations in iterations 1 and 2. The agent had generated plausible quotes attributed to specific source locations that did not exist. Self-tests (output-self-test) passed both times — confirming that self-evaluation has structural blind spots only independent evaluation catches. Iteration 3 passed after citations were restructured as summaries with explicit source-type markers.

Pre-Write Governance Hook

The PreToolUse hook extracts the target engine from the file path and requires a run plan at the matching scope:

# --- SCOPE DETECTION --- ENGINE="" if [[ "$FILE_PATH" == *"/engines/"* ]]; then after_engines="${FILE_PATH#*/engines/}" ENGINE="${after_engines%%/*}" fi # --- SCOPE-MATCHED RUN PLAN CHECK --- if [ -n "$ENGINE" ]; then # Engine-scoped: accept plan at engines/$ENGINE/run-plans/ OR root ACTIVE_PLAN=$(find "$ROOT/engines/$ENGINE/run-plans" "$ROOT/run-plans" \ -maxdepth 1 -name "*.md" -mtime -2 2>/dev/null | head -1) else # OS-level: require plan at root run-plans/ only ACTIVE_PLAN=$(find "$ROOT/run-plans" \ -maxdepth 1 -name "*.md" -mtime -2 2>/dev/null | head -1) fi

v1 governance hole: Any recent plan anywhere unlocked any write. An agent working on JSE could write to ODC because an unrelated JSE plan existed. v2 (above) scope-matches: engine writes require an engine-scoped or root plan. OS writes require a root plan only.

The Adversarial Evaluator

A subagent with three architectural properties that make it structurally different from self-evaluation.

Independent Context
The evaluator does NOT share the executor's session. It receives only deliverable paths, criteria JSON, pass threshold, and a one-line task description. It cannot see the executor's reasoning, run plan, or conversation history.
Tool Asymmetry
The evaluator has Read, Bash, Glob, and Grep. It does NOT have Write or Edit. It can read files and run verification commands. It cannot fix what it finds. A fixer is not adversarial.
Mechanical Distrust
The executor does NOT trust the evaluator's self-reported passed field. It recalculates: passed = ALL criteria scores >= thresholds. Parse failure = hard fail: all scores 0.

Why this matters: agent judges disagree with humans only 0.3% of the time, versus 31% for single LLM self-judges (Agent-as-a-Judge, arxiv:2508.02994). The independent context is the key structural difference.

Contract Hardening

Before presenting a run plan, success criteria are hardened with three questions per criterion. Criteria use structured JSON — not markdown — because models are less likely to tamper with structured JSON.

{ "id": "C3", "criterion": "pre-write-governance.sh scope-matches write path to run plan location", "threshold": 8, "pass_definition": "Hook logic extracts target engine from file_path when path matches engines/[name]/... pattern, requires active run plan at engines/[name]/run-plans/ OR root run-plans/.", "fail_definition": "Hook allows write to engines/X/ when only plan for engines/Y/ exists, OR hook blocks a write that should be allowed", "edge_cases": [ "Operations touching multiple engines", "OS-level work touching .claude/skills or methodology", "Writes to run-plans/ directory itself still exempt" ] }

Three hardening questions: (1) Is this measurable? "High quality" is not a criterion. A mechanical pass/fail check is. (2) What would a hostile reviewer add? (3) Is the pass_definition specific enough to score YES/NO?

Run Plans: Planning Artifacts AND Gate Keys

The key architectural insight: run plans serve two purposes simultaneously. As a planning artifact, the phase-controller creates a 6-layer markdown document that captures raw intake, classifies the work, specifies the skill chain, hardens success criteria, and persists execution state across compaction boundaries. As a mechanical gate key, the PreToolUse hook checks for the run plan's existence on disk before allowing writes. No run plan = no writes. This bridges the advisory and mechanical layers.

Layer 4 is a structural dependency. For chains with [MANDATORY - structural] planning steps, the production step reads Layer 4 as its first action. Empty Layer 4 means the plan was never written, and production cannot proceed. This is file-based communication between the planning step and the production step.

11 Forcing Function Rules

Once approved, a run plan executes under these rules. They are not suggestions.

  1. Every skill in the chain gets invoked. Not referenced, not "kept in mind" — actually loaded and executed.
  2. Sanity-check runs at every lint point. 2-minute spot-check against 11 known failure modes.
  3. Output-self-test runs before any "done" declaration. NO means fix it before proceeding.
  4. Gates are non-negotiable. Work does not proceed past a gate without the operator's explicit approval. Not silence. Not implied consent.
  5. Every skill invocation gets logged in Layer 5.
  6. The run plan is updated at every transition. Disk is the source of truth.
  7. 6.5. Infrastructure updates happen BEFORE content presentation. Prevents drift between what the operator sees and what files say.
  8. Skipping a chain step requires justification. The chain is a minimum. You can add skills. You cannot silently skip them.
  9. Subagent outputs are pre-declared in the run plan. Subagents don't inherit parent hooks.
  10. Rendered artifacts require render-validate before COMPLETE. Visual verification via Puppeteer.
  11. Mandatory planning steps require explicit engagement or skip-justification. [MANDATORY - structural] steps require output in Layer 4 before production begins.
  12. Evidence-before-reporting at phase transitions. Re-verify filesystem/state claims against disk via ls, wc -l, grep, Read.

The Honest Acknowledgment

Advisory enforcement depends on the agent following instructions. A sufficiently confident agent can ignore every rule, skip every skill invocation, and produce output that looks professional but followed none of the governance. This is not hypothetical — it happened in three consecutive sessions (WS3–WS5) where the agent skipped planning skills entirely while producing acceptable output. The mechanical layer exists because advisory alone demonstrably fails on confident agents. The advisory layer remains essential for everything the mechanical layer cannot reach. What the evidence from 100+ days of production supports: mechanical hooks catch what advisory misses, advisory governance covers what hooks cannot reach, and the operator catches what both miss.

The Operator as Final Enforcement Layer

EngineOS does not claim to be self-governing. Gates require explicit approval — not silence, not implied consent. In production, the operator has caught the evaluator validating against the wrong baseline, redirected substrate work that was drifting toward feature scope, and collapsed gate boundaries when the plan was well-designed and pre-approved. When the adversarial evaluator fails a deliverable 3 times, the operator receives the full iteration history and decides: accept as-is, provide specific guidance, or take over manually.

Key Questions

A CLAUDE.md gives you instructions. EngineOS gives you infrastructure. The difference is enforcement. A CLAUDE.md says "always run quality checks." EngineOS has a PreToolUse hook that mechanically blocks writes without a run plan, a phase-controller that forces quality skills into every production chain, an adversarial evaluator that scores output with independent context, and iteration envelopes that automatically retry on failure. When the agent judges that it doesn't need the planning step (documented across 3 consecutive sessions), the CLAUDE.md instruction gets skipped. The hook doesn't care how confident the agent is.

Yes. EngineOS is operator-agnostic by design. The operator/ directory personalizes the system through a structured Phase 0 onboarding process (37-question intake via the profile-builder skill). A new user would clone the system, run session-orchestrator (detects missing PROFILE.md, triggers Phase 0), complete the intake, and the system generates tailored identity files. Everything personalizes around the new operator. The engine tenant model means domain-specific work lives in isolated tenants — a new user creates their own engines without touching existing ones.

Because you cannot mechanize judgment. A hook can check "does a run plan exist?" (binary, deterministic). It cannot check "is this research synthesis well-reasoned?" or "does this campaign match the client's voice?" Those require semantic evaluation — the advisory layer provides this through rules, skill chains, and the adversarial evaluator. The split is deliberate: mechanical enforcement for deterministic operations, advisory enforcement for semantic operations. The operator is the final layer for everything else.

Three candidates:

  1. Advisory governance failure (J3). Phase-controller was designed to classify every operation. During J3, the agent created a resume without invoking phase-controller at all — file loading, resume writing, DOCX generation, inline QA. Resume was 9.8/10. Governance failed completely. Led to D22: mechanical PreToolUse hook.
  2. Act 3 lift regression. The capability lift systematically missed top-level scripts/ directories. SEE's 891-line Attio direct API suite, notion-mapper's 43KB of Python scripts — all missing. Discovered accidentally during a JSE pipeline operation. Required a dedicated restoration operation.
  3. The WONDA-STUFF incident. Agent declared a directory doesn't exist after 4 glob-variant attempts. Actual path: all-caps with hyphens. That wrong negative invalidated an entire audit quadrant. The operator found it with one case-insensitive ls. Led to evidence-first-reporting rule, confident-negative-finding pattern, and sanity-check #11.

Each failure produced concrete infrastructure improvements. The system learned from its mistakes in a way that prevents recurrence.

Rules encode process: "always log file operations," "verify state before reporting." They are about what to DO. Patterns encode experience: "here's a failure mode we observed, here's the incident, here's how to prevent it." They are about what to WATCH FOR. EngineOS has 7 rules and 64 patterns. Rules are few because process should be minimal. Patterns are many because the system has encountered many failure modes across 105+ days. Every pattern comes from a real incident.

output-self-test runs before declaring work complete. Binary YES/NO tests calibrated by output type. "Does every recommendation have evidence behind it?" A NO means fix it. Fast — 30-60 seconds.

sanity-check runs periodically at natural pause points. It checks for 11 known failure modes accumulated from real incidents. Takes about 2 minutes. Output-self-test asks "is this output ready?" Sanity-check asks "am I making known mistakes right now?"

The cost of losing history is asymmetric. Three failure modes that never-delete prevents:

  1. The vanished rationale. A decision was made six weeks ago. Why? If deleted, you re-research it. If marked outdated with a reason, the rationale is there.
  2. The repeated experiment. A configuration was tried and failed. Without a trace, you try it again.
  3. Undetectable drift. Small deletions accumulate. After 20 sessions, the system has quietly changed and nobody noticed. Append-only history makes drift visible.

In practice, the mechanism is lightweight: outdated content gets a date and reason stamp. CONTEXT-HISTORY.md archives older entries so CONTEXT.md stays focused.

Dual-Source Intelligence

Documentation tells you how something is supposed to work. Community intelligence tells you how it actually works. The gap between those two is where the most valuable findings live.

Context7 (Official Documentation)
API references, configuration schemas, changelogs, architectural docs. The skeleton — authoritative, structured, verifiable, but can be outdated or aspirational.
Bright Data (Community Intelligence)
Reddit, Hacker News, GitHub issues, developer blogs, expert analysis. The muscle and scars — real-world validation, undocumented gotchas, but signal-to-noise varies.

Neither source is sufficient alone. The discipline: every research question gets both sources. Contradictions between them are intelligence insights, not failures. If docs say "all plugins are reviewed" but a security audit finds 20% are malicious, that contradiction is a critical finding.

Depth Assessment: Scan vs. Deep-Dive

LLMs default to medium depth on everything. Without explicit classification, research gets "pretty thorough" and outputs get "pretty good" — never sharp. Depth assessment is a mandatory 30-second classification at the start of any pipeline stage. Three questions determine the depth: Will this finding drive a GO/NO-GO decision? Is the operator new to this topic? Has this topic had security implications? All three NO = scan is appropriate. Mixed-depth within a single task is normal and expected.

Anti-Patterns: 14 Evidence-Based

Every entry cites a specific incident. No theoretical anti-patterns. If it has not been seen to fail, it is not listed.

Premature Confidence
Presenting a small number of community sources as consensus. Three Reddit posts from the same week are not "community consensus" — they might all trace back to one person's experience.

Binary test: Find a claim described as "consensus." Can you count 5+ independent sources behind it?
Contradictory Frame
Same output contains two conflicting framings of the same fact. A production output framed hardware as "dedicated" in one section and "shared" in the security section, building its biggest risk assessment around the wrong assumption. The end user caught it.

Binary test: Pick any assumption. Search the full output. Does every mention agree?
Scope Ratchet
Project framing evolves significantly during execution, but each expansion feels natural. One project went from "install tool X" to "reusable engine" in 21 days through three incremental reframings.

Binary test: Read current vs. oldest purpose statement. Same project? If not, has existing work been reviewed against the new purpose?
Missing Source Trail
Research finds many sources, but the consolidated source list is an afterthought. In one production output, the source index had 1 entry versus 130+ sources cited across the knowledge base.

Binary test: Does the source index entry count roughly match unique sources cited?

Research Cadence: Intelligence Decay

Intelligence decays. A finding from 30 days ago may be stale. A finding from 90 days ago may be dangerous to act on. Scheduled research sweeps prevent staleness from accumulating silently.

Watch (Frequent)
15–30 minutes. Catch critical changes: new releases, security advisories, breaking changes. Narrow scope, high frequency matched to domain volatility.
Pulse (Moderate)
30–60 minutes. Track broader landscape shifts, community sentiment changes, emerging patterns. Half the watch frequency.
Deep Refresh (Thorough)
1–2 hours. Full re-evaluation. Question assumptions. Check if the right questions are still being asked. Monthly to quarterly.

Three staleness thresholds: time-based (security findings = 0 days, technology = 3–7 days, market positioning = 14–30 days), event-based (new version ships = finding invalidated regardless of age), and confidence-based (lower-tier findings decay faster because initial confidence was lower).

Editorial Standards

Six core principles govern all written output from EngineOS. Not aspirational — enforced by the advisory layer and tested by the quality gates.

  • 1 Evidence Requirement. If you cannot cite it, do not claim it. Every claim needs a source and credibility tier. "I believe" and "it seems like" are red flags.
  • 2 Honest Assessment. Never oversell. Never downplay. Note residual risk. "Impressive adoption rate AND significant unresolved security concerns" is honest. Picking one framing is not.
  • 3 Transferable Framing. Distinguish universal principles from tool-specific details. When a concept transfers, say so explicitly.
  • 4 Community Validation. Every research question gets both official docs and community intelligence. Disagreement is an intelligence insight.
  • 5 Security as a Lens. Security is evaluated on every decision, not treated as a separate phase. Noted inline, where the decision is made.
  • 6 Living Documentation. Mark outdated content as outdated. Never delete. All entries are date-stamped. The history has value.

Section-by-Section Construction

Quality degrades predictably in single-pass generation beyond approximately 500 lines. The first third is strong, the middle is adequate, the final third loses detail and drops conventions. The section-construction methodology solves this with four phases: Plan sections with unique namespace prefixes, Build one section at a time with inter-section verification, Review the whole output as a reader would experience it, and Render-validate for visual outputs via Puppeteer (typical iteration count: 2–4 passes). This walkthrough was built using this methodology.

06 Design Decisions

EngineOS records every design decision with context, options, and rationale. 28 decisions in DECISIONS.md. Click any card to see the full reasoning.

What was decided: Four-tier loading model. Tier 1 (~340 lines always), Tier 2 (path-scoped rules), Tier 3 (skill content on invocation), Tier 4 (reference docs on demand).

Why: The SEE's 918-line CLAUDE.md loaded everything on every session. At scale, it consumed so much of the context window there was barely room for work. A session invoking 3 of 28 skills now loads 3 skills, not 28. The savings compound with every skill that does not need to load.

Date: Phase 1, realized Phase 5A

What was decided: Three-layer enforcement: CLAUDE.md Core Behavior + PostCompact hook + PreToolUse mechanical gate + phase-controller subagent/render rules.

Why: Advisory governance fails on confident agents — structural, not behavioral. In J3 (Sardine resume), the agent went from file loading to resume writing to DOCX generation with zero governance engagement. The resume was 9.8/10 quality. But governance failed completely. The hook intercepts every Write/Edit call and returns permissionDecision: "deny" when no run plan exists. The agent cannot override this.

Immediate validation: The hook caught its own implementation. When the CLAUDE.md edit was attempted without a run plan, the hook blocked it.

Date: J3 Finding 1

What was decided: Hooks for non-optional file operations, advisory for semantic judgment. Not everything can be a hook.

Why: A hook can check "does a run plan exist?" (binary, deterministic). It cannot check "is this research synthesis well-reasoned?" or "does this campaign match the client's voice?" The split is deliberate: mechanical enforcement for deterministic operations, advisory enforcement for semantic operations. The operator is the final layer for everything else.

Date: Phase 5C

What was decided: Single BL operation combining state integrity tightening (control plane drift, path canonicalization, hook hardening) with cowork pattern internalization (encoding the operator's corrective behaviors as system artifacts).

Why: Track 1 (fix state) alone gives a tighter system that drifts again. Track 2 (install discipline) alone gives encoded patterns on top of unstable state. Together, the fixed substrate and installed patterns reinforce each other. The new hook scope-matching catches governance drift. The new patterns catch variant-hunting and confident-negative failures. The new evidence-first-reporting rule catches unverified state claims at Tier 1.

Scope: 8 files created, 13 files modified. 4 new problem patterns, 1 new rule, v1-to-v2 hook rewrite.

Date: 2026-04-05

What was decided: Minimal routing layer that points to where detail lives. Contains identity, core behaviors, skill routing summary, engine convention, key references. Delegates everything else.

Why: Every line in CLAUDE.md costs context on every session. The SEE's 918-line CLAUDE.md tried to contain everything: logging specs, engagement structure, integration config, full skill inventory, patterns index. ODC's concise editorial DNA approach outperformed the comprehensive inventory approach. The routing layer puts the right detail in the right tier.

Date: Phase 5A

What was decided: Trace the genealogy of each capability and use the strongest version from any source. When no single source had the best version, composite from multiple sources.

Why: 175+ skills across 11 engines needed consolidation. The Act 2 skill genealogy traced every capability to its strongest implementation. For 8 capabilities, the best version required compositing (e.g., transcript-processor = SEE v1.1 methodology + restaurant principles). This approach preserved hard-won operational knowledge while producing something better than any source alone.

Date: Phase 1–2A

What was decided: Context-dependent forcing with explicit skip-justification. Writing-plans output populates Layer 4 of the run plan. The production step reads Layer 4 as its first action. Empty Layer 4 means production cannot proceed.

Why: Three sessions (WS3–WS5) proved advisory enforcement does not work for planning skills. Structural enforcement (file-based input dependency) works where the artifact is concrete — a plan in Layer 4. Advisory enforcement with transparency (visible skip-justification) works where artifacts are fuzzy — like brainstorming. The asymmetry is intentional.

Date: WS6

What was decided: All log entries go to root logs/. Engine-local logs are legacy. Every entry is tagged with an engine column for filtering.

Why: Centralized logging with tenant tags is the industry standard across Grafana Loki, Datadog, Azure, AWS, and OpenTelemetry. Per-tenant stores are only recommended under strict regulatory isolation or at scales like 100M events/second. At EngineOS scale, one location with engine tags is simpler and sufficient. Filtering by engine tag produces the tenant-specific view.

Key Build Methodology

The build encoded several discipline practices that are now formalized in EngineOS methodology:
