Design System

The EngineOS design system provides a unified visual language across all HTML outputs produced by any engine. It is a single CSS file -- design-system/enterprise-styles.css -- composited from two production-proven sources: MLR's enterprise stylesheet (776 lines, November 2025, battle-tested across 13 professional deliv

Overview¶

Engines producing HTML link this stylesheet. Engine-specific visual additions go in engine-level CSS that follows or imports the shared file. No engine duplicates tokens defined at the OS layer.

The system ships with five companion reference documents: color-tokens.md (full token inventory), typography.md (type scales and spacing), accessibility.md (verified contrast tables), pdf-pipeline.md (Chrome headless generation), and render-validate-pipeline.md (6-step visual QA). This document synthesizes all six sources into one architectural reference.

The House Deliverable Style (navy/gold)¶

The enterprise stylesheet below is the walkthrough/showcase lineage. Client deliverables ship in a second, newer identity: the house navy/gold report page — white page on warm-gray canvas, navy #1f3a5f + gold #b08423 spine, finding-panels, tier badges, the claims-confidence bar, and the per-section engagement loop. It evolved across the June 2026 client arc (an investor-diligence engagement, a client intake-response engagement, a comp-benchmarking engagement, a go-to-market launch engagement) and was enforced through operator feedback and exemplars before it had a home in this directory; as of 2026-07-02 it is captured at the source level in design-system/house-style.md (identity, signature components, the de-AI rules, and the clone-and-prune build motion). The operational ship-gate is templates/house-deliverable-component-checklist.md. When producing a client deliverable, that pair — not the enterprise stylesheet alone — is the standard.

7-Layer CSS Architecture¶

The stylesheet is organized into seven layers, ordered by specificity and dependency. Each layer builds on the one before it. The layering exists for three reasons: it enforces a single source of truth for design tokens (Layer 1), it separates concerns cleanly enough that an engine can use Layer 2 for reports without pulling in Layer 3’s interactive components, and it keeps print/dark/responsive overrides isolated from the base visual system.

Layer 1: CSS Custom Properties¶

Single source of truth for every design token. Components reference these variables – never hard-coded hex values. If a color, spacing value, or font stack appears in Layers 2-7, it traces back to a :root variable defined here.

:root {
  /* Typography */
  --font-body: -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto,
               Oxygen, Ubuntu, Cantarell, sans-serif;
  --font-mono: "SF Mono", SFMono-Regular, ui-monospace,
               "DejaVu Sans Mono", Menlo, Consolas, monospace;

  /* 4px spacing grid */
  --space-1: 4px;   --space-2: 8px;   --space-3: 12px;
  --space-4: 16px;  --space-5: 20px;  --space-6: 24px;
  --space-8: 32px;  --space-10: 40px; --space-12: 48px;

  /* Layout constraints */
  --max-content-width: 1200px;
  --max-prose-width: 780px;
  --sidebar-width: 260px;

  /* Semantic color tokens (50+ across 7 categories) */
  --color-blue-500: #3b82f6;    /* Infrastructure, links, primary */
  --color-red-500: #ef4444;     /* Security, warnings, critical */
  --color-green-500: #22c55e;   /* Success, data/config, completed */
  --color-amber-500: #f59e0b;   /* Tips, user/operator, educational */
  --color-indigo-500: #6366f1;  /* External services */
  --color-purple-500: #a855f7;  /* Agent/LLM */
  --color-stone-700: #44403c;   /* Primary body text */
  /* ... plus shades at 50/100/200/300/400/600/800/900 per category */

  /* Enterprise report palette (MLR slate-gray, pandoc-aligned) */
  --color-enterprise-text: #333333;
  --color-enterprise-accent: #4a5568;
  --color-enterprise-border: #e2e8f0;
  /* ... */

  /* Chart and role colors (D3.js visualization) */
  --chart-color-1: #4A90E2;  /* Primary series / leader */
  --chart-color-2: #27AE60;  /* Secondary series / positive */
  --chart-color-3: #E74C3C;  /* Tertiary series / negative */
  /* ... 6 sequential colors total */
}

Every downstream layer references these properties. When dark mode activates, Layer 6 remaps the custom properties – no component code changes.

Layer 2: Core Enterprise Formatting¶

Professional report styling aligned with pandoc output conventions. This layer handles the bread-and-butter elements of any report deliverable: base typography, heading hierarchy with bottom-border anchors, table formatting with alternating rows and hover states, list styles, section boxes, badges (both grayscale and colored priority variants), callouts (enterprise callout-box with 5 semantic variants plus interactive .callout with 4 variants), header patterns, and table-of-contents navigation.

Representative structure:

/* Tables: enterprise convention */
th {
  background-color: var(--color-enterprise-accent);
  color: #ffffff;
  font-size: 11px;
  text-transform: uppercase;
  letter-spacing: 0.5px;
}

tbody tr:nth-child(even) {
  background-color: var(--color-enterprise-bg-alt);
}

/* Callouts: four semantic variants (interactive/ODC-derived) */
.callout.critical { background: var(--color-red-50);   border-left-color: var(--color-red-500); }
.callout.tip      { background: var(--color-amber-50); border-left-color: var(--color-amber-500); }
.callout.info     { background: var(--color-blue-50);  border-left-color: var(--color-blue-500); }

/* Badges: grayscale for document body, colored for emphasis */
.badge {
  display: inline-block;
  padding: 4px 10px;
  border-radius: 3px;
  font-size: 9pt;
  font-weight: 600;
  text-transform: uppercase;
}

Two callout systems coexist. The enterprise .callout-box (with .important, .success, .info, .warning, .danger modifiers) is from MLR’s report convention. The interactive .callout (with .critical, .warning, .tip, .info modifiers and uppercase .callout-label) is from ODC’s walkthrough convention. Both are available; use enterprise callouts in reports, interactive callouts in walkthroughs.

Layer 3: Interactive Components¶

For curriculum walkthroughs and interactive HTML outputs. This layer provides:

  • Code blocks with syntax highlighting (8 token types, monospace font, language labels, copy-to-clipboard buttons)
  • Expandable/collapsible sections with semantic type variants (understanding, troubleshooting, expected-output, deployment) that color-code the trigger
  • Interactive checkboxes with localStorage persistence, custom appearance (20px visual, green check on checked state), focus-visible outlines, and strikethrough labels
  • Navigation sidebar with fixed positioning, scroll spy, progress bar, nav groups with uppercase labels, and active-state highlighting
  • Phase headers with phase-number labels, time-estimate badges, and security-critical border variants
  • “Understanding” sections with amber accent for educational context
  • Notes input fields for user annotations with localStorage persistence
  • Directory tree display in monospace
/* Expandable sections */

  width: 100%;
  padding: var(--space-3) var(--space-4);

  border: none;

  font-size: 15px;
  font-weight: 600;

Layer 4: Data Visualization¶

Strategic analysis components from MLR’s competitive intelligence deliverables:

  • SWOT grids – 2x2 CSS grid with color-coded quadrants (green/strengths, red/weaknesses, blue/opportunities, amber/threats), each with section headers and bullet lists
  • Positioning maps – Absolute-positioned quadrant charts (700x500px) with axis labels, quadrant labels, and platform dots using semantic role colors (leader/challenger/incumbent/threat/subject)
  • Chart color classes – Six sequential colors mapped to CSS classes for D3.js integration (chart-color-1 through chart-color-6 applying both fill and stroke)
  • Map legends and strategic options formatting

Layer 5: Print/PDF Optimization¶

CSS rules that Chrome headless depends on for clean PDF generation. Three mechanisms:

  1. Page-break control – Headings get page-break-after: avoid (no orphaned headings). Table rows get page-break-inside: avoid. thead repeats on every page via table-header-group. Explicit .page-break and .no-break utility classes.

  2. @page rule – Letter portrait, 0.75in margins.

  3. @media print query – Hides interactive elements (sidebar, dark mode toggle, copy buttons, progress bar), forces expandable sections open (display: block !important), and resets body padding.

@page {
  size: letter portrait;
  margin: 0.75in;
}

@media print {
  .sidebar, .dark-mode-toggle, .code-copy-btn,
  .sidebar-progress { display: none; }

  .expandable-content { display: block !important; }

  h1, h2, h3, h4 { page-break-after: avoid; }
  tr { page-break-inside: avoid; }
  thead { display: table-header-group; }
}

Layer 6: Dark Mode Overrides¶

Activated by setting <html data-theme="dark">. The implementation remaps every custom property in the :root scope to its dark-mode equivalent. Components that reference --color-stone-700 for body text automatically get #d4d4d4 instead of #44403c. No component-level dark mode logic is needed.

The stone scale inverts: --color-stone-50 goes from #fafaf9 (near-white) to #1a1a1a (near-black). Semantic colors shift to lighter, higher-contrast variants: --color-blue-500 goes from #3b82f6 to #60a5fa, --color-red-500 from #ef4444 to #f87171.

Element-specific overrides handle components that reference hard-coded values or need additional dark treatment: tables, sidebar, expandable triggers, checkboxes, input fields, and syntax highlighting tokens.

[data-theme="dark"] {
  --color-stone-50: #1a1a1a;   /* Was #fafaf9 */
  --color-stone-700: #d4d4d4;  /* Was #44403c */
  --color-stone-900: #f5f5f5;  /* Was #1c1917 */

  --color-blue-500: #60a5fa;   /* Was #3b82f6 */
  --color-red-500: #f87171;    /* Was #ef4444 */
  --color-green-500: #4ade80;  /* Was #22c55e */
  --color-amber-500: #fbbf24;  /* Was #f59e0b */
  /* ... all semantic categories remapped */
}

/* Dark syntax highlighting */
[data-theme="dark"] .token-keyword    { color: #a78bfa; }
[data-theme="dark"] .token-string     { color: #34d399; }
[data-theme="dark"] .token-comment    { color: #737373; }

All dark-mode text-on-background pairings are verified to WCAG AA. The contrast table is in accessibility.md.

Layer 7: Responsive/Mobile¶

Triggered at max-width: 768px. Three major adaptations:

  1. Sidebar collapse – The fixed sidebar transforms off-screen (translateX(-100%)) and becomes an overlay triggered by a hamburger button. A backdrop overlay dims the content area.

  2. Touch targets – Nav items, expandable triggers, and checkboxes get min-height: 44px per WCAG 2.1 SC 2.5.5.

  3. Content scaling – Body font increases to 14px, padding reduces to --space-5, tables wrap in horizontally-scrollable containers, and positioning maps scale via aspect-ratio: 7/5 with width: 100%.

@media (max-width: 768px) {
  .sidebar {
    transform: translateX(-100%);
    transition: transform 200ms ease;
    width: 280px;
  }
  .sidebar.open { transform: translateX(0); }

  .nav-item, .expandable-trigger, .checkbox-input {
    min-height: 44px;
  }

  .matrix-container {
    width: 100%;
    height: auto;
    aspect-ratio: 7/5;
  }
}

50+ semantic tokens across 7 categories, each with light/dark pairs. Every color belongs to a semantic category – the category determines usage, not aesthetic preference.

Typography¶

Font Stacks¶

Two font stacks, no external font loading:

  • Body/UI: -apple-system, BlinkMacSystemFont, "Segoe UI", Roboto, Oxygen, Ubuntu, Cantarell, sans-serif – system font stack, zero FOUT, renders natively on every platform.
  • Monospace: "SF Mono", SFMono-Regular, ui-monospace, "DejaVu Sans Mono", Menlo, Consolas, monospace – used for code blocks, inline code, file paths, directory trees, config keys.

Text rendering is optimized with -webkit-font-smoothing: antialiased and text-rendering: optimizeLegibility.

Two Type Scales¶

The system has two type scales for two contexts. Selecting the wrong scale for a deliverable type is a common failure mode.

Interactive / Curriculum Scale (ODC-derived): 16px body text, detailed type hierarchy for walkthroughs and interactive HTML. Heading sizes: h1 at 28px/700, h2 at 22px/700, h3 at 18px/600. Body at 16px/400 with 1.65 line-height. Code at 14px. Nav items at 14px/500. Max prose width: 780px.

Enterprise Report Scale (MLR-derived): 13px body text, conservative hierarchy for professional reports and PDF output. Heading sizes: h1 at 24pt/700, h2 at 18pt/600, h3 at 14pt/600, h4 at 12pt/600. Table headers at 11px/600 uppercase. Max content width: 1200px.

Scale selection by output type:

Output Type Scale Rationale
Interactive walkthrough Interactive Larger body for screen reading, detailed hierarchy for curriculum structure
Competitive analysis report Enterprise Pandoc alignment, conservative sizing for dense data, PDF-optimized
Framework explainer Interactive Interactive HTML with progressive disclosure
Client-ready PDF Enterprise Professional, print-optimized
Dashboard / data visualization Either Enterprise for data-heavy, interactive for narrative-heavy

All spacing is built on a 4px grid. Nine tokens:

--space-3 12px Standard inline padding (nav items, table cells)
--space-4 16px Standard block padding (cards, callouts)
--space-5 20px Content section vertical gap

--space-8 32px Phase section top padding
--space-10 40px Major section dividers, desktop content padding

Heading Rules¶

Never skip heading levels (h1 > h2 > h3 > h4). Both scales use bottom borders as visual anchors: the interactive scale puts a 2px border in --color-stone-200 on h2; the enterprise scale puts a 3px border in --color-enterprise-accent on h1 and a 2px border in --color-enterprise-border on h2. h3 and h4 get no borders in either scale. All heading levels carry page-break-after: avoid for PDF generation.

Accessibility¶

The design system targets WCAG AA: 4.5:1 contrast ratio for normal text (< 18px), 3:1 for large text (>= 18px or >= 14px bold).

Focus States¶

All interactive elements have visible focus indicators: 2px solid --color-blue-500 with 2px offset. Applied to checkboxes (:focus-visible), notes inputs (:focus), expandable triggers, copy buttons, and sidebar nav items. Focus must be visible in both light and dark mode.

Touch Targets¶

Mobile touch targets are at least 44x44px per WCAG 2.1 SC 2.5.5. Nav items and expandable triggers get min-height: 44px in the responsive layer. Checkboxes are 20px visually but provide a 44px hit area via padding.

Color-Independent Meaning¶

Color is never the sole indicator: badges include text labels (“CRITICAL”, “HIGH”), SWOT boxes include section headers, callout variants include uppercase labels, and diagram semantic categories are reinforced by shape differences (rectangles vs. circles vs. dashed boundaries).

Reduced Motion¶

For users with prefers-reduced-motion, all transitions and animations collapse to 0.01ms:

@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    transition-duration: 0.01ms !important;
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    scroll-behavior: auto !important;
  }
}

This rule is recommended for inclusion in engine-level CSS that implements interactive behaviors.

Semantic HTML Requirements¶

The design system assumes correct semantic structure: <button> for expandable triggers (not <div> with click handlers), <nav> for sidebar, <main> for primary content, proper heading hierarchy, aria-expanded on expandable triggers, aria-current="true" on active nav items.

Production Pipelines¶

PDF Pipeline¶

Chrome headless generation with no intermediate tooling, no build system, no server. The HTML source is the single source of truth; the PDF is a generated artifact.

Command:

"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless \
  --disable-gpu \
  --no-pdf-header-footer \
  --print-to-pdf="output.pdf" \
  "file:///absolute/path/to/source.html"

The --no-pdf-header-footer flag is critical – without it, Chrome prints the file URL at the top and date/page number at the bottom of every page. The --disable-gpu flag avoids rendering inconsistencies in headless mode.

CSS requirements: The PDF pipeline depends on three CSS mechanisms in the stylesheet: @page (letter portrait, 0.75in margins), page-break rules (headings avoid, rows avoid, thead repeats), and the @media print query (hides interactive elements, forces expandables open). These are not optional – removing any of them breaks the pipeline output.

Deliverable production sequence:

  1. Content creation / template population (HTML with {{PLACEHOLDER}} convention)
  2. Render-validate (browser verification – see next section)
  3. Fix any defects (one at a time, re-verify each)
  4. Chrome headless PDF generation
  5. PDF verification (open and scan for page-break issues, missing headers, blank trailing pages)
  6. Distribution-ready

Combined PDFs: For multi-file deliverables, generate individual PDFs then combine with pdfunite (poppler-utils).

Common failures: Tables breaking mid-row (fix: tr { page-break-inside: avoid }), headings orphaned at page bottom (fix: h1-h4 { page-break-after: avoid }), interactive elements visible in PDF (fix: @media print rules hiding sidebar/toggle/copy-btn), expandable sections collapsed (fix: .expandable-content { display: block !important } in print query), color mismatch between browser and PDF (fix: verify in print preview first).

This pipeline was battle-tested across 13 MLR deliverables through 7 iteration cycles (V1.0 through V2.3, November 2025). Cross-platform: same flags on macOS/Linux/Windows, only the Chrome executable path changes.

Render-Validate Pipeline¶

6-step visual verification using Puppeteer. Exists because source code review is insufficient for visual outputs – four classes of defects are invisible in code:

  1. CSS hiding content – a display:none or zero-height container hides content that has correct markup.
  2. Broken interactivity – click handlers bound to wrong selectors, event listeners on stale IDs.
  3. Missing runtime dependencies – CDN libraries that load but do not initialize (syntax highlighting, charting).
  4. Non-persisting state – localStorage bindings referencing stale IDs, save handlers that do not fire.

All four were discovered in the ODC’s first production walkthrough. “It looks right in the markup” is not evidence.

The six steps:

  1. Render – Launch Puppeteer, navigate to the HTML file via file:// URL, wait for full page load including CDN libraries.

  2. Screenshot – Capture systematic evidence: full page at 1280px (desktop), each major section, sidebar navigation (default + active state), most complex diagram at detail zoom, full page at 375px (mobile), and at least one section in dark mode.

  3. Audit against style guide – Every item is YES/NO. Diagrams: visible, correct colors, readable labels, correct arrows, dark mode rendering. Interactive: expandables open/close, checkbox persistence, notes persistence, copy buttons functional. Layout: sidebar hierarchy, scroll spy, mobile hamburger, table horizontal scroll, 44px touch targets. Typography: monospace code blocks, syntax highlighting active, correct callout colors, WCAG AA contrast in dark mode.

  4. Audit diagrams against design intent – Three per-diagram checks: (a) the visual pattern matches the concept’s behavior (a flow concept in a layered diagram is wrong regardless of rendering quality), (b) the isomorphism test (remove all labels – does the bare structure still communicate the concept? if not, it is decoration, not communication), (c) the diagram argues, not just displays (it makes a point about relationships, dependencies, risks, or sequences – not just listing items in boxes).

  5. Fix and re-render – One defect at a time. Fix, reload, re-screenshot the specific area, verify the fix without regressions. Do not batch fixes – that masks regressions where fixing issue A breaks something near issue B.

  6. Report results – Iteration count, issues found and fixed, remaining known issues, screenshot count and coverage scope.

The variety rule: In any output with more than three major diagrams, each should use a different visual pattern. If three diagrams are all left-to-right box-and-arrow layouts, at least two are almost certainly using the wrong pattern for their concept.

Fallback: If Puppeteer MCP is unavailable, degrade to manual verification (operator opens the file and provides screenshots). Never degrade to skipping verification.
