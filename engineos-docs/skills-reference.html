Skills Reference

EngineOS ships 29 skills at .claude/skills/. Each skill is a self-contained SKILL.md file with YAML frontmatter (description, allowed-tools) and a structured body covering purpose, triggers, phases, and integration points.

Skills load passively via native discovery (descriptions only, ~2% of context). Full content loads only on invocation. Every skill declares its allowed-tools in frontmatter, restricting what tools it can access.

Categories¶

Research and Intelligence¶

Seven skills that gather, classify, and structure external information. recall is the read-side retrieval companion – it searches the internal corpus (intelligence log, KB, daily logs, run-plans, methodology) before external research begins.

market-scanner¶

One-liner: Market intelligence, company research, and industry scanning for any engine.

Triggers: “research [company]”, “scan the [industry] market”, “what’s happening at [company]”, “competitive landscape for [space]”, “validate this hypothesis”, “market intelligence on [topic]”.

Allowed tools: Read, Write, Edit, Glob, Grep, WebSearch, WebFetch, mcp__brightdata__*, mcp__context7__*

Key behaviors: - Operates in two modes governed by depth-governor: Scan (broad landscape, Phase A only) and Deep-Dive (specific target, all three phases – broad search, targeted research, comparative analysis). Mixed depth is normal. - Teaches methodology, not just tool usage. For token-heavy research sweeps, writes code to gather, filter, and synthesize, keeping heavy processing out of context. - Always starts by clarifying the research objective – what question are we answering, what evidence would validate or invalidate.

Invokes: depth-governor (before execution), findings-formatter (to structure output)

Invoked by: research-engine, lead-builder, campaign-builder, attio-optimizer

research-engine¶

One-liner: Orchestrate research and analysis work across EngineOS capabilities. This is the routing layer – it classifies the domain, looks up capabilities in the registry, and invokes them.

Triggers: “research [topic]”, “analyze [company/market]”, “benchmark [metric]”, “competitive analysis of [space]”, “what does the data say about [question]”, or any request for a consulting-grade research deliverable.

Allowed tools: Read, Write, Edit, Glob, Grep, Skill

Key behaviors: - Thin orchestration skill that routes, not researches. Research logic lives in market-scanner and other registered capabilities. - Runs a 5-stage pipeline: Intake (clarify who and what), Research (route via registry), Analysis (three-ring convergence, findings-formatter), Deliverable (section-construction, render-validate), Delivery (deploy, quality gate). - Applies the three-ring approach to every research request: primary data, industry surveys, and broader context. When all three rings agree, the finding is solid. When they disagree, the contradiction is flagged.

Invokes: market-scanner, findings-formatter, section-construction, render-validate, qa-pipeline, depth-governor (via registry resolution)

Invoked by: phase-controller (via skill chain), eos-assistant (in production mode)

depth-governor¶

One-liner: Mandatory 30-second depth classification (scan vs. deep-dive) before starting any substantive work.

Triggers: Starting research, synthesis, or output generation. Invoked by phase-controller as part of run plan creation.

Allowed tools: Read, Glob, Grep

Key behaviors: - Prevents the default failure mode: medium-quality everything. Forces explicit classification so scans are broad and fast, deep-dives are exhaustive and narrow. - Three-question classification: (1) Will this drive a strategic decision? (2) Is this a high-priority target? (3) Does the operator have contradictory information? First YES triggers deep-dive; all NO means scan. - Classifies per-topic, not per-task. A single task often has both scan and deep-dive areas. Watches for reclassification signals during execution.

Invokes: None (read-only governance skill)

Invoked by: phase-controller, market-scanner, research-engine, findings-formatter, output-self-test, section-construction, content-updater

findings-formatter¶

One-liner: Select and apply the right structure for research findings during synthesis. Seven patterns plus an escape hatch.

Triggers: Writing knowledge base entries, intelligence log entries, research reports, or structured findings. Especially when catching yourself writing “we found that…” prose paragraphs.

Allowed tools: Read, Write, Edit, Glob, Grep

Key behaviors: - Seven typed finding patterns: Contradiction Insight, Validation Entry, Discovery Entry, Risk Entry, Comparison Matrix, Resolution Entry, Recommendation Entry. Each has required and optional fields. - Depth-aware fill level: scan depth skips optional fields, deep-dive fills everything. The pattern shape stays the same; completeness changes. - Enforces source traceability – every claim must have a named source and confidence level retrievable in under 5 seconds.

Invokes: depth-governor (to check depth classification)

Invoked by: research-engine, market-scanner (indirectly, as structured output stage)

codebase-onboarder¶

One-liner: First-time codebase analysis – creates CLAUDE.md and context structure for any repository adopting Claude Code.

Triggers: “onboard this codebase”, “set up Claude Code for this repo”, first time using Claude Code with an existing repository, after major architectural changes.

Allowed tools: Read, Glob, Grep, Bash

Key behaviors: - Three-phase workflow: Discovery (read-only audit of structure, build/test/run, architecture, existing docs), Generate (create CLAUDE.md under 100 lines plus supporting docs), Validation (verify commands actually work). - Principles: Minimal over comprehensive, pointers over duplication, verified over assumed, honest over complete. - Operator review required before finalizing. The operator knows things about the codebase that discovery cannot surface.

Invokes: None

Invoked by: Manual invocation only

recall¶

One-liner: Search EngineOS’s second brain (intelligence log, knowledge index, KB concepts/connections, recent daily logs, recent run-plans, methodology) for prior context relevant to a topic. Pure Read/Grep/Glob – zero API cost.

Triggers: /recall <query>, “have we seen this”, “what’s our prior thinking on X”, “what did we decide about”, “do we have notes on”, “remember”, “look up”, “search the second brain”, or before making an architecture/methodology/pattern decision in a domain where prior intelligence likely exists.

Allowed tools: Read, Glob, Grep

Key behaviors: - Six-surface priority order: (1) logs/intelligence-log.md – curated strategic moments, highest density; (2) knowledge/index.md – 200+ row catalog with summaries, cheapest pointer; (3) knowledge/concepts/*.md + knowledge/connections/*.md – full KB articles, grep headers and first paragraphs unless query matches main subject; (4) daily/*.md last 30 days – recent session arcs and work-in-flight context; (5) run-plans/*.md last 60 days – detailed plans with hardened criteria and execution logs; (6) methodology/*.md – only when query is methodology-flavored. Stopping rule: if surfaces 1-2 yield 3+ strong hits, do not exhaustively grep lower surfaces. - Honest “nothing found” on zero hits – does NOT hallucinate matches when the corpus is empty. Returns the surfaces searched and suggests rephrasing, scripts/query.py for LLM-ranked deeper search, or noting the gap as a candidate for a new article. - Does NOT invoke scripts/query.py (which uses Claude Agent SDK and has API cost). Recall is pure ripgrep + Read; typical invocation under 2 seconds wall-clock. The Agent SDK path remains available for synthesis-heavy queries when recall returns nothing. - Does NOT add interpretive commentary – cites, does not synthesize. The operator does the synthesis after seeing the ranked hits. - Does NOT search across engine tenants by default. OS-level corpus only unless the query names an engine (“in JSE”, “for sales-enablement”), in which case the grep extends into that engine’s knowledge/, engagements/, and CONTEXT.md.

Invokes: None (read-only governance skill)

Invoked by: Manual /recall <query> invocation; auto-fire via the UserPromptSubmit retrieval hook’s heuristic gate (hooks/prompt-retrieval.py, ~90% of retrieval) and the retrieval-before-decide framework pattern at architecture/methodology decision points.

Content and Deliverable Production¶

Seven skills that produce client-facing or operator-facing content. framework-explainer is cross-listed from Research.

campaign-builder¶

One-liner: Email sequence and outreach campaign creation. Orchestration tier – invokes content-updater for KB updates and qa-pipeline before delivery.

Triggers: “create email sequence”, “build a campaign”, “write outreach emails”, “nurture sequence for [segment]”, “sales cadence”, “follow-up sequence”.

Allowed tools: Read, Write, Edit, Glob, Grep, Skill

Key behaviors: - Mandatory Pre-Flight Check (Phase 0) surfaces the working foundation – KB files, prior research, context, key assumptions – and waits for operator confirmation before building. - Mandatory Campaign Readiness Litmus Test before any campaign launch: 5 questions testing conversation depth, pain validation, warm paths, proof points, and entry point knowledge. Fewer than 3/5 pass means “not ready.” - Four campaign frameworks: Cold Outreach, Warm Nurture, Post-Event Follow-up, Re-engagement. Four personalization levels from Segment to Deep.

Invokes: content-updater (for KB updates during campaign research), qa-pipeline (before delivery)

Invoked by: phase-controller (via skill chain)

lead-builder¶

One-liner: Enriched lead list and prospect profile generation for targeted outreach.

Triggers: “build a lead list”, “find prospects in [industry/segment]”, “who should we target”, “create target account list”, “enrich these leads”, “prioritize prospects”.

Allowed tools: Read, Write, Edit, Glob, Grep, WebSearch, WebFetch, mcp__brightdata__*, mcp__attio-mcp__*

Key behaviors: - Core philosophy: filter before output. Research broadly, qualify ruthlessly, output only what passes. A weak lead list wastes sales time. - Orchestration tier – invokes market-scanner for web research, attio-ops for CRM enrichment, qa-pipeline before delivery. - Depth-aware: simple (single industry, known ICP, available sources) vs. complex (multiple verticals, emerging ICP, limited sources). Defaults to complex when mixed.

Invokes: market-scanner, attio-ops, qa-pipeline

Invoked by: phase-controller (via skill chain)

transcript-processor¶

One-liner: Process meeting transcripts, stakeholder conversations, and session notes into structured intelligence.

Triggers: User pastes a meeting transcript, shares call notes, session notes, brain dumps, Slack/email threads, or any raw dialogue containing intelligence.

Allowed tools: Read, Write, Edit, Glob, Grep, Skill

Key behaviors: - Non-negotiable rules: stakeholder corrections override analysis, preserve voice with direct quotes, track the correction chain (what KB said, what correction is, why original was wrong), don’t over-interpret. - Pre-Phase tags every meeting (type, date, participants, urgency, signal quality) and threads it to prior conversations by searching CONTEXT-HISTORY.md and existing profiles. - Routes extracted intelligence to KB locations: decisions, pain points, action items, quotes, hypotheses, relationship dynamics.

Invokes: content-updater (for KB updates), profile-builder (when new stakeholder detected), audit-logging

Invoked by: phase-controller (via skill chain)

profile-builder¶

One-liner: Build operator profile from source material and structured intake. Generates the identity files EngineOS personalizes around.

Triggers: “set up my profile”, “who am I”, Phase 0 onboarding, missing PROFILE.md detected by session-orchestrator.

Allowed tools: Read, Write, Edit, Glob, Grep, Skill

Key behaviors: - Two modes: fresh onboarding (full flow) when PROFILE.md is missing, or profile refresh (targeted update) when it exists. - Source Material Intake reads everything in operator/assets/ and extracts career timeline, role history, quantifiable claims, voice signals, goals. - Generative population runs a 37-question conversational intake – not reading from a list but generating specific, tailored questions from source material.

Invokes: content-updater (for file updates)

Invoked by: session-orchestrator (when PROFILE.md is missing), transcript-processor (when new stakeholder detected)

section-construction¶

One-liner: Incremental build for complex outputs. Prevents single-pass quality degradation on outputs exceeding ~500 lines.

Triggers: “build the walkthrough”, “generate the report”, “create the interactive HTML”, “produce the output”, or any variation of generating a large structured deliverable.

Allowed tools: Read, Write, Edit, Glob, Grep

Key behaviors: - 10-second gate: Only applies if the output was classified as deep-dive AND will exceed ~500 lines. Otherwise, generate normally. - Phase A plans sections with namespace prefixes, cross-reference mapping, and size balance checks before any content is written. Operator approves the plan. - Builds one section at a time with explicit verification between sections, preventing the known degradation pattern where the last third of single-pass outputs loses detail.

Invokes: depth-governor (referenced for classification)

Invoked by: research-engine, framework-explainer, phase-controller (via skill chain)

render-validate¶

One-liner: Mandatory visual verification for interactive HTML outputs via browser rendering and screenshot review.

Triggers: “the output is ready”, “HTML complete”, “check the render”, “does it look right?”, or any variation of declaring a visual output finished.

Allowed tools: Read, Glob, Grep, mcp__puppeteer-mcp-claude__puppeteer_launch, mcp__puppeteer-mcp-claude__puppeteer_navigate, mcp__puppeteer-mcp-claude__puppeteer_screenshot, mcp__puppeteer-mcp-claude__puppeteer_evaluate, mcp__puppeteer-mcp-claude__puppeteer_click, mcp__puppeteer-mcp-claude__puppeteer_wait_for_selector, mcp__puppeteer-mcp-claude__puppeteer_close_browser, mcp__puppeteer-mcp-claude__puppeteer_new_page, mcp__puppeteer-mcp-claude__puppeteer_close_page, mcp__puppeteer-mcp-claude__puppeteer_get_text

Key behaviors: - Exists because source code review misses an entire class of visual defects. Provenance: 4 real production defects (hidden diagram via display:none, 14/22 broken expandables, missing syntax highlighting, non-persisting localStorage) – all invisible in source, all obvious in a browser. - Renders HTML via Puppeteer, takes screenshots, audits against design system specifications, fixes issues, re-screenshots in a loop until output matches intent. - Does not apply to pure-text outputs. Only for content that will be opened in a browser.

Invokes: None (verification-only)

Invoked by: research-engine, qa-pipeline (as Stage 3), framework-explainer, phase-controller (via skill chain)

framework-explainer¶

One-liner: Generate interactive HTML presentations that explain frameworks, methodologies, or complex systems to stakeholders.

Triggers: “explain the framework”, “create a presentation”, “visualize how this works”, “make an interactive demo”, “walk me through this system”.

Allowed tools: Read, Write, Edit, Glob, Grep

Key behaviors: - Core insight: people understand file trees. The Finder-style file browser view is the star visual pattern – show the structure in a familiar way, then layer on intelligence. - Five visual patterns: Finder View (Mac-style file browser), Workflow Flow (animated CSS diagrams), Before/After Comparison, Demo Walkthrough (real prompt to real output), Progressive Disclosure (zoom out to zoom in). - Always uses real examples from the framework, never hypotheticals. All HTML must use the EngineOS design system (enterprise-styles.css, color tokens, typography, accessibility).

Invokes: qa-pipeline (on generated HTML), audit-logging

Invoked by: phase-controller (via skill chain)

Cross-listed: Also appears under Research and Intelligence as it explains complex systems.

Integration¶

Seven skills that connect EngineOS to external platforms (Attio CRM and Notion).

attio-mapper¶

One-liner: Map Attio CRM workspaces to generate schema caches and playbooks consumed by all other Attio skills.

Triggers: “map this Attio workspace”, “map Attio”, “check for Attio schema changes”, “refresh Attio schemas”, “what objects are in Attio”.

Allowed tools: Read, Glob, Grep, mcp__attio-mcp__records_get_attributes

Key behaviors: - Dynamic object discovery via GET /v2/objects – never hardcodes object names. Custom objects are discovered automatically. - Three phases: Discovery (enumerate objects, fetch schemas, apply type inference, detect MCP bugs), Change Detection (diff cached vs. current schemas, append changelog), Pattern Learning (analyze structure, log new MCP bugs). - Produces per-object JSON schemas, select field options, human-readable playbook, and schema changelog. Output goes to engines/<engine>/integrations/attio/.

Invokes: audit-logging

Invoked by: attio-ops (prerequisite), attio-qualify (prerequisite), attio-optimizer (prerequisite), session-orchestrator (can trigger refresh)

attio-ops¶

One-liner: Attio CRM operations – CSV import, list population, bulk operations. The single skill for all write-path Attio operations.

Triggers: “import CSV to Attio”, “populate list”, “add contacts to list”, “sync list”, “bulk update”, “import contacts”.

Allowed tools: Read, Write, Edit, Glob, Grep, mcp__attio-mcp__records_search_advanced, mcp__attio-mcp__records_get_details, mcp__attio-mcp__records_list, mcp__attio-mcp__lists_list, mcp__attio-mcp__lists_get_entries, mcp__attio-mcp__objects_list_attributes, mcp__attio-mcp__records_create, mcp__attio-mcp__records_update, mcp__attio-mcp__records_add_to_list

Key behaviors: - Three modes: CSV Import (records into People/Companies objects), CSV to List (records into a specific list with entry values), Bulk List Ops (add/remove/sync/update list membership at scale). - Domain-first company strategy: extracts domain from email, skips generic domains, searches by domain not name, lets Attio auto-enrich. Person-company association is automatic. - Mandatory pre-execution approval gate. Every mutating operation requires explicit user confirmation with a clear summary of what will change.

Invokes: attio-mapper (if schemas missing), audit-logging, content-updater

Invoked by: attio-refiner (downstream execution), lead-builder, phase-controller (via skill chain)

attio-qualify¶

One-liner: ICP classification and lead qualification for Attio contacts. Assigns ICP personas using configurable keyword matching with confidence scoring.

Triggers: “assign ICPs”, “enrich contacts”, “qualify users”, “classify leads”, “ICP coverage”.

Allowed tools: Read, Write, Glob, Grep, mcp__attio-mcp__records_search_advanced, mcp__attio-mcp__records_get_details, mcp__attio-mcp__records_list, mcp__attio-mcp__records_search

Key behaviors: - Two modes: Enrich (bulk ICP assignment via job title matching with confidence scoring) and Qualify (cross-reference new signups against CRM for categorization). - All persona definitions, keywords, weights, and thresholds load from icp_definitions.json at runtime. The skill is the algorithm; the engine owns the data. - Direct API execution for speed: MCP one-by-one takes ~60-90 min for 150 contacts; generated curl scripts take ~3-5 min. Scripts are idempotent.

Invokes: attio-mapper (prerequisite), audit-logging, content-updater

Invoked by: attio-refiner (downstream execution), attio-ops (two-stage import pattern), phase-controller (via skill chain)

attio-optimizer¶

One-liner: CRM health audit, best practices research, and optimization recommendations. Four-phase process: Audit, Research, Recommend, Visualize.

Triggers: “audit the CRM”, “CRM health check”, “how healthy is our Attio”, “clean up Attio”, “optimize CRM”, “CRM optimization report”.

Allowed tools: Read, Glob, Grep, mcp__attio-mcp__records_search, mcp__attio-mcp__records_search_advanced, mcp__attio-mcp__records_search_batch, mcp__attio-mcp__records_search_by_relationship, mcp__attio-mcp__records_search_by_timeframe, mcp__attio-mcp__records_get_details, mcp__attio-mcp__records_get_info, mcp__attio-mcp__records_get_attributes, mcp__attio-mcp__records_list, mcp__attio-mcp__lists_list, mcp__attio-mcp__lists_get_entries, mcp__attio-mcp__objects_list_attributes, mcp__context7__resolve-library-id, mcp__context7__query-docs, mcp__brightdata__search_engine, mcp__brightdata__search_engine_batch, mcp__brightdata__scrape_as_markdown

Key behaviors: - Intelligent sampling with two layers: Layer A (engine-engaged records – referenced in context, active deals, renewal targets) and Layer B (broader health assessment – recent records, dormant records, population extremes). - Five audit categories with weighted scoring: Completeness (30%), Accuracy (25%), Pipeline Health (20%), Consistency (15%), Schema Utilization (10%). - Auto-generates a 7-page interactive HTML presentation suite from audit findings using the EngineOS design system.

Invokes: attio-mapper (prerequisite – fresh schemas required), audit-logging

Invoked by: Phase-controller (via skill chain). Feeds into attio-refiner.

attio-refiner¶

One-liner: Operator-driven audit refinement. Takes attio-optimizer output and produces annotated findings plus approved work orders through structured Q&A.

Triggers: “refine the audit”, “review CRM findings”, “let’s work through the audit”, “approve CRM actions”, “triage the audit actions”.

Allowed tools: Read, Write, Glob, Grep, mcp__attio-mcp__records_search, mcp__attio-mcp__records_search_advanced, mcp__attio-mcp__records_search_by_relationship, mcp__attio-mcp__records_search_by_timeframe, mcp__attio-mcp__records_get_details, mcp__attio-mcp__records_get_info, mcp__attio-mcp__records_list, mcp__attio-mcp__lists_list, mcp__attio-mcp__lists_get_entries

Key behaviors: - The audit is the clean room; the refiner is the war room. Captures WHY things are that way and decides WHAT TO DO, adding operator context (institutional knowledge, automation awareness, historical decisions) that the audit cannot surface. - Structured review by priority: P0 actions get individual attention with 3 structured questions (context, priority check, decision). P1 supports batching. P2/P3 are batch-reviewed. - Produces 06-operator-review.md (annotated findings) and 07-approved-actions.md (work orders structured for downstream execution) plus their HTML visualizations.

Invokes: attio-ops (downstream – executes approved CSV/list actions), attio-qualify (downstream – executes approved ICP actions), audit-logging, content-updater

Invoked by: Operator-initiated after reviewing attio-optimizer output. Valuable but not gating – operators can skip it.

notion-mapper¶

One-liner: Map any Notion workspace to generate a playbook with working code examples, database mappings, and relationship documentation.

Triggers: “map this Notion workspace”, “map from this page down”, “check for Notion changes”, “refresh the playbook”.

Allowed tools: Read, Write, Edit, Glob, Grep, mcp__claude_ai_Notion__notion-search, mcp__claude_ai_Notion__notion-fetch, mcp__claude_ai_Notion__notion-query-database-view

Key behaviors: - Mirrors attio-mapper’s architecture: discovery, caching, change detection, pattern learning. Designed for any Notion workspace, not hardcoded to a specific structure. - Produces a playbook folder with database mappings, working code examples, relationship maps, and pitfall documentation at engines/<engine>/integrations/notion/playbook/. - Engines that provide a workspace context file get significantly better mapping results.

Invokes: audit-logging

Invoked by: notion-ops (prerequisite), session-orchestrator (can trigger refresh)

notion-ops¶

One-liner: Read/write operations for Notion databases. Querying, creating, updating, and analyzing Notion content.

Triggers: User mentions “Notion” or database names, wants to add content matching database patterns, asks about tracked data or database structure.

Allowed tools: Read, Write, Edit, Glob, Grep, Bash, mcp__claude_ai_Notion__*

Key behaviors: - Code-first approach using Notion API directly. Companion Python scripts in scripts/ provide a full SDK for property building, querying, ingestion, and domain helpers. - Supports 4 phases: read from playbook, ingestion (content routing), optimization (schema analysis), and query/analysis (cross-database queries). - Requires a mapped workspace playbook from notion-mapper. If missing, directs the user to run notion-mapper first.

Invokes: notion-mapper (prerequisite if playbook missing), audit-logging

Invoked by: transcript-processor (for action item routing), session-orchestrator (auto-suggest)

Governance and Quality¶

Eight skills that enforce methodology, quality gates, and operational discipline.

phase-controller¶

One-liner: The run controller for all substantive EngineOS work. Classifies operations, builds disk-persisted run plans, forces skill chains, and gates on operator approval.

Triggers: Starting any new work – research, engagement tasks, content production, integration work, system builds/audits, or OS maintenance. Invoked after session-orchestrator has oriented the session.

Allowed tools: Read, Write, Edit, Glob, Grep, Skill

Key behaviors: - Classifies work into 7 types: Build/Audit (BL), Engine Work (EW), Engagement (EN), Research (RE), Content Production (CP), Integration (IN), Maintenance (MT). Classification takes 60 seconds maximum. - Produces a disk-persisted run plan with 5 layers: classification, depth/scope, skill chain (forced invocation order), hardened criteria, and execution log. The run plan IS the session state for a piece of work. - Forces skill invocation at every transition. Without this, the LLM defaults to “just do the thing” and skips depth governance, quality checks, and structured findings. This is the forcing function.

Invokes: depth-governor, market-scanner, research-engine, findings-formatter, campaign-builder, lead-builder, qa-pipeline, output-self-test, render-validate, adversarial-evaluator, section-construction, content-updater, audit-logging (any skill needed by the chain)

Invoked by: session-orchestrator (hands off to phase-controller after routing), eos-assistant (in production mode)

session-orchestrator¶

One-liner: Orient the OS at session start. Detects phase, loads tiered context, shows engine states, routes by intent.

Triggers: Beginning of every session. /start-session.

Allowed tools: Read, Write, Edit, Glob, Grep, Skill

Key behaviors: - Multi-user check (dormant until profiles exist), phase detection (fresh install vs. existing operator), context staleness alerts (7-day warning, 14-day escalation). - Four-tier context loading: Tier 1 always (CONTEXT.md, PROFILE.md, capabilities), Tier 2 phase-hinted (active engine context, recent intelligence), Tier 3 on-demand (skill content, engine methodology), Tier 4 reference (intelligence log, patterns, methodology docs). - Dashboard shows engine states, active run plans, recent activity, and recent intelligence. Triggers: “QA this”, “check before sending”, “is this ready?”, “verify quality”, “review before delivery”, or as part of a phase-controller skill chain.

Key behaviors: - Four stages run sequentially: Stage 1 (Programmatic Checks – citation gaps, marketing language, cross-document inconsistencies), Stage 2 (Binary Self-Tests from output-self-test), Stage 3 (Visual Verification via Puppeteer for HTML outputs), Stage 4 (Domain-Specific Standards). - Depth classification governs scope: Quick (5 min, internal), Standard (15 min, external client), Comprehensive (30+ min, high-stakes delivery). - Composited from four source engines: MLR programmatic QA, ODC editorial standards, JSE binary self-tests, SEE quality patterns.

Invokes: output-self-test (Stage 2), render-validate (Stage 3, for HTML outputs), adversarial-evaluator (can be a stage)

output-self-test¶

One-liner: Run binary self-tests against output before declaring it complete. Yes/no questions, not judgment calls.

Triggers: About to say “done”, “complete”, “ready for review”. Invoked when finishing any research, content production, integration output, or deliverable.

Allowed tools: Read, Glob, Grep

Key behaviors: - Binary test design rules: answerable YES/NO in under 5 seconds, references specific parts of the output, a NO implies a specific fix, paired quick/thorough versions for scan vs. deep-dive depth. - Test sets selected by output type: Research Output Tests, Content/Deliverable Tests, HTML Output Tests, Integration Output Tests, plus Cross-Cutting Tests that always run. - Read-only governance skill. Cannot modify files. Diagnoses; does not fix.

Invokes: None (read-only)

Invoked by: qa-pipeline (Stage 2), phase-controller (via skill chain), findings-formatter (self-test step)

sanity-check¶

One-liner: Quick scan for 11 known failure modes at natural pause points. A pulse check, not a gate.

Triggers: “sanity check this”, something feels off, after producing a large chunk of work, natural pause points between phases.

Allowed tools: Read, Glob, Grep

Key behaviors: - 11 binary tests against known failure modes: Premature Confidence, Staleness Blindness, Scope Ratchet, Generic Output, Claim Hallucination, Missing Source Trail, Contradictory Frame, Agent Hallucinated Success, Depth Miscalibration, Cross-Engine Contamination, Unverified State Claim. - Should take under 2 minutes. If it takes longer, you’re overthinking it. Lightweight by design – not a substitute for qa-pipeline. - Three-step workflow: scan current work, run binary test for suspected matches, act (fix if straightforward, flag for operator if unclear).

Invokes: None (read-only)

Invoked by: eos-assistant (complementary spot-checks), phase-controller (periodic invocation during long operations)

content-updater¶

One-liner: Choke point for all content updates. Routes updates through origin-skill audit requirements, logs with user attribution, cascades to related files.

Triggers: “update [entity]”, “status change”, “new development”, any modification to profiles, KB files, patterns, or tracked content. Key signal words: update, change, new development, refresh, status change.

Allowed tools: Read, Write, Edit, Glob, Grep, Skill

Key behaviors: - Four-phase workflow: Phase 0 (check logs for prior context), Phase 1 (identify content type and load origin skill’s audit requirements), Phase 2 (execute the update, cascade to related files), Phase 3 (mandatory audit logging with user attribution). - Origin-skill delegation: reads the originating skill’s “Audit Requirements” section and executes those requirements. This is how skill-specific audit discipline is enforced on ad-hoc updates. - User attribution always present. Single-operator mode uses operator name from PROFILE.md; multi-user mode supports “Mike (drafted for Sarah)” attribution.

Invokes: audit-logging (always), origin skill’s audit requirements (loaded dynamically)

Invoked by: campaign-builder, transcript-processor, profile-builder, attio-ops, attio-qualify, attio-refiner, and any skill that modifies tracked content

audit-logging¶

One-liner: Two-layer audit system. Layer 1 (Activity Log) captures breadcrumb trails of all file operations. Layer 2 (Intelligence Log) captures strategic moments with engine tagging.

Triggers: Invoked to understand logging requirements, record strategic insights, or check logs before starting work.

Allowed tools: Read, Write, Edit, Glob, Grep

Key behaviors: - Layer 1 (Activity Log at logs/activity-log.md): always on, records every file operation with user attribution and engine tagging. Action types: Created, Updated, Deleted, Invoked, Researched. - Layer 2 (Intelligence Log at logs/intelligence-log.md): selective, records insights that would change how you approach similar work. Nine categories from Strategy Shift to Methodology Learning. - Pre-work log check protocol: before starting work that continues a thread, scan both logs for recent entries in the relevant engine and category. This is how institutional memory survives context compaction.

Invokes: None

Invoked by: Every skill in EngineOS. All skills must append to the activity log after completing work and selectively log to the intelligence log when trigger conditions are met.

adversarial-evaluator¶

One-liner: Spawn an independent evaluator subagent to adversarially score deliverables against structured criteria. The evaluator has no access to the executor’s context.

Triggers: After producing any research document, engagement deliverable, or content piece. As a step in a phase-controller skill chain. When the operator requests “evaluate this” or “score this against criteria.”

Allowed tools: Read, Bash, Glob, Grep

Key behaviors: - Dispatches a subagent with independent context. The subagent receives only deliverable paths, criteria JSON, pass threshold, and a one-line task description. No conversation history, no run plan. - Tool asymmetry: subagent has Read, Bash, Glob, Grep but NOT Write or Edit. It diagnoses; it cannot fix. This prevents the evaluator from silently patching issues instead of reporting them. - Mechanical distrust: the invoking agent recalculates pass/fail from individual criterion scores, never trusting the evaluator’s self-reported summary. Parse failure is treated as evaluation failure (all-zero scores, HARD FAIL).

Invokes: None (dispatches a subagent, does not invoke other skills)

Invoked by: phase-controller (as evaluation step in skill chains), qa-pipeline (can be a stage)

eos-assistant¶

One-liner: EngineOS-aware conversational partner. Knows the system cold – current state, engine health, methodology, patterns, connections, history.

Conversational after these reads. - Eight behavioral directives encoding how an intelligent partner actually operated across the system: know the system not just the task, push back with evidence, surface staleness with a throttle, think in the operator’s decision framework, separate interesting from actionable, challenge framing before it propagates, treat second occurrences as patterns, persist corrections as feedback memories.

Invokes: phase-controller (in production mode), any skill via on-demand loading based on conversation topic

Invoked by: Manual invocation only. Not invoked by other skills.

Cross-Category Notes¶

Several skills appear in multiple categories by nature of their function:

  • framework-explainer is primarily a Content and Deliverable Production skill (it generates interactive HTML) but also serves Research and Intelligence (it explains complex systems and can include competitive positioning research).
  • codebase-onboarder is primarily Research and Intelligence (it audits and analyzes codebases) but also serves a Meta function (it sets up the context infrastructure for any new repository).
  • research-engine is primarily Research and Intelligence (it routes research requests) but also serves a Meta function (it orchestrates across multiple OS capabilities via the registry).

  +----+----+----+

Content-updater and audit-logging sit beneath everything as cross-cutting infrastructure that all other skills invoke.
