EngineOS — System Overview¶

EngineOS is a two-layer operating system for professional work, built on Claude Code. Layer 1 is the OS: shared skills, methodology, patterns, enforcement rules, operator identity, and a design system. Layer 2 is the engines: domain-specific tenants that inherit OS capabilities and keep their own engagement data, knowledge bases, and domain-adapted workflows.

It is not a prompt library. It is not a collection of Claude Code skills taped together. It is an operating system with mechanical enforcement, adversarial quality evaluation, disk-persisted governance, and a methodology layer distilled from 105+ days of production work across 11 projects.

EngineOS is operator-agnostic. The operator/ directory personalizes the system at runtime through a structured 37-question intake process. The OS and its engines work for anyone; nothing assumes a specific person until operator/PROFILE.md exists.

Five Operating Principles¶

These are not aspirational. They describe how EngineOS was built and how it operates.

  1. Research-First — No deliverable begins without research. Hypotheses are tested, not assumed. If training data says X but current research says Y, trust the research.

  2. Discover-Assess-Decide-Execute-Verify — The universal workflow. Skipping stages (especially discover and verify) is the most common failure mode. The phase-controller enforces this through forced skill chains.

  3. Context-as-Session-State — CONTEXT.md is the handoff mechanism between sessions. It is always current. Every session reads it on start and updates it at end.

  4. Never-Delete, Mark Outdated — Content is never deleted. Outdated content is marked with date and reason. The history has value. Logs are append-only.

  5. Constitution-from-Reality — Build first, describe last. When the system and the documentation disagree, the system is right and the documentation needs updating. This file, and CLAUDE.md itself, were written after the system was built.

Provenance¶

EngineOS was not designed top-down. It was built from a three-act ecosystem audit (March 2026):

  • Act 1 mapped the ecosystem structure across 11 projects on the operator’s Desktop.
  • Act 2 read every line of every file across those 11 projects. 89 finding files and 7 cross-cutting analyses.
  • Act 3 built EngineOS from that evidence, using a “best-version-wins” compositing methodology — the strongest version of each capability was traced to its source via skill genealogy.

The primary donors: SEE (operator identity, CRM integration, engagement workflows), JSE (governance stack, phase control, depth governance), ODC (methodology layer, editorial standards), WondaKB (multi-user architecture, Notion integration), MLR (QA pipeline, enterprise CSS), Restaurant (transcript innovations).

The audit evidence lives at ~/Desktop/ecosystem-audit-act-2/findings/. The build record is at ~/Desktop/ecosystem-audit-act-3/docs/build-log.md.

The substrate has continued to evolve since the initial build: a substrate-tightening operation (D25, April 2026) tested the governance stack against real failures and added the evidence-first-reporting rule plus sanity-check #11; a re-lift audit (D26) restored capabilities missed by the initial Act 3 pass; and the second-brain capture+retrieval layer (D29-D32, June 2026) added marathon-session capture caps with a shared hook module, retry+observability infrastructure, and a three-layer retrieval architecture (SessionStart injection, UserPromptSubmit mid-work hook, manual /recall escalation) over a six-surface corpus. See Second Brain for the retrieval and capture pipeline.

What This Documentation Is Not¶

This documentation explains EngineOS to humans. It does not replace the operational files that serve the system at runtime:

  • CLAUDE.md is the routing layer and constitution — it tells Claude Code how to behave. This doc explains what CLAUDE.md does.
  • CONTEXT.md tracks current state for session continuity. This doc explains why that matters.
  • Skill SKILL.md files contain behavioral rules for execution. This doc explains the skill system.
  • Methodology docs are immutable reference material. This doc summarizes what they contain.

If you’re looking for operational files, see the File Map above. If you’re trying to understand the system, keep reading these docs.
