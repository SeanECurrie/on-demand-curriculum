Architecture — Two-Layer Model and Context Engineering¶

EngineOS is structured as two distinct layers with a context engineering system that controls how much of the system loads into Claude Code’s context window at any given time. This architecture was a deliberate design decision (D11) that reduced context consumption by 68% compared to the original Sales Enablement Engine’s load-everything approach.

The Two-Layer Model¶

  EngineOS (Layer 1 — the OS)
  ┌──────────────────────────────────────────────────────┐
  │  29 Skills  │  15 Methodology  │  70 Patterns        │
  │  7 Rules    │  8 Hooks         │  5 Principles        │

  │ Job      │ │ Job      │ │ On-Demand  │ │ Sales    │
  │ Search   │ │ Search   │ │ Curriculum │ │ Enable-  │
  │ (Sean)   │ │ (Arnett) │ │            │ │ ment     │

Layer 1 (the OS) contains everything that generalizes across domains: skills, methodology, patterns, enforcement rules, operator identity, and the design system. When a capability is useful to more than one engine, it lives here.

Layer 2 (the engines) contains domain-specific tenants. Each engine inherits the full OS capability set and adds its own domain skills, engagement data, knowledge bases, and workflows. Engines are peers to each other, not to the OS.

The inheritance rule: If an engine needs a capability that lives at Layer 1, it references the OS version. It does not duplicate it. If an engine has a domain-specific variant that genuinely differs, it keeps that variant locally and documents why it diverges.

This separation means the OS can evolve without breaking engines, and engines can specialize without polluting the OS. See Engine Model for the full tenant architecture.

Four-Tier Context Engineering¶

Context engineering is the core architectural problem for any system built on an LLM. Claude Code has a finite context window. EngineOS has 29 skills (some over 700 lines), 15 methodology docs, 70 patterns, 38 templates, and extensive operator identity files. Loading everything at once would consume the entire window before any work begins.

EngineOS solves this with a four-tier loading model that keeps context consumption proportional to the work being done.

Tier 1: Always Present¶

Loads: Every session, unconditionally.

File Purpose Why Always-Present
CLAUDE.md Constitution and routing layer Defines core behaviors, enforcement architecture, system structure. Survives compaction because it’s always re-read.
.claude/rules/governance-baseline.md 6 non-negotiable behaviors Research before agreeing, push back with evidence, write as you go, never delete, constitution from reality, govern before producing.
.claude/rules/logging.md Two-layer logging specification Every session needs to know how to log. Activity log (always) + intelligence log (selective).
.claude/rules/evidence-first-reporting.md Verify state before claiming Prevents wrong state claims from propagating into downstream work. Motivated by a real incident.

These files have no paths: key in their YAML frontmatter, which signals Claude Code to load them unconditionally. They represent approximately 340 lines of always-present context.

Compaction resilience: When Claude Code compacts the context window, the post-compact.sh hook fires and re-injects the core governance behaviors as plain text. CLAUDE.md is re-read on the next interaction. The always-present tier is designed to survive compaction without information loss.

Tier 2: Path-Triggered¶

Loads: Automatically when Claude Code reads files matching specific path patterns.

Rule Trigger Path What It Governs
engagement-structure.md engines/*/engagements/**, engines/*/knowledge/** Knowledge base provenance, engagement conventions
integrations.md **/integrations/** CRM/Notion safety rules, batch discipline, credential handling
living-projects.md engines/*/projects/** Required project files (README, CONTEXT, DECISIONS)
methodology-immutable.md methodology/** Immutability protection for methodology docs

The loading is automatic based on Claude Code’s native rule system. The paths: array in each rule’s YAML frontmatter is the control mechanism:

---
description: Integration safety rules for CRM, Notion, and MCP tool operations.
paths:
  - "**/integrations/**"
---

When a session never touches integration files, the integration rules never load. This is zero-cost context when not needed.

Tier 3: Skill-Invoked¶

Loads: Skill descriptions load passively at session start (~2% of context budget). Full skill content loads only when a skill is actually invoked.

EngineOS has 29 skills at .claude/skills/. Each skill has a SKILL.md file with YAML frontmatter containing a description field. Claude Code reads these descriptions at session start for discovery purposes — so it knows what skills exist and when to suggest them.

The full SKILL.md content (which can be substantial — phase-controller is 739 lines, attio-optimizer is over 500) only enters context when the skill is invoked. This means a session that uses 3 skills loads 3 skills, not 29.

Example frontmatter showing the two key fields:

---
description: >
  The run controller for all substantive EngineOS work. Classifies the operation,
  builds a disk-persisted run plan with hardened criteria, forces skill invocation
  at every transition, and gates on operator approval before execution begins.
allowed-tools: Read, Write, Edit, Glob, Grep, Skill
---

The allowed-tools field restricts what tools a skill can use when invoked. See Skill System for the full access control model.

Tier 4: Explicit Reference¶

Loads: Only when a skill or the operator explicitly requests it. Never loaded preemptively.

Content Location When Loaded
Methodology docs (15) methodology/ When a skill chain includes a methodology load step (e.g., BL chains mandate ecosystem-build.md)
Patterns (64) patterns/ When sanity-check detects a failure mode, or when analyzing a specific incident
Templates (38) templates/ When producing a deliverable or setting up an engagement
Operator identity operator/ When personalizing output or during Phase 0 onboarding
Design system (6) design-system/ When producing HTML outputs
Intelligence log logs/intelligence-log.md When session-orchestrator surfaces recent insights

This tier contains the bulk of EngineOS’s content by volume. By loading it only on demand, the system can maintain a large knowledge base without paying a constant context cost.

The Context Budget in Practice¶

A typical session might load: - Tier 1: ~340 lines (always) - Tier 2: 1-2 rules (~80 lines) if working in a matching path - Tier 3: 2-4 skill descriptions passively + 2-4 full skills on invocation (~600-1,200 lines) - Tier 4: 1-3 methodology docs if the skill chain requires them (~300-900 lines)

Total: ~1,300-2,500 lines of EngineOS context, leaving the majority of the window for actual work content.

Compare this to the SEE’s original approach: load all 49 skills, all patterns, all templates at session start. That’s why D11 (four-tier context budget) was one of the founding architectural decisions — it made the system viable.

Retrieval Architecture¶

The four-tier context model controls what loads into the window. The retrieval architecture controls how the system finds prior context inside its own corpus mid-work. The two are peers: the context budget is the write-side (what enters context); retrieval is the read-side (what gets found and surfaced).

EngineOS captures heavily — 216+ knowledge base articles, 70+ intelligence log entries, daily session arcs, run plans, methodology docs. Capture without retrieval is a write-only system. Until 2026-06-04, that’s what EngineOS was: a marathon-arc audit showed zero reads of knowledge/concepts/*.md across ~30 hours of substantive work. D32 (second-brain retrieval layer) closed the gap with three layers over a six-surface corpus.

Three Retrieval Layers¶

Layer Mechanism Fires when Coverage target
1. Session-start injection hooks/session-start.py Every session start Orientation — full KB index + last 30 lines of today’s daily log injected once at ~20K cap
2. Mid-work retrieval hook hooks/prompt-retrieval.py (UserPromptSubmit) Every prompt matching the heuristic gate ~90% — silent, mechanical, ≤1024 chars, ≤1s, top-3 matches from the six-surface corpus
3. Manual escalation .claude/skills/recall/ (/recall <query>) Operator or agent invocation when hook missed or deeper sweep needed ~10% — explicit, ranked, no cap

Layer 1 establishes orientation. Layer 2 fills in mid-work context mechanically before the prompt reaches Tier 3 skill loading. Layer 3 escalates when the hook misses or the decision is load-bearing.

Six-Surface Priority Corpus¶

All three layers read the same corpus in the same priority order: logs/intelligence-log.md → knowledge/index.md → knowledge/concepts/*.md + connections/*.md → daily/*.md (last 30d) → run-plans/*.md (last 60d) → methodology/*.md. Higher surfaces have higher signal-to-noise. Stopping rule: when surfaces 1-2 yield 3+ strong hits, lower surfaces aren’t swept.

Why No Vector DB¶

At personal-KB scale (<500 articles, currently 216), structured markdown index + ripgrep + LLM-reads-relevant-files outperforms vector retrieval on precision and is dramatically simpler. Pure Read/Grep/Glob — zero API cost. The Phase C vector layer is deferred with explicit revisit conditions in D32 (KB exceeds 2000 articles, or hook gate hit rate sustained >60% with useful injections, or semantic misses grep can’t surface).

Measurement Built In¶

scripts/retrieval-health.jsonl is append-only, one record per UserPromptSubmit invocation (gate fire, query terms, surfaces searched, chars injected, exec time). The operator runs scripts/retrieval-review.py after ~10 sessions to make the keep/tune/kill decision. Healthy band: gate hit rate 10-60%.

See Second Brain for the full capture-plus-retrieval pipeline (flush.py, compile.py, knowledge/, daily/, health logs, decision rules). This section is the architectural slot; the deep reference is one click away.

32 capabilities with stable identifiers, current file locations, and source engines. When a skill or file moves, the registry is updated — all references resolve through it.

| Identifier            | Capability                    | Current Location             | Source    |

The registry uses IDs-only reach (D4 from methodology/memory-architecture.md): it stores identifiers and pointers, not content. This keeps it minimal and reduces drift risk.

Compaction Resilience¶

Claude Code compacts older context when the window fills. EngineOS is designed for this. Eight hook events are wired in .claude/settings.json — four shell hooks govern writes and post-compact recovery; four Python hooks handle session-start orientation, session-arc capture, pre-compact flushing, and mid-work retrieval.

The eight wired hook events:

Hook Script What it does
PreToolUse (Write|Edit) pre-write-governance.sh Blocks deliverable writes without an active run plan (scope-matched per D22)
PostToolUse (Write|Edit) post-tool-use.sh Mechanical activity logging (every Write/Edit appended to logs/activity-log.md)
Stop stop.sh Session-end CONTEXT.md check (warns if stale)
PostCompact post-compact.sh Re-injects core governance behaviors, active run plan awareness, current engine tenant list after compaction
SessionStart session-start.py Retrieval Layer 1 — injects full KB index + last 30 lines of today’s daily log (~20K cap) for orientation
PreCompact pre-compact.py Captures the about-to-compact session arc to today’s daily log via flush.py (shared logic in _flush_common.py per D29)
SessionEnd session-end.py Captures session arc to daily log at session close (same flush.py spawn, same shared module)
UserPromptSubmit prompt-retrieval.py Retrieval Layer 2 — heuristic-gated injection of top matches from the six-surface corpus (≤1024 chars, ≤1s)

How compaction is survived:

  1. PostCompact hook fires after every compaction and re-injects the 6 core governance behaviors as plain text, active run plan awareness (recent .md files in run-plans directories), and the current engine tenant list. CLAUDE.md is re-read on the next interaction.

  2. PreCompact hook fires before the compaction lands and flushes the session arc to daily/<today>.md via flush.py. This means the conversation history that’s about to be lost from the window has already been written to disk — recovery doesn’t depend on PostCompact re-injection alone. The shared _flush_common.py module (D29) is the single source of truth for capture caps (MAX_TURNS=60, MAX_CONTEXT_CHARS=30_000) across both PreCompact and SessionEnd.

  3. SessionStart hook re-establishes orientation on the post-compaction session by injecting KB index + today’s daily log, restoring retrieval surfaces that compaction stripped.

  4. Disk-persisted run plans are the primary recovery mechanism for in-flight operations. If context compacts mid-operation: - Session-orchestrator reads CONTEXT.md (knows what’s active) - Checks for run plan at the canonical path - The run plan shows what’s been done (populated layers) and what’s next - Execution resumes from the last completed step

  5. CONTEXT.md is always current (the Stop hook warns if it wasn’t updated). It’s the handoff mechanism between compaction boundaries, just as it is between sessions.

  6. Tier 1 files (CLAUDE.md + 3 unconditional rules) are re-read on every interaction after compaction, ensuring the system’s core identity is never permanently lost.

  7. Health observability — scripts/hook-health.jsonl (per-flush record) and scripts/retrieval-health.jsonl (per-retrieval record) are append-only logs reviewed via health-review.py / retrieval-review.py. If a hook starts failing silently, the operator sees it in the next review pass (D30).

The design principle: anything that must survive compaction lives on disk at a predictable path. The context window is a working space, not a storage system.

Key Architectural Decisions¶

Decision What Why
D6 Two-layer architecture (OS + tenants) Capabilities that generalize go to Layer 1; domain specifics stay in Layer 2. Prevents duplication.
D11 Four-tier context budget 68% context reduction vs. loading everything. Made the system viable.
D12 CLAUDE.md as routing layer, not reference manual 155-line constitution pointing to detail. ODC’s concise approach outperformed SEE’s 918-line inventory.
D14 Hooks as enforcement enhancement Mechanical enforcement for deterministic operations (logging, run plan checking). Advisory for semantic judgment.
D22 PreToolUse mechanical gate Advisory governance fails on confident agents. The hook blocks writes without a run plan — makes skipping harder than complying.
D25 Substrate tightening — state integrity + cowork internalization Fixed control-plane drift (CLAUDE.md vs CONTEXT.md vs disk), scope-matched hook governance, evidence-first-reporting unconditional rule, plus 4 new patterns from forensic cowork analysis. Tracks 1 (state) and 2 (discipline) reinforce each other.
D28 Root-only logs with engine tags One logging location, engine column on every entry. Simpler than per-engine logs.
D29 Marathon-session capture caps + shared hook module Bumped flush caps to MAX_TURNS=60 / MAX_CONTEXT_CHARS=30_000 and extracted _flush_common.py so cap changes propagate to both SessionEnd and PreCompact. Anti-drift via shared module.
D32 Second-brain retrieval layer (hooks + skill, no vector DB) Three layers (SessionStart injection, UserPromptSubmit hook, /recall manual escalation) over a six-surface corpus. Closes the capture-without-retrieval gap. Pure Read/Grep/Glob beats vector retrieval at <500-article scale.
