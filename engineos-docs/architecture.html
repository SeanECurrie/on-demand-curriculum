EngineOS System Documentation · Section 02 · Built 2026-07-10

Architecture

EngineOS is structured as two distinct layers with a context engineering system that controls how much of the system loads into Claude Code's context window at any given time. This architecture was a deliberate design decision (D11) that reduced context consumption by 68% compared to the original Sales Enablement Engin

The Two-Layer Model¶

EngineOS splits into two layers so the shared substrate stays single-version while domain work stays isolated.

Layer 1 is the OS. Skills, methodology, patterns, design system, enforcement rules, operator identity — everything that generalizes across domains. When a capability is useful to more than one engine, it lives here.

Layer 2 is the engines. Domain-specific tenants (job search, sales enablement, on-demand curriculum) inherit the full Layer 1 capability set and add their own domain skills, engagement data, knowledge bases, and workflows. Engines are peers to each other, not to the OS.

The inheritance rule: if an engine needs a Layer 1 capability, it references the OS version. It does not duplicate it. If an engine genuinely needs a variant, it keeps that variant locally and documents why it diverges. So a fix to the OS propagates everywhere; an engine-specific need stays local. See Engine Model for the full tenant architecture.

Four-Tier Context Engineering¶

Context engineering is the core architectural problem for any system built on an LLM. Claude Code has a finite context window. EngineOS has 38 skills (some over 700 lines), 24 methodology docs, 88 patterns, 38 templates, and extensive operator identity files. Loading everything at once would consume the entire window before any work begins.

EngineOS solves this with four tiers that load proportionally to the work — always-present constitution (Tier 1), path-triggered rules (Tier 2), skill descriptions discovered at start but full content only on invocation (Tier 3), and explicit-reference content loaded by skills or operator on demand (Tier 4). A typical session uses ~1,300–2,500 lines of EngineOS context, leaving the majority of the window for actual work content. Compare that to the SEE’s original approach of loading all 49 skills, all patterns, all templates at session start — D11 (four-tier budget) was a founding architectural decision that made the system viable.

Tier 1: Always Present¶

Loads: Every session, unconditionally.

File Purpose Why Always-Present
CLAUDE.md Constitution and routing layer Defines core behaviors, enforcement architecture, system structure. Survives compaction because it’s always re-read.
.claude/rules/governance-baseline.md 6 non-negotiable behaviors Research before agreeing, push back with evidence, write as you go, never delete, constitution from reality, govern before producing.
.claude/rules/logging.md Two-layer logging specification Every session needs to know how to log. Activity log (always) + intelligence log (selective).
.claude/rules/evidence-first-reporting.md Verify state before claiming Prevents wrong state claims from propagating into downstream work. Motivated by a real incident.

These files have no paths: key in their YAML frontmatter, which signals Claude Code to load them unconditionally. They represent approximately 340 lines of always-present context.

Compaction resilience: When Claude Code compacts the context window, the post-compact.sh hook fires and re-injects the core governance behaviors as plain text. CLAUDE.md is re-read on the next interaction. The always-present tier is designed to survive compaction without information loss.

Tier 2: Path-Triggered¶

Loads: Automatically when Claude Code reads files matching specific path patterns.

Rule Trigger Path What It Governs
engagement-structure.md engines/*/engagements/**, engines/*/knowledge/** Knowledge base provenance, engagement conventions
integrations.md **/integrations/** CRM/Notion safety rules, batch discipline, credential handling
living-projects.md engines/*/projects/** Required project files (README, CONTEXT, DECISIONS)
methodology-immutable.md methodology/** Immutability protection for methodology docs
sandbox-tier.md sandbox/** Posture for the personal tier (D44): personal/for-fun, firewalled from the professional layer, promotion path to Layer 1

The loading is automatic based on Claude Code’s native rule system. The paths: array in each rule’s YAML frontmatter is the control mechanism:

---
description: Integration safety rules for CRM, Notion, and MCP tool operations.
paths:
  - "**/integrations/**"
---

When a session never touches integration files, the integration rules never load. This is zero-cost context when not needed.

Tier 3: Skill-Invoked¶

Loads: Skill descriptions load passively at session start (~2% of context budget). Full skill content loads only when a skill is actually invoked.

EngineOS has 38 skills at .claude/skills/. Each skill has a SKILL.md file with YAML frontmatter containing a description field. Claude Code reads these descriptions at session start for discovery purposes — so it knows what skills exist and when to suggest them.

The full SKILL.md content (which can be substantial — phase-controller is 739 lines, attio-optimizer is over 500) only enters context when the skill is invoked. This means a session that uses 3 skills loads 3 skills, not 38.

Example frontmatter showing the two key fields:

---
description: >
  The run controller for all substantive EngineOS work. Classifies the operation,
  builds a disk-persisted run plan with hardened criteria, forces skill invocation
  at every transition, and gates on operator approval before execution begins.
allowed-tools: Read, Write, Edit, Glob, Grep, Skill
---

The allowed-tools field restricts what tools a skill can use when invoked. See Skill System for the full access control model.

Tier 4: Explicit Reference¶

Loads: Only when a skill or the operator explicitly requests it. Never loaded preemptively.

Content Location When Loaded
Methodology docs (20) methodology/ When a skill chain includes a methodology load step (e.g., BL chains mandate ecosystem-build.md)
Patterns (72) patterns/ When sanity-check detects a failure mode, or when analyzing a specific incident
Templates (38) templates/ When producing a deliverable or setting up an engagement
Operator identity operator/ When personalizing output or during Phase 0 onboarding
Design system (6) design-system/ When producing HTML outputs
Intelligence log logs/intelligence-log.md When session-orchestrator surfaces recent insights

This tier contains the bulk of EngineOS’s content by volume. By loading it only on demand, the system can maintain a large knowledge base without paying a constant context cost.

The Context Budget in Practice¶

A typical session might load: - Tier 1: ~340 lines (always) - Tier 2: 1-2 rules (~80 lines) if working in a matching path - Tier 3: 2-4 skill descriptions passively + 2-4 full skills on invocation (~600-1,200 lines) - Tier 4: 1-3 methodology docs if the skill chain requires them (~300-900 lines)

Total: ~1,300-2,500 lines of EngineOS context, leaving the majority of the window for actual work content.

Compare this to the SEE’s original approach: load all 49 skills, all patterns, all templates at session start. That’s why D11 (four-tier context budget) was one of the founding architectural decisions — it made the system viable.

Retrieval Architecture¶

The four-tier model controls what loads into the window. Retrieval controls what gets found inside the system’s own corpus mid-work. The two are peers: the context budget is the write-side; retrieval is the read-side.

EngineOS captures heavily — 539 knowledge base articles, 311 intelligence log entries, daily session arcs, run plans. Until 2026-06-04, capture-without-retrieval was a write-only system: a marathon-arc audit showed zero reads of knowledge/concepts/*.md across ~30 hours of substantive work. D32 closed the gap with three retrieval layers reading a six-surface corpus, sized for personal-KB scale (grep + markdown index beat vector retrieval on precision at <500 articles).

Three Retrieval Layers¶

Layer Mechanism Fires when Coverage target
1. Session-start injection hooks/session-start.py Every session start Orientation — full KB index + last 30 lines of today’s daily log injected once at ~20K cap
2. Mid-work retrieval hook hooks/prompt-retrieval.py (UserPromptSubmit) Every prompt matching the heuristic gate ~90% — silent, mechanical, ≤1024 chars, ≤1s, top-3 matches from the six-surface corpus
3. Manual escalation .claude/skills/recall/ (/recall <query>) Operator or agent invocation when hook missed or deeper sweep needed ~10% — explicit, ranked, no cap

Layer 1 establishes orientation. Layer 2 fills in mid-work context mechanically before the prompt reaches Tier 3 skill loading. Layer 3 escalates when the hook misses or the decision is load-bearing.

Six-Surface Priority Corpus¶

All three layers read the same corpus in the same priority order: logs/intelligence-log.md → knowledge/index.md → knowledge/concepts/*.md + connections/*.md → daily/*.md (last 30d) → run-plans/*.md (last 60d) → methodology/*.md. Higher surfaces have higher signal-to-noise. Stopping rule: when surfaces 1-2 yield 3+ strong hits, lower surfaces aren’t swept.

Why No Vector DB¶

At personal-KB scale (currently 539 articles, against a <500-article research threshold), structured markdown index + ripgrep + LLM-reads-relevant-files outperforms vector retrieval on precision and is dramatically simpler. Pure Read/Grep/Glob — zero API cost. The original D32 deferral of a vector layer has since been measured rather than assumed: Phase C (D57, 2026-07-03) built an optional on-device hybrid index behind /recall as an escalation, and the recall-eval harness (2026-07-06) then measured it — BM25 (FTS5) beat dense-hybrid fusion at this corpus scale, so D63 flipped the escalation default to pure BM25 and retired the dense path to opt-in (repaired and dependency-pinned, re-measurable as the corpus grows). Grep remains the step-1 default throughout; D32 was never overridden.

Measurement Built In¶

scripts/retrieval-health.jsonl is append-only, one record per UserPromptSubmit invocation (gate fire, query terms, surfaces searched, chars injected, exec time). The operator runs scripts/retrieval-review.py after ~10 sessions to make the keep/tune/kill decision. Healthy band: gate hit rate 10-60%.

See Second Brain for the full capture-plus-retrieval pipeline (flush.py, compile.py, knowledge/, daily/, health logs, decision rules). This section is the architectural slot; the deep reference is one click away.

People Profiling Subsystem¶

People Profiling is a cross-cutting OS subsystem (Layer 1) — a peer to the Second Brain, the governance stack, and the design system, NOT an engine. It profiles the people the operator works with — collaborators, stakeholders, friends, advisors, subjects — so the system stops guessing wrong about who matters and whose judgment counts.

Why it’s a subsystem, not an engine. Engines (Layer 2) are domain tenants serving one line of work. People appear in every domain, so the capability is engine-independent and invokable from anywhere. It was re-lifted from the SEE source on 2026-06-24 after the original compositing left it engine-bound; engine-coupling it again would repeat that incomplete-lift bug. If it ever splits off, it does so as a distributable capability via the fork / cross-operator-distribution pattern — not as an engine.

The six axes. A person is several independent axes, not one rank — collapsing them is how a friend’s offhand take becomes system canon:

Axis Answers Set by Slides?
Tier How much do they matter? (Core / Active / Reference) Operator Sticky
Heat How much are they coming up now? Computed (scripts/people-heat.py) Yes
Influence ⚑ Does their input count as canon? (canon / domain-authority / lessons-only / NOT-canon) Operator Sticky
Value-type What do they bring? (builder/SME/connector/channel/friend/advisor/subject) Operator/observed Slow
Relationship direction Who serves whom? Operator/observed Slow
Sensitivity Capture/share limits (public-professional default) Convention —

Tier ⊥ Heat ⊥ Influence. A Core person can be quiet; an important person’s input can be NOT-canon; high heat can be a research artifact, not a relationship. Influence is a SAFETY axis (important-to-operator ≠ right-for-the-system) — enforced loudly via a caveat block in the profile and prompt-retrieval.py echoing ⚠ NOT-CANON on mention, even by first name.

The mechanism. Two skills — person-profiler (synthesis: build/update a profile to the template) and people-curator (operator-facing curation: triage / feed-intel / adjudicate / inventory). The heat engine scripts/people-heat.py scores activity and surfaces thin-profile candidates at session start; the review dossier scripts/people-dossier.py → people/dossier/index.html is the invokable review-and-adjust surface. registry/people.md is the authoritative index (the six axes per person). The operator is always the gate — the system proposes from evidence; the operator rules.

See Methodology Index for the people-profiling methodology doc and Skills Reference for person-profiler + people-curator. The subsystem front door is people/README.md.

Registry System¶

Registries provide stable identifiers for system components so references survive when files move. When a skill is renamed or a capability is restructured, the registry is updated and every reference resolves through it — no broken cross-links, no need to grep-and-replace across the codebase. The registries store identifiers and pointers, not content (D4 from methodology/memory-architecture.md), which keeps them minimal and drift-resistant. The two structural registries (capabilities, engines) are joined by registry/people.md — the index for the People Profiling subsystem (one row per person, the six axes).

File Structure¶

Every top-level directory has a single, well-defined purpose. The layout is the architecture — read top-down and you can see what kind of thing each piece is and how often it’s expected to change. Rules and methodology are nearly immutable; engines and run-plans churn fast; logs, daily/, and knowledge/ are append-only. This makes mutability legible: if you know where you’re writing, you know what discipline applies.

Compaction Resilience¶

Claude Code compacts older context when the window fills. EngineOS is designed for this — anything that must survive compaction lives on disk at a predictable path, and a layered hook system makes sure disk and context stay in sync. PreCompact captures the about-to-be-lost arc before it disappears; PostCompact re-injects the constitution after the cut; SessionStart re-establishes retrieval on the post-compaction window; CONTEXT.md and run plans are the disk-persistent handoff mechanism. The context window is a working space, not a storage system.

The eight wired hook events:

Hook Script What it does
PreToolUse (Write|Edit) pre-write-governance.sh Blocks deliverable writes without an active run plan (scope-matched per D22)
PostToolUse (Write|Edit) post-tool-use.sh Mechanical activity logging (every Write/Edit appended to logs/activity-log.md)
Stop stop.sh Session-end CONTEXT.md check (warns if stale)
PostCompact post-compact.sh Re-injects core governance behaviors, active run plan awareness, current engine tenant list after compaction
SessionStart session-start.py Retrieval Layer 1 — injects full KB index + last 30 lines of today’s daily log (~20K cap) for orientation
PreCompact pre-compact.py Captures the about-to-compact session arc to today’s daily log via flush.py (shared logic in _flush_common.py per D29)
SessionEnd session-end.py Captures session arc to daily log at session close (same flush.py spawn, same shared module)
UserPromptSubmit prompt-retrieval.py Retrieval Layer 2 — heuristic-gated injection of top matches from the six-surface corpus (≤1024 chars, ≤1s)

How compaction is survived:

  1. PostCompact hook fires after every compaction and re-injects the 6 core governance behaviors as plain text, active run plan awareness (recent .md files in run-plans directories), and the current engine tenant list. CLAUDE.md is re-read on the next interaction.

  2. PreCompact hook fires before the compaction lands and flushes the session arc to daily/<today>.md via flush.py. This means the conversation history that’s about to be lost from the window has already been written to disk — recovery doesn’t depend on PostCompact re-injection alone. The shared _flush_common.py module (D29) is the single source of truth for capture caps (MAX_TURNS=90, MAX_CONTEXT_CHARS=60_000 — bumped stepwise from 30_000 as telemetry kept showing sessions cap-bound, most recently 2026-07-02) across both PreCompact and SessionEnd.

  3. SessionStart hook re-establishes orientation on the post-compaction session by injecting KB index + today’s daily log, restoring retrieval surfaces that compaction stripped.

  4. Disk-persisted run plans are the primary recovery mechanism for in-flight operations. If context compacts mid-operation: - Session-orchestrator reads CONTEXT.md (knows what’s active) - Checks for run plan at the canonical path - The run plan shows what’s been done (populated layers) and what’s next - Execution resumes from the last completed step

  5. CONTEXT.md is always current (the Stop hook warns if it wasn’t updated). It’s the handoff mechanism between compaction boundaries, just as it is between sessions.

  6. Tier 1 files (CLAUDE.md + 3 unconditional rules) are re-read on every interaction after compaction, ensuring the system’s core identity is never permanently lost.

  7. Health observability — scripts/hook-health.jsonl (per-flush record) and scripts/retrieval-health.jsonl (per-retrieval record) are append-only logs reviewed via health-review.py / retrieval-review.py. If a hook starts failing silently, the operator sees it in the next review pass (D30).

The design principle: anything that must survive compaction lives on disk at a predictable path. The context window is a working space, not a storage system.

Key Architectural Decisions¶

Decision What Why
D6 Two-layer architecture (OS + tenants) Capabilities that generalize go to Layer 1; domain specifics stay in Layer 2. Prevents duplication.
D11 Four-tier context budget 68% context reduction vs. loading everything. Made the system viable.
D12 CLAUDE.md as routing layer, not reference manual 155-line constitution pointing to detail. ODC’s concise approach outperformed SEE’s 918-line inventory.
D14 Hooks as enforcement enhancement Mechanical enforcement for deterministic operations (logging, run plan checking). Advisory for semantic judgment.
D22 PreToolUse mechanical gate Advisory governance fails on confident agents. The hook blocks writes without a run plan — makes skipping harder than complying.
D25 Substrate tightening — state integrity + cowork internalization Fixed control-plane drift (CLAUDE.md vs CONTEXT.md vs disk), scope-matched hook governance, evidence-first-reporting unconditional rule, plus 4 new patterns from forensic cowork analysis. Tracks 1 (state) and 2 (discipline) reinforce each other.
D28 Root-only logs with engine tags One logging location, engine column on every entry. Simpler than per-engine logs.
D29 Marathon-session capture caps + shared hook module Extracted _flush_common.py so flush-cap changes propagate to both SessionEnd and PreCompact (caps since bumped stepwise to MAX_TURNS=90 / MAX_CONTEXT_CHARS=60_000 as telemetry demanded). Anti-drift via shared module.
D32 Second-brain retrieval layer (hooks + skill, no vector DB) Three layers (SessionStart injection, UserPromptSubmit hook, /recall manual escalation) over a six-surface corpus. Closes the capture-without-retrieval gap. Pure Read/Grep/Glob beats vector retrieval at <500-article scale.
D44 The personal sandbox/ tier A third top-level tier (sibling to engines/ + projects/) for personal/for-fun work — firewalled from the professional layer, own posture rule, and a promotion path to Layer 1 (first exercised by D45: epistemic-tagging + tone-firewall).
D50 Session-entry posture: the Full-Breadth Start The session-orchestrator natively owns capability self-orientation — on a full-breadth opener it self-updates from scripts/capability-snapshot.json (counts derived live) and STANDS READY without guessing the work. Backed by behavior 7.6 and the SessionStart surface.
D51 Second-brain health process kb-health composes live KB stats + graph health + pipeline vital signs into one fireable report; kb-stats becomes the single source for any “by the numbers” claim — hand-typed health numbers are the rot class it closes.
D52 Census single-sourcing + the living health dashboard Docs counts become {{CENSUS:key}} tokens resolved from live disk at build time (hand-typed censuses linted); docs/site/dashboard.html composes every health surface into a status strip + heartbeat tiles + the observability inventory — standing audit practice, refreshed at session end.
D53 Usage economy — disciplines + the instrument’s economy lens Session cost ≈ context-size × turn-count (mostly cache reads re-paid each turn); the usage log gains an economy view (tokens/turn, ctx/turn context-floor, cache-hit%) in usage-review.py + a dashboard tile. Correctness-neutral levers — fewer/denser turns, protect the cache, model+effort to task, sequential-near-limit — plus disabling two never-invoked plugin packs (enabledPlugins:false) for context economy.
D54 Retire the usage-log’s engaged-vs-cold headline At a degenerate 26:1 engaged:cold ratio the comparison had no baseline; usage-review.py now leads with the economy lens and auto-suppresses the comparison until a real cold baseline accumulates (self-healing, never-delete).
D58 KB index becomes a derived artifact knowledge/index.md is generated from article frontmatter by every producer (including failure paths) — the index-desync class made impossible by construction, the same derived-over-hand-typed move as D52’s census tokens.
D62/D64 The EngineOS Console — read-only live cockpit A localhost governance console over the existing instrument estate, architected as a consumer, not a producer: it reads every surface (decision queue, vitals, transcripts, the KB graph) and executes nothing ungoverned. Command-deck intents queue as JSON records for the governed session to pick up; direct headless execution is deliberately absent.
D63 Retrieval escalation defaults to BM25; dense retired The recall-eval harness measured pure FTS5 beating dense-hybrid fusion at current corpus scale (Success@10 0.821 vs 0.786), so the /recall escalation runs BM25 and the dense path is opt-in — the long-deferred vector question settled by measurement, not intuition.
