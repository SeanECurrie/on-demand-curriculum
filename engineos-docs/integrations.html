Integrations

EngineOS integrates with external systems through a layered architecture: MCP (Model Context Protocol) servers provide tool-level access, skills encode domain logic and workflow orchestration, and direct API scripts handle operations where MCP falls short. Seven skills and a Node.js utility suite cover the two primary integration domains – Attio CRM and Notion.

Integration Philosophy¶

Three principles govern how EngineOS connects to external systems.

Domain-scoped MCP access. Every skill declares an allowed-tools frontmatter block that restricts which MCP tools it can invoke. An integration skill gets its domain-specific MCP tools and nothing else. A research skill gets Bright Data and Context7. A governance skill gets no MCP access at all – read-only filesystem tools only. This prevents cross-domain tool bleed and makes each skill’s external surface area inspectable from its frontmatter.

Safety rules from .claude/rules/integrations.md. Four rules apply to all integration work: - Verify a single record before running batch operations. - Check the Attio playbook for known MCP bugs before operations. - Log all integration operations to the activity log with the tool name. - Credentials via environment variables (Attio) or engine-level config files (Notion) – never hardcoded, never logged.

The mapper-to-operator-to-executor pipeline. The integration architecture follows a consistent pattern across both domains:

  1. Mapper discovers the external schema and produces a playbook (machine-readable cache + human-readable reference).
  2. Operator-facing skills consume the playbook to audit, classify, or refine – producing analysis and approved action plans.
  3. Write skills execute approved operations against the external system.

No write skill runs without a playbook from the mapper. No bulk mutation runs without operator approval. The mapper is the foundation; everything downstream depends on it.

Attio CRM Suite (5 Skills)¶

The Pipeline¶

attio-mapper ──> attio-optimizer ──> attio-refiner ──> attio-ops
  (schemas)        (audit)            (decisions)       (execution)
                                          ^
                                          |
                                   Operator context
                                   Institutional knowledge

attio-mapper ──> attio-qualify
  (schemas)      (ICP classification)

The pipeline has two branches. The audit branch (mapper -> optimizer -> refiner -> ops) handles CRM health: audit the data, refine findings with operator context, execute approved fixes. The enrichment branch (mapper -> qualify) handles ICP classification: match contacts against persona definitions using configurable keyword scoring.

Both branches share the mapper’s schema cache. Both require operator approval before mutations. Both produce logged, auditable output.

Individual Skills¶

attio-mapper – Schema Discovery and Caching¶

What it does: Dynamically discovers all objects in an Attio workspace (standard and custom), fetches full attribute metadata, applies type inference corrections for known MCP bugs, and generates both machine-readable JSON schemas and a human-readable playbook. Every other Attio skill reads from this cache.

When to invoke: - First-time Attio setup for an engine - “Map this Attio workspace” / “refresh Attio schemas” - Before heavy Attio operations (ensures schemas are current) - After custom objects or fields are added in Attio - When _meta.json shows last map > 30 days ago

Key behaviors: - Dynamic object discovery via GET /v2/objects – never hardcodes object names. Custom objects are discovered automatically. - MCP bug detection: compares MCP-reported types against direct API types and annotates discrepancies. Fixes ~44% of “unknown” types on companies. - Three-phase operation: Discovery (fetch and cache), Change Detection (diff against previous schemas), Pattern Learning (log notable workspace patterns).

MCP tools used: - mcp__attio-mcp__records_get_attributes – attribute list for standard objects

Direct API calls: GET /v2/objects, GET /v2/objects/{slug}/attributes, GET /v2/objects/{slug}/attributes/{attribute_slug}/options

Output location: engines/<engine>/integrations/attio/schemas/ (JSON schemas, select field options, changelog, metadata) and engines/<engine>/integrations/attio/attio-playbook/ (workspace map, objects reference, known bugs, pitfalls).

attio-optimizer – CRM Health Audit¶

What it does: Four-phase systematic audit: measure current state using intelligent sampling, benchmark against Attio docs and industry best practices via research tools, produce a gap analysis with prioritized action plan, and auto-generate an interactive 7-page HTML presentation suite.

When to invoke: - “Audit the CRM” / “CRM health check” - Before a major initiative that depends on CRM data quality - After large data imports (post-import quality check) - Quarterly maintenance review

Key behaviors: - Intelligent two-layer sampling: Layer A (engine-engaged records – active deals, referenced contacts, renewal targets) and Layer B (broader health assessment – recent records, dormant records, population extremes). Layer A records are what the engine is making decisions from; quality issues there are urgent. - Five audit categories with weighted scoring: Completeness (30%), Accuracy (25%), Pipeline Health (20%), Consistency (15%), Schema Utilization (10%). - Research cache: Bright Data and Context7 research results are cached for 30 days to avoid redundant queries.

MCP tools used: - Attio read tools: records_search, records_search_advanced, records_search_batch, records_search_by_relationship, records_search_by_timeframe, records_get_details, records_get_info, records_get_attributes, records_list, lists_list, lists_get_entries, objects_list_attributes - Research tools: mcp__context7__resolve-library-id, mcp__context7__query-docs, mcp__brightdata__search_engine, mcp__brightdata__search_engine_batch, mcp__brightdata__scrape_as_markdown

Output location: engines/<engine>/integrations/attio/audits/YYYY-MM-DD/ – 6 markdown files (executive summary through field strategy) + 7 HTML pages (CRM object map + 6 deliverable visualizations).

attio-refiner – Operator-Driven Audit Refinement¶

What it does: Takes attio-optimizer output and walks the operator through structured decision-making. The audit is the clean room; the refiner is the war room. It captures institutional knowledge about why data looks the way it does and produces annotated findings plus approved work orders that downstream skills can execute.

When to invoke: - “Refine the audit” / “review CRM findings” - “Approve CRM actions” / “triage the audit actions” - After reviewing the HTML audit presentation

Key behaviors: - Structured Q&A per finding: present audit evidence, ask for operator context (why does this exist?), check priority agreement, collect decision (approve / modify / deprioritize / need more info). - P0 actions get individual review. P1 actions support batch approval with exceptions. P2/P3 actions are batched. - Produces 07-approved-actions.md with execution-ready work orders specifying which downstream skill to use, affected record IDs, and acceptance criteria.

MCP tools used: - Attio read tools: records_search, records_search_advanced, records_search_by_relationship, records_search_by_timeframe, records_get_details, records_get_info, records_list, lists_list, lists_get_entries

Output location: Same audits/YYYY-MM-DD/ directory as the source audit – adds 06-operator-review.md, 07-approved-actions.md, and their HTML visualizations.

attio-ops – CRM Write Operations¶

What it does: Unified write-path skill covering three operational modes: CSV Import (records into People/Companies objects), CSV to List (records into a specific Attio list with entry-level properties), and Bulk List Ops (add/remove/sync/update list membership at scale).

When to invoke: - “Import this CSV into Attio” / “add these contacts” - “Populate the [list name] list” / “import CSV into [list]” - “Sync [list] with this data” / “bulk add to [list]”

Key behaviors: - Domain-first company strategy: extract domains from emails, skip generic domains (gmail, outlook, etc.), search by domain not name, create company with domain only (Attio auto-enriches), rely on automatic person-to-company association. - Three-tier field mapping: explicit (user-provided or CSV format spec), cached (prior mapping decisions), heuristic (confidence scoring with auto-accept at 0.82+, confirm at 0.65+, skip below). - Mandatory pre-import approval gate: presents a full summary of what will be created/updated/skipped and waits for explicit confirmation before any write. - Checkpoint saves for large imports (>50 records): progress saved every 25 records, supports resumption.

MCP tools used: - mcp__attio-mcp__records_search_advanced, records_get_details, records_list, records_create, records_update, records_add_to_list, lists_list, lists_get_entries, objects_list_attributes

Reads approved work orders from: attio-refiner’s 07-approved-actions.md when it specifies attio-ops:csv-import or attio-ops:bulk-list as the execution method.

attio-qualify – ICP Classification and Lead Qualification¶

What it does: Two-mode intelligence skill. Enrich mode: bulk ICP assignment via job title keyword matching with configurable confidence scoring. Qualify mode: cross-reference new signups against CRM data to categorize as existing customer, internal, spam, or new lead (high/medium/personal).

When to invoke: - “Assign ICPs” / “enrich contacts” / “classify leads” - “Qualify these users” / “categorize these signups” - “Generate ICP assignment script” (script-only, no execution)

Key behaviors: - All persona definitions, keywords, weights, thresholds, and domain lists load from icp_definitions.json at runtime. The skill is the algorithm; the engine owns the data. Zero engine-specific content in the skill itself. - Weighted scoring: exact title match (1.0), keyword in title (0.8), keyword in department (0.6), seniority bonus (+0.1). Configurable threshold (default 0.7) – below threshold goes to manual review queue. - Performance optimization: MCP one-by-one takes ~60-90 min for 150 contacts. The skill generates batch curl scripts using the direct API that complete in ~3-5 min. Scripts are idempotent and saved for manual retry on failure.

MCP tools used: - mcp__attio-mcp__records_search_advanced, records_get_details, records_list, records_search

Config dependency: engines/<engine>/integrations/attio/config/workspace/icp_definitions.json – must contain personas array, matching_algorithm config, and qualification criteria.

Real Workflow Trace¶

Operator says: “Audit the CRM.”

  1. Phase-controller classifies the request as a substantive operation and creates a run plan.

  2. attio-optimizer fires. First checks schemas/_meta.json – if schemas are >14 days stale, it recommends running attio-mapper first. Assuming schemas are fresh: - Phase 1 (Audit): Loads engine context to understand active deals and campaigns. Builds an intelligent sample – Layer A pulls records the engine is actively working from (referenced in context, active deals and their networks, renewal targets). Layer B pulls broader health samples (recent records, dormant records, population extremes). Runs 5-category audit checks across the sample. - Phase 2 (Research): Checks research cache. If stale or missing, queries Context7 for Attio documentation and Bright Data for industry CRM benchmarks. Caches results for 30-day reuse. - Phase 3 (Recommend): Gap analysis against benchmarks. Produces prioritized action plan – P0 (revenue-blocking), P1 (efficiency), P2 (hygiene), P3 (optimization). Every action includes specific record IDs or reproducible queries. - Phase 4 (Visualize): Generates 7-page interactive HTML presentation suite with the shared design system.

  3. Operator reviews the HTML presentation. Opens crm-object-map.html as entry point, navigates through executive summary, health audit details, gap analysis, and action plan.

  4. Operator says: “Let’s refine the audit.” attio-refiner fires. - Loads the audit output. Presents dashboard summary with health score, sample composition, and action counts by priority. - Walks through P0 actions individually: presents finding with audit evidence, asks for operator context (“is there a reason this exists?”), confirms priority, collects decision. - Batches P1-P3 for efficiency. Operator can cherry-pick or batch-approve. - If operator needs more info, pre-formed exploration queries pull live CRM data using the audit’s record IDs as starting points. - Produces 06-operator-review.md (annotated findings) and 07-approved-actions.md (execution-ready work orders).

  5. Execution phase. Operator triggers execution. Approved actions route to the appropriate downstream skill: - Data cleanup and imports route to attio-ops (specifying attio-ops:csv-import or attio-ops:bulk-list). - ICP classification actions route to attio-qualify (specifying attio-qualify:enrich). - Schema changes flag as manual-ui (Attio doesn’t support programmatic schema modification).

  6. Downstream skills read 07-approved-actions.md, load the acceptance criteria, execute, and report results. Every mutation requires its own operator confirmation at execution time.

Direct API Layer¶

The scripts/attio/ directory contains a production REST API client suite that exists because the Attio MCP server has known bugs. Four zero-dependency Node.js scripts (built-ins only – https, fs, path):

Script Purpose
attio-direct-api.js Core utility. 20 functions covering MCP workarounds: select field updates (MCP silently fails), bulk list operations (MCP validation errors), record-reference fields (MCP 400 errors), list attribute management (no MCP tool exists). Works as both require() module and CLI tool.
enhanced-schema-fetch.js Full attribute metadata beyond MCP: writable/required/multiselect/archived flags, select field options with IDs, markdown report generation, MCP bug detection and annotation.
type-inference.js Field type inference engine. Workaround for the MCP bug where attribute types are extracted from record values instead of the proper /objects/{type}/attributes API. Three-tier inference: exact name mappings, pattern-based regex, text fallback.
mapping.js CSV-to-Attio field mapping with confidence scoring. Heuristic matching: exact (1.0), substring (0.8), synonym (0.7), Levenshtein distance (0.6), word boundary (0.7).

Why the direct API layer exists: MCP one-by-one operations take ~60-90 minutes for bulk work (150+ records). The direct API suite completes the same work in ~3-5 minutes. Beyond performance, several Attio operations simply fail through MCP – select field updates report success but don’t persist, list operations throw validation errors, and record-reference writes return 400. The direct API scripts use the correct Attio REST API patterns that MCP doesn’t implement.

Provenance note: The scripts/attio/ direct-API layer (8 files, ~97KB) was restored to EngineOS under D26 after the Act 3 lift regression discovered the original SEE-source suite had been missed during the initial OS build. The restoration recovered the production REST client that the audit/optimize/ops chain depends on for the operations MCP cannot complete.

Authentication: All scripts use process.env.ATTIO_API_KEY exclusively. No file-based credential fallbacks, no config files for credentials.

Design contract: Zero npm dependencies. Engine-agnostic – no workspace-specific field names or values hardcoded. The scripts are the MCP workaround layer; when Attio fixes their MCP server upstream, these workarounds can be retired.

Notion Suite (2 Skills + Scripts)¶

The Pipeline¶

notion-mapper ──> notion-ops
  (playbook)       (read/write operations)

Simpler than Attio because Notion’s API is more reliable – no MCP bug workaround layer needed. The mapper produces a playbook; notion-ops consumes it for all read/write operations.

Individual Skills¶

notion-mapper – Workspace Discovery and Playbook Generation¶

What it does: Deep-maps a Notion workspace to produce a playbook with database IDs, property definitions, relationship maps, working code examples, and pitfall documentation. Supports full workspace mapping or scoped mapping from a specific page down.

When to invoke: - First-time Notion setup for an engine - “Map this Notion workspace” / “refresh the playbook” - “Check for Notion changes” - Before heavy Notion operations

Key behaviors: - Three-phase operation mirroring attio-mapper: Discovery, Change Detection, Pattern Recognition. - Workspace context file (optional but recommended): engines can provide workspace-context.md describing known databases, AI-managed properties, and domain patterns. This dramatically improves mapping quality – the mapper can validate expectations, flag anomalies, and produce richer pitfall documentation. Without it, discovery runs mechanically from API responses alone. - Generates databases.py as the primary reference: database ID constants, per-database property maps with types, select options, relation targets (showing both human-readable title and machine-usable ID), rollup sources (marked read-only), and working create/query examples.

MCP tools used: - mcp__claude_ai_Notion__notion-search, notion-fetch, notion-query-database-view

Output location: engines/<engine>/config/notion/playbook/ – workspace-map.json, databases.py, relations.md, pitfalls.md, changelog.md, _meta.json.

Scripts: map_workspace.py, workspace_mapper.py, playbook_generator.py, change_detector.py, formatters.py, notion_client.py – all in .claude/skills/notion-mapper/scripts/.

notion-ops – Read/Write Operations¶

What it does: Full read/write operations for Notion databases. Four phases: Read from Playbook (load structure), Ingestion (route content to the right database), Optimization (schema analysis and improvement suggestions), and Query & Analysis (cross-database queries and gap analysis).

When to invoke: - User mentions Notion or database names - “Add this to Notion” / “route this to the right database” - “What campaigns are active?” / “which ICPs lack assets?” - Building deliverables that could benefit from database context

Key behaviors: - Code-first approach using the Notion API directly. Seven Python scripts provide a full SDK:

Script Purpose
domain_helpers.py High-level NotionHelpers class: create_task(), create_project(), query_meetings(), get_meeting_with_content()
property_builders.py Typed property/filter/sort builders: props.title(), props.rich_text(), props.relation(), filters.equals(), filters.and_filter(), sorts.descending()
query_engine.py Cross-database queries, gap analysis, summary statistics. Loads from playbook’s workspace-map.json
ingester.py Content routing with confidence scoring. Suggests target database, proposes property mapping, confirms before creating
notion_client.py API wrapper: query_by_id(), get_page_with_content()
notion_formatters.py Standalone property formatters and block text extraction
schema_mapper.py Schema extraction and documentation
  • Reads playbook before any operation – never queries the API for structure information that the playbook already has.
  • Content routing with deduplication: checks for existing records before creating, supports --upsert mode.

MCP tools used: - mcp__claude_ai_Notion__* (wildcard – all Notion MCP tools available)

Key Concepts¶

AI-managed properties are READ-ONLY. Notion AI manages certain properties (task suggestions, project next steps, meeting summaries, action items). These are marked DO NOT WRITE in the playbook. Scripts can read them to extract insights but never write to them – doing so would conflict with Notion AI’s management.

Two-way relations: set one side, the other auto-populates. When Notion relations are configured as two-way, setting a Task’s Project field automatically updates the Project’s Tasks list. The playbook documents which relations are two-way so scripts don’t redundantly set both sides.

Workspace context as configuration, not embedded knowledge. The WondaKB engine proved that providing workspace context (known databases, AI-managed properties, domain patterns) dramatically improves mapping quality. This insight was lifted to the OS level: any engine can provide a workspace-context.md file, and the mapper uses it as an accelerator. The skill itself contains zero workspace-specific knowledge.

Credentials are engine-scoped. Each engine provides its own Notion credentials at engines/<engine>/config/notion/credentials.json (or the path specified in engine config). Different engines can connect to different Notion workspaces.

API version pinning and a known breaking change. Notion’s API is versioned via the Notion-Version header. The current playbook scripts pin to 2022-06-28. A D27 adjacent finding flagged a breaking change in Notion API versions released after 2026-03-11: the archived boolean property was renamed to in_trash. Code on the older pinned version continues to work, but mappers and ops scripts that auto-upgrade or copy current Notion docs may break on the rename. When refreshing the playbook or generating new query/filter code, verify which field name the active Notion-Version expects.

MCP Tool Scoping¶

Every skill in EngineOS declares an allowed-tools block in its YAML frontmatter. This restricts which tools – filesystem, MCP, and skill invocation – are available during that skill’s execution. The scoping is declarative and inspectable: reading a skill’s frontmatter tells you its full external surface area.

How It Works¶

The allowed-tools line lists every tool the skill is permitted to use. Tools not listed are not available. MCP tools follow the naming convention mcp__<server>__<tool> (e.g., mcp__attio-mcp__records_search_advanced). Some skills use wildcards (e.g., mcp__claude_ai_Notion__* grants access to all Notion MCP tools).

Three Scoping Patterns¶

Pattern 1: Integration skill with domain-specific MCP tools.

attio-ops – the CRM write-path skill:

allowed-tools: Read, Write, Edit, Glob, Grep,
  mcp__attio-mcp__records_search_advanced,
  mcp__attio-mcp__records_get_details,
  mcp__attio-mcp__records_list,
  mcp__attio-mcp__lists_list,
  mcp__attio-mcp__lists_get_entries,
  mcp__attio-mcp__objects_list_attributes,
  mcp__attio-mcp__records_create,
  mcp__attio-mcp__records_update,
  mcp__attio-mcp__records_add_to_list

Full filesystem access (it writes import results and logs), plus exactly the Attio MCP tools it needs for record CRUD and list operations. No research tools, no Notion tools, no skill invocation. The scope matches the job: read schemas, search records, create/update records, manage list membership.

Pattern 2: Research skill with external intelligence tools.

research-engine – the research orchestrator:

allowed-tools: Read, Write, Edit, Glob, Grep, Skill

Filesystem access plus the Skill tool (it orchestrates other skills like depth-governor and findings-formatter). No direct MCP tools listed in the frontmatter – research MCP access (Bright Data, Context7) flows through the sub-skills it invokes. The orchestrator coordinates; the sub-skills hold the MCP scopes.

Compare with attio-optimizer, which directly holds both Attio MCP tools and research MCP tools (mcp__context7__*, mcp__brightdata__*) because it runs its own research during Phase 2 without delegating to the research-engine.

Pattern 3: Governance skill with no MCP access.

sanity-check and depth-governor:

allowed-tools: Read, Glob, Grep

Read-only filesystem access. No Write, no Edit, no MCP tools, no Skill invocation. These skills inspect the current state of work against known failure modes and depth classification criteria. They cannot modify files or call external services. This is intentional – governance skills that can’t change anything can be trusted to report honestly about the current state.

The Scoping Table¶

Skill Category Filesystem MCP Access Skill Invocation Rationale
Integration (attio-ops, notion-ops) Read + Write Domain-specific MCP tools No Write to external systems within their domain
Audit (attio-optimizer) Read + Write Attio MCP + Research MCP No Reads CRM, researches benchmarks, writes audit output
Research (research-engine) Read + Write Via sub-skills Yes (Skill tool) Orchestrates research sub-skills
Governance (sanity-check, depth-governor) Read-only None No Inspect and report only
Orchestration (phase-controller, session-orchestrator) Read + Write None Yes (Skill tool) Coordinate skill chains, no direct external access

This architecture means a CRM skill can never accidentally query Notion, a Notion skill can never accidentally hit the Attio API, and a governance skill can never modify anything. The allowed-tools frontmatter is the single source of truth for what each skill can touch.
