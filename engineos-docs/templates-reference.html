Templates Reference

EngineOS provides 38 templates (README indexes excluded from the count), organized across four locations: deliverables/ (client-facing and operational outputs in six subcategories plus top-level briefs), engagement/ (a copy-as-a-unit scaffold for new client engagement directories), knowledge-base/ (profiling templates)

Overview¶

Four placeholder types appear across the library:

Convention Meaning Example

Engagement Setup Workflow¶

The NEW-ENGAGEMENT-CHECKLIST.md defines a three-phase setup process:

  1. Phase 1 – Create Structure. Copy the entire templates/engagement/ directory to the target location. Verify the directory tree matches the expected layout.

  2. Phase 2 – Initialize Core Files. Populate README.md with engagement basics. Set CONTEXT.md quick status and current focus. Fill company-core.md with initial intelligence. Create the primary contact profile.

  3. Phase 3 – First Session. Orient via CONTEXT.md. Define the first work item. Record any setup decisions in DECISIONS.md.

The checklist also defines a minimum viable engagement (copy, edit README, edit CONTEXT, create primary contact profile, start working) to prevent setup from blocking actual work.

How Templates Work¶

Standard Workflow¶

  1. Select template from the appropriate category based on what you need to produce
  2. Copy to engine deliverables directory – engines/[engine-name]/deliverables/ or the engagement-specific output location
  3. Replace placeholders – fill all [PLACEHOLDER] fields, populate {{variable}} merge fields, follow <!-- INSTRUCTION --> guidance then remove the comments
  4. Adapt to context – remove [OPTIONAL: ...] sections that do not apply, add engagement-specific content where needed
  5. Run QA – invoke the qa-pipeline skill before delivery. The output-self-test skill runs binary quality gates calibrated by output type.
  6. File with versioning – follow the deliverables naming convention (YYYY-MM-DD-description.md for individual files, v[X.Y]-[status]-YYYY-MM-DD/ for formal versioned deliverables)

Operator vs. External Naming¶

Not all deliverables are client hand-offs. Materials for the operator’s own use carry an -OPERATOR suffix to distinguish them from external deliverables. Example: weekly-report.md (hand-off) vs. meeting-scripts-OPERATOR.md (operator use).

Folder Templates¶

The campaign-package.md template is a folder template – each numbered section becomes its own file within a campaign directory (campaigns/[campaign-name]/). The structure and naming convention in the template are preserved across the individual files.

AI-Assisted Population¶

Templates are structured for AI consumption: clear section headers for extraction, confidence levels for weighting, source attribution for verification, and atomic sections that can be processed independently. The recommended approach is to provide the template plus source data and request section-by-section population, then review for accuracy and verify source citations.

Creating New Templates¶

When a deliverable type recurs, generalize it into a template: remove engagement-specific details, add standard placeholders, include metadata (version, date, purpose), place it in the appropriate category folder, and update the deliverables README index.

HTML Deliverables¶

Deliverables that produce HTML output use the EngineOS design system at design-system/. The enterprise stylesheet at design-system/enterprise-styles.css provides consistent styling. The render-validate skill verifies HTML output quality.
