Skill System

EngineOS ships 29 skills at .claude/skills/. Individually, each skill is a SKILL.md file with YAML frontmatter and structured methodology. Collectively, they compose into typed workflows enforced by a run controller. The system's value is not in any single skill -- it is in the composition: how skills chain together, h

This document covers the machinery: discovery, anatomy, access control, categories, forced chains, and concrete traces from operator prompt to disk output. For the flat catalog of all 29 skills with one-liners, see skills-reference.md. For the enforcement architecture that makes chains non-optional, see governance.md.

Discovery¶

Claude Code discovers skills through native directory scanning. Every .claude/skills/*/SKILL.md file is detected automatically. Discovery loads in two phases:

Passive loading (~2% of context): Skill descriptions from YAML frontmatter load at session start. Claude Code sees the name and a one-line summary for all 29 skills. This is the index – enough to know what exists, not enough to execute.

Full loading (on invocation): When a skill is invoked by name, its full SKILL.md loads into context. The complete methodology, phase structure, integration points, anti-patterns, and self-tests become available.

This is the Tier 3 context budget model from CLAUDE.md. A session that uses 3 skills loads 3, not 29. A research session loads depth-governor, market-scanner, and findings-formatter. A CRM audit loads attio-mapper, attio-optimizer, and attio-refiner. Skills the session never touches stay at their 2% description footprint.

The practical effect: EngineOS carries 29 skills without paying the context cost of 29 skills. A focused session consumes context proportional to its actual work, not proportional to the system’s total capability.

Passive Retrieval via UserPromptSubmit Hook¶

Native skill discovery is the routing layer for capability loading – which procedure should fire for a given prompt. A parallel mechanism handles context loading: the UserPromptSubmit hook (hooks/prompt-retrieval.py, added 2026-06-04 per D32) silently injects relevant prior context from the second brain into the prompt before any skill loads. A heuristic gate (trigger words, question-form starts, minimum prompt length) decides whether to fire. When it fires, it searches the same six-surface priority corpus as the recall skill – intelligence log, knowledge index, KB concepts/connections, recent daily logs, recent run-plans, methodology – and injects up to 1,024 characters of top-3 matches with a ≤1-second budget.

The hook complements native discovery without replacing it. Discovery answers “which skill should run.” The retrieval hook answers “what does the corpus already know that the operator hasn’t said.” Together they front-load both capability and context before the model decides what to do. When the hook misses or the operator wants a deeper sweep, the recall skill (Read-only, manual invocation) handles the unbounded version of the same search. Append-only health records at scripts/retrieval-health.jsonl make the hook’s behavior auditable – the operator runs scripts/retrieval-review.py periodically to keep, tune, or kill the gate.

Anatomy of a Skill¶

Every skill follows the same structure: YAML frontmatter for metadata and access control, then a markdown body with methodology, phases, integration points, and self-tests.

Frontmatter¶

The frontmatter is the machine-readable contract. Two fields matter:

  • description – What Claude Code sees during passive discovery. This is the routing signal. It tells the system when to invoke the skill and what triggers it responds to.
  • allowed-tools – The access control boundary. This field restricts which tools the skill can use when loaded.

Here are three real frontmatter blocks, side by side, showing how access control varies by skill category:

Governance skill (depth-governor) – read-only:

---
description: >
  Mandatory 30-second depth classification before starting any
  substantive work. Determines whether to scan (breadth) or
  deep-dive (depth) for each topic area.
allowed-tools: Read, Glob, Grep
---

Orchestration skill (phase-controller) – write + Skill invocation:

---
description: >
  The run controller for all substantive EngineOS work. Classifies
  the operation, builds a disk-persisted run plan with hardened
  criteria, forces skill invocation at every transition.
allowed-tools: Read, Write, Edit, Glob, Grep, Skill
---

Integration skill (attio-mapper) – MCP-scoped:

---
description: >
  Maps Attio CRM workspaces to generate schema caches and playbooks
  consumed by all other Attio skills.
allowed-tools: Read, Glob, Grep, mcp__attio-mcp__records_get_attributes
---

The depth-governor can observe and classify but cannot modify files. The phase-controller can write run plans and invoke other skills. The attio-mapper can read from Attio’s MCP endpoint but has no general write access – it generates schema caches through a controlled process, not ad-hoc edits.

Body Structure¶

After the frontmatter, a skill’s body typically includes:

  • Provenance – Which source engine(s) the skill was adapted from
  • When to Use / When NOT to Use – Invocation boundaries
  • Methodology – Phased workflow with explicit steps
  • Integration points – How this skill connects to other skills
  • Anti-patterns – What goes wrong and how to avoid it
  • Self-tests – Binary checks to run before declaring done

The body is the methodology that loads on invocation. It is not a prompt template – it is a structured operating procedure with decision trees, quality gates, and worked examples.

Why This Matters¶

Tool asymmetry is the structural mechanism that prevents quality evaluation from collapsing into self-approval. The adversarial-evaluator has Read, Bash, Glob, Grep – it can read deliverables and run checks, but it cannot fix what it finds. This is deliberate. An evaluator with Write access becomes a fixer, and a fixer is not adversarial. The same principle from Cole’s adversarial-dev evaluator: tool asymmetry forces honest scoring because the evaluator cannot resolve its own criticism.

Governance skills (depth-governor, output-self-test, sanity-check) are read-only for the same reason. They observe and report. They do not modify. If a sanity-check finds a problem, it surfaces the problem to the operator or the orchestrating skill – it does not silently fix it.

MCP scoping prevents integration skills from accessing unrelated external systems. The attio-mapper can call mcp__attio-mcp__records_get_attributes but not Bright Data search endpoints. The market-scanner can call Bright Data and Context7 but not Attio or Notion. Each skill sees only the external surface it needs.

Forced Skill Chains¶

The defining feature of the skill system is composition. Skills do not fire independently – they chain into typed workflows enforced by the phase-controller. When the phase-controller classifies an operation, it selects a chain template that specifies which skills fire, in what order, with what gates between them.

The chains are not suggestions. Phase-controller Rule 1: “Every skill in the chain gets invoked. Not referenced, not ‘kept in mind’ – actually loaded and executed.” Rule 4: “Gates are non-negotiable. Work does not proceed past a gate without the operator’s explicit approval.”

The Iteration Envelope¶

Production chains (BL, EW, EN, CP, RE) wrap their produce-and-evaluate steps in an iteration envelope – an evaluator-optimizer loop:

OUTSIDE ENVELOPE (runs once):
  depth-governor, brainstorming, writing-plans, operator approval

INSIDE ENVELOPE (iterates on failure, max 3 retries):
  Produce deliverable
    --> adversarial-evaluator (independent context, scored JSON)
    --> IF PASS: exit envelope, proceed to next step
    --> IF FAIL: inject evaluation feedback --> re-produce --> re-evaluate
    --> After 3 failures: OPERATOR GATE with full iteration history

AFTER ENVELOPE (runs once on final version):
  qa-pipeline (if external-facing), operator approval, audit-logging

The iteration envelope is bounded. Three retries, then operator escalation. Each retry injects the evaluator’s critical_issues and per-criterion feedback as additional context for the next attempt. The run plan logs each iteration with scores so the full history is visible.

What makes IN distinct: No iteration envelope – integration work is data-driven, not creative. No brainstorming or writing-plans – scope comes from the integration spec. Sanity-check focuses on data integrity rather than content quality.

Methodology-to-Skill Relationship¶

Skills automate methodology. The methodology/ directory contains 15 formalized documents encoding proven research and quality methodology. Skills reference these documents during execution; methodology documents are immutable without operator approval (enforced by .claude/rules/methodology-immutable.md).

Five skills have direct methodology companions – the skill operationalizes what the methodology document defines:

Methodology Document Companion Skill Relationship
methodology/depth-assessment.md depth-governor Methodology defines the two-depth model, classification questions, and calibration guidance. Skill executes the 30-second classification.
methodology/binary-self-tests.md output-self-test Methodology defines the YES/NO testing philosophy and test design principles. Skill runs the tests against specific output types.
methodology/findings-pattern-library.md findings-formatter Methodology defines the 7 finding types and their structural templates. Skill selects and applies the right template during synthesis.
methodology/section-construction.md section-construction Methodology defines the incremental build approach for large outputs. Skill manages the section-by-section construction with inter-section verification.
methodology/memory-architecture.md § Retrieval Surfaces recall (+ UserPromptSubmit hook) Methodology defines the three-layer retrieval architecture and six-surface priority corpus. The recall skill executes Layer 3 (manual escalation); the prompt-retrieval.py hook executes Layer 2 (silent mid-work injection).

Other skills reference methodology documents without having a dedicated companion. The phase-controller references methodology/ecosystem-build.md for BL chains and methodology/adversarial-validation.md for evaluation methodology. The market-scanner references methodology/credibility-tiers.md for source quality classification and methodology/dual-source-intelligence.md for cross-validation discipline.

The separation matters: methodology can be updated independently of skill behavior, and skill behavior can be refined without changing the underlying methodology. When the credibility tier system gets a new tier or reclassification rule, the methodology document changes; the market-scanner’s reference to it means the updated methodology takes effect on the next invocation without touching the skill.

How This Connects to Enforcement¶

The skill system does not enforce itself. Three mechanisms external to skills make the chains non-optional:

  1. PreToolUse hook (pre-write-governance.sh) – Blocks deliverable writes to engine paths without an active run plan at the canonical run-plans directory. The phase-controller must have created a run plan before any production skill can write output.

  2. Phase-controller forcing function rules – 11 rules govern chain execution. Rule 1: every chain skill gets invoked. Rule 4: gates require explicit operator approval. Rule 7: skipping requires justification. Rule 10: mandatory steps require invocation or documented skip-justification. Rule 11: evidence-before-reporting at phase transitions.

  3. Structural enforcement via Layer 4 – For chains with [MANDATORY - structural] planning steps, the production step reads Layer 4 of the run plan as its first action. Empty Layer 4 means the plan was never written, and production cannot proceed. This is file-based communication between the planning step and the production step.

For the full enforcement architecture, see governance.md.
