EngineOS System Documentation · Section 03 · Built 2026-07-03

Governance

EngineOS governs a confident AI agent — one that will skip steps it considers unnecessary, generate plausible completion summaries for work that didn't happen, and report filesystem facts from memory instead of checking disk. The governance stack exists because methodology alone does not survive contact with that agent

“This is methodology-as-infrastructure for a single operator using orchestration, discipline, and operator review checkpoints. It works because the operator is engaged. It does not claim to be deterministic enforcement.”

– CLAUDE.md, Enforcement Architecture

The stack has two layers. Mechanical enforcement uses hooks that block tool calls at the Claude Code platform level. Advisory enforcement uses instructions (CLAUDE.md, rules files, skill specs) that depend on the agent following them. A run plan bridges both: a planning artifact created by advisory governance that doubles as a mechanical gate key the hook checks before allowing writes.

TL;DR — what actually blocks a write, and what only detects:

  • Blocks: the PreToolUse Write|Edit gate (hooks/pre-write-governance.sh) — a non-exempt write with no scope-matched active run plan is denied, and the gate fails closed if its policy library is missing. And the PreToolUse Bash tripwire (hooks/pre-bash-tripwire.sh, D35) — denies rm with recursive+force flags; # eos-allow-rm is the deliberate-override escape.
  • Detects, never blocks: the PostToolUse Bash detector (hooks/post-bash-governance.sh, D34) — warns loudly after an ungoverned Bash write to a watched governed path. The write has already happened.
  • Everything else is advisory. The Bash write channel as a whole is Turing-complete and cannot be gated; rules and skills depend on the agent following them; the operator is the final enforcement layer.

Two Enforcement Layers¶

Mechanical Enforcement (Hooks)¶

Hooks are the mechanical layer — they fire at lifecycle events in Claude Code and either block, log, or augment the agent’s behavior. They don’t depend on the agent reading instructions. EngineOS wires 8 hook events carrying ten hook wirings — PreToolUse and PostToolUse each run two matcher groups (Write|Edit and Bash). Together they cover write-governance, a destructive-rm tripwire, Bash-write detection, audit logging, post-compact recovery, session-start orientation, session-arc capture (twice — on SessionEnd and PreCompact), and mid-work retrieval injection. The stack grew from four events (April 2026, original governance build) to eight (June 2026, when the second-brain capture and retrieval layer landed per D29-D32), then gained the Bash-governance pair on the two tool events (2026-06-13: D34 detector + D35 tripwire).

The ten hook wirings across 8 events (1–8 in build order; 9–10 are the 2026-06-13 Bash-governance pair):

# Event Matcher Script Purpose
1 PreToolUse Write\|Edit hooks/pre-write-governance.sh Block deliverable writes without a scope-matched run plan
2 PostToolUse Write\|Edit hooks/post-tool-use.sh Append activity-log row on every successful write/edit
3 Stop (any) hooks/stop.sh Warn if CONTEXT.md was not updated this session
4 PostCompact (any) hooks/post-compact.sh Re-inject core behaviors and active run-plan awareness
5 UserPromptSubmit (any) hooks/prompt-retrieval.py Inject relevant prior context from the second brain when the prompt matches the heuristic gate
6 SessionStart (any) hooks/session-start.py Inject KB index + last 30 lines of today’s daily log as orientation context
7 SessionEnd (any) hooks/session-end.py Spawn flush.py to capture the session arc into today’s daily log
8 PreCompact (any) hooks/pre-compact.py Spawn flush.py to capture the session arc into today’s daily log before compaction discards detail
9 PreToolUse Bash hooks/pre-bash-tripwire.sh DENY rm with recursive+force before it runs (named-pattern accident catch, D35; # eos-allow-rm escape)
10 PostToolUse Bash hooks/post-bash-governance.sh Warn — never block — after an ungoverned Bash write to a watched governed path (D34; detection, not prevention)

The wiring lives in .claude/settings.json — described here rather than quoted, because quoted configs rot (this very section once showed one hook per tool event long after disk had two; the file itself is one Read away). The same file also carries enabledPlugins (added 2026-07-02, D53): two plugin packs with zero Skill-invocations across the transcript history are disabled there for context economy — a config lever on the always-loaded surface, distinct from the hook wiring. Each of the 8 events maps to one or two matcher groups: PreToolUse and PostToolUse each define TWO — Write|Edit and Bash — while the six lifecycle events match everything. Shell hooks are invoked as bash $CLAUDE_PROJECT_DIR/hooks/<name>.sh; Python hooks run via uv run --directory $CLAUDE_PROJECT_DIR python hooks/<name>.py with per-hook timeouts (15s session-start, 10s pre-compact and session-end, 3s prompt-retrieval).

On disk that is 7 shell scripts (the governance core: gate, tripwire, detector, activity logging, Stop checks, post-compact recovery, plus the shared policy library hooks/_governance-common.sh) and 6 Python files (the second-brain layer: session-start/end, pre-compact, prompt-retrieval, plus shared modules _flush_common.py and _people_surface.py). All shell scripts resolve the repo root portably via ENGINEOS_ROOT="${CLAUDE_PROJECT_DIR:-$HOME/Desktop/EngineOS}" rather than hardcoded paths. The two flush hooks (SessionEnd, PreCompact) share extraction and spawn logic via hooks/_flush_common.py (D29) so capture caps stay in sync across both firing points.

Hook 1: PreToolUse – Governance Gate (pre-write-governance.sh)¶

Type: PreToolUse (fires before a Write or Edit tool call executes) Trigger: Every attempt to write or edit any file What it does: Gates Write/Edit deliverable writes unless a scope-matched active run plan exists on disk

This is the hook that makes governance mechanical rather than advisory. A confident agent can ignore instructions. It cannot ignore a JSON response that denies permission to execute its tool call.

The honest boundary of the gate: the matcher is Write|Edit, so the gate covers Write and Edit tool calls — including subagent Write/Edit calls (hook firing in subagent context verified empirically 2026-06-12; re-verify after harness updates). Bash-mediated writes are not gated by this hook — the Bash channel is Turing-complete and not heuristically gateable, and no denylist closes it. Since 2026-06-13 that gap is made loud rather than closed: the PostToolUse Bash detector (D34) warns after an ungoverned Bash write, and the PreToolUse tripwire (D35) denies the single most common destructive fat-finger. See Hooks 9 & 10: The Bash-Governance Surface below. For everything the detector cannot see (external paths, .gitignored paths, deliberate evasion), governance remains the forced skill chain plus the parent’s post-hoc verification of outputs against the active plan.

The deny mechanism:

When no qualifying run plan is found, the hook outputs JSON to stdout:

{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "GOVERNANCE GATE (scope-matched): No active run plan found in [scope] for write to [path]. Before writing deliverables or modifying engine state, invoke phase-controller to classify this operation and create a scope-matched run plan. If this is a trivial fix (typo, metadata), phase-controller will classify it as skip in under 60 seconds. Exempt paths (logs, CONTEXT.md, DECISIONS.md, run-plans, memory) do not require a run plan; hook/rule/settings edits DO (de-exempted 2026-06-12 per fix-ledger L-G3)."
  }
}

Claude Code reads permissionDecision: "deny" and blocks the tool call. The agent sees the permissionDecisionReason and must comply – there is no override available to the agent. Only the operator can create a run plan (via approving one), and only the hook can unlock the write.

Exempt paths:

Not every write needs a run plan. The exempt list — housekeeping writes that map to phase-controller’s skip list — lives in hooks/_governance-common.sh (eos_is_exempt_path), the single policy source shared with the Bash detector: */logs/*, */CONTEXT.md, */DECISIONS.md, */run-plans/*, */memory/*, *MEMORY.md. An exempt path exits with no opinion and the normal permission flow continues. Note what is deliberately absent from the list: .claude/settings*, .claude/rules/, and hooks/ were de-exempted 2026-06-12 (fix-ledger L-G3) — edits to the governance infrastructure itself require an active run plan, closing the hole where the gate’s own configuration was the easiest thing to write without governance.

Fail-closed posture (v2.1): if the gate cannot read _governance-common.sh, it does not shrug and allow — it DENIES with a “GOVERNANCE GATE MISCONFIGURED” reason naming the missing library. A gate that cannot evaluate its policy must not silently allow writes.

Scope-matching logic (v2; extracted to the shared library in v2.1):

The hook’s critical evolution was from v1 (any recent plan anywhere unlocks any write) to v2 (scope-matched plans). The v1 governance hole: an agent working on a JSE engagement could write to ODC files because an unrelated JSE run plan existed somewhere in the tree. Since v2.1 (2026-06-13, the D34 build) the scope logic lives in hooks/_governance-common.sh — eos_engine_of_path (which engine a path belongs to), eos_active_plan_for (find a scope-matched active plan at the canonical flat paths, -maxdepth 1, -mtime -2), and the D2 status filter eos_first_active_plan (a candidate counts as active only if it is not a DEBRIEF-* file and its **Status:** line is not COMPLETE/ARCHIVED; plans with no Status line fail open — legacy plans predate the convention) — one sourced file, so the gate and the Bash detector can never drift into disagreement. Behavior is byte-for-byte v2; only the implementation is shared. (This section once quoted the hook’s inline code; the quote rotted when the code moved to the library — described-and-linked now.)

The rules:

Write target Required run plan location
engines/job-search/... engines/job-search/run-plans/ OR run-plans/ (root)
engines/on-demand-curriculum/... engines/on-demand-curriculum/run-plans/ OR run-plans/ (root)
OS-level paths (.claude/skills/, methodology/, etc.) run-plans/ (root only)

Root run-plans/ always qualifies because OS-level operations (builds, audits) legitimately touch engine files. Engine-specific run-plans/ directories scope engine work to its own tenant. The -maxdepth 1 enforces canonical flat paths – no nested subdirectories like engines/X/pipeline/run-plans/ (a legacy pattern that was deprecated in the v2 rewrite). The -mtime -2 requires the plan to have been modified within the last 2 days – stale plans don’t unlock writes. The status filter (2026-06-12, fix-ledger L-G2) adds a content check on top of the mtime check: DEBRIEF-* files never qualify, and a plan whose **Status:** line reads COMPLETE or ARCHIVED no longer unlocks writes even if recently touched. Plans with no Status line fail open (legacy plans predate the convention).

Hook 2: PostToolUse – Activity Logging (post-tool-use.sh)¶

Type: PostToolUse (fires after a Write or Edit tool call completes) Trigger: Every successful file write or edit What it does: Appends a timestamped entry to logs/activity-log.md

This hook solves a specific governance gap: advisory logging dropped during subagent dispatch because no skill explicitly instructed the subagent to log. Mechanical logging fires regardless of what the agent or subagent thinks about logging.

ENGINEOS_ROOT="${CLAUDE_PROJECT_DIR:-$HOME/Desktop/EngineOS}"

INPUT=$(cat)
FILE_PATH=$(echo "$INPUT" | jq -r '.tool_input.file_path // "unknown"')
TOOL_NAME=$(echo "$INPUT" | jq -r '.tool_name // "unknown"')

# Determine action from tool name
if [ "$TOOL_NAME" = "Write" ]; then
    ACTION="Created"
elif [ "$TOOL_NAME" = "Edit" ]; then
    ACTION="Updated"
fi

# Strip the repo-root prefix for cleaner log entries
FILE_PATH_CLEAN="${FILE_PATH#$ENGINEOS_ROOT/}"

# Determine engine from file path (engine-agnostic, defaults to "OS")
ENGINE="OS"
if [[ "$FILE_PATH" =~ /engines/([^/]+)/ ]]; then
    ENGINE="${BASH_REMATCH[1]}"
fi

# Schema: 6-column (Date|Engine|Action|File|Skill|User) per methodology/memory-architecture.md D-5
echo "| $TIMESTAMP | $ENGINE | $ACTION | $FILE_PATH_CLEAN | hook:post-tool-use | ${USER:-operator} |" >> "$ACTIVITY_LOG"

Every write produces a row in the activity log using the canonical 6-column schema (Date | Engine | Action | File | Skill | User) from .claude/rules/logging.md. Engine detection is an engine-agnostic regex over the /engines/<name>/ path segment – new tenants get tagged without editing the hook. The infinite-loop guard (if [[ "$FILE_PATH" == *"activity-log.md" ]]; then exit 0) prevents the hook from logging its own writes. Attribution reads from $USER environment variable with fallback to “operator” – preparing for future multi-user support without breaking the single-operator default.

Hook 3: Stop – Session-State Checks (stop.sh)¶

Type: Stop (fires at EVERY turn-end, not just session close) Trigger: Turn end What it does: Runs four STATE-AWARE advisory checks and emits any warnings as a single user-visible systemMessage

The naive version of this hook (“CONTEXT.md wasn’t updated today”) fired mid-session before the producing step had a chance to run — it could not tell broken from nothing-happened-yet, and it trained the operator to ignore it. The WS2 hook-honesty rewrite (2026-06-20, run-plans/2026-06-20-ws2-hook-honesty-build.md) made every check state-aware: each warns only on a TRUE condition and names what triggered it so the operator can verify. A warning is a LEAD, not a defect — the hook’s own output header says so.

The four checks (described from the live file rather than quoted — the previous quoted body outlived two rewrites):

  1. Root CONTEXT.md stale + real work today. Warns only when the activity log shows a today-dated Created/Updated row AND CONTEXT.md’s mtime is older than today. Read-only or judgment-only sessions stay silent — the false positive the old version generated constantly.
  2. Engine CONTEXT.md stale + that engine worked today. The same gate, scoped per tenant via the activity log’s Engine column.
  3. Knowledge-base compile drift. Compares the last compile date in knowledge/log.md against the newest daily/ file; warns past a 3-day tolerance band. (Unchanged in WS2 — it was already honest.)
  4. Missing daily log + a flush was actually attempted. daily/<today>.md absent mid-session is NORMAL — flush runs on SessionEnd/PreCompact, which fire after Stop. This warns only when scripts/flush.log records a flush attempt today and the file is still missing: a real pipeline failure, distinguishable from “nothing has happened yet.”

The hook is advisory, not blocking — it never prevents session end. The delivery mechanism was re-plumbed 2026-06-12 (fix-ledger L-G5): plain stdout from a Stop hook on exit 0 is NOT shown to the user (it goes to the debug log only, per the official hooks doc), so warnings accumulate and emit once as a JSON systemMessage via jq, which IS user-visible.

Hook 4: PostCompact – Compaction Recovery (post-compact.sh)¶

Type: PostCompact (fires after Claude Code compacts its context window) Trigger: Context compaction event What it does: Re-injects core behaviors and active run plan awareness

Context compaction is the event where Claude Code’s context window fills and older conversation turns are summarized or dropped. CLAUDE.md and rules survive compaction (they’re always-loaded files), but in-session awareness of active work can be lost.

The live behavior (described, not quoted — the previously quoted body used the -newer CONTEXT.md heuristic that the live file’s own comment now calls “the old bug”): the hook echoes the seven core behaviors as a plain-text reminder, then lists ACTIVE run plans using the same single-source-of-truth definition the gate uses — it sources hooks/_governance-common.sh and calls eos_list_active_plans (canonical flat paths only, -mtime -2, **Status:** not COMPLETE/ARCHIVED, DEBRIEF-* excluded). The old -newer CONTEXT.md approach hid every plan whenever CONTEXT.md was touched after the plan (a common ordering) and scanned non-canonical nested dirs — a definition-mismatch with the gate found and fixed by the WS2 hook-honesty build (2026-06-20). If the shared library can’t be sourced, the hook fails open to the behavior reminder — it is advisory, never a gate. It closes by enumerating the engine tenants and pointing the agent at CONTEXT.md and the activity log.

This hook is the compaction survival mechanism. The run plan on disk persists the full execution state (6 layers of context). The PostCompact hook tells the agent where to find it. Together, they bridge the compaction gap.

Hook 5: UserPromptSubmit – Retrieval Injection (prompt-retrieval.py)¶

Type: UserPromptSubmit (fires after the operator submits a prompt, before the agent receives it) Trigger: Every prompt matching the heuristic gate (trigger words, question starts, minimum length) What it does: Searches the second brain and injects the top 3 matches as <prior-context>...</prior-context> mid-prompt

This is the mechanical half of the retrieval architecture (DECISIONS.md D32). Capture-side infrastructure (flush.py, compile.py, the KB, daily logs, intel log) grew strong by mid-2026 – 216 KB articles, 70+ intel-log entries, 18 daily logs at the time – but a marathon-arc audit showed zero reads of knowledge/concepts/*.md across ~30 hours of substantive work. Capture without retrieval is a write-only system. This hook closes the gap mechanically so the agent doesn’t have to remember to query its own corpus.

Gate heuristic:

The hook does not fire on every prompt. It applies three cheap tests (config in hooks/retrieval-triggers.json):

  1. Prompt length – skip if under 20 chars (one-liners aren’t worth a corpus sweep)
  2. Trigger words – fires when prompt contains one of: our, before, prior, previous, remember, similar, again, last time (we was removed 2026-07-02 — it fired on 602 of 756 gate hits, making the gate effectively always-on)
  3. Question starts – fires when prompt begins with have, did, what, how, why, when

Either trigger condition firing is sufficient. The thresholds tune the noise/signal balance – defaults target a 10-60% gate hit rate per session.

Search:

The hook extracts query terms (≥4 chars, stopwords filtered, max 8 terms), compiles a single case-insensitive regex, and sweeps the six-surface priority corpus (the same priority order used by Hook 6 and by the recall skill):

  1. logs/intelligence-log.md – highest density curated strategic moments
  2. knowledge/index.md – catalog with summaries
  3. knowledge/concepts/*.md + connections/*.md – KB article slug matching
  4. daily/*.md (last 14 days) – recent session arcs
  5. run-plans/*.md (last 60 days) – recent plan-and-execution records
  6. (methodology reserved for skill-side /recall; hook stops earlier)

A budget deadline (default 1000ms) gates each surface – if the deadline expires mid-sweep, lower surfaces are skipped. Score-capping at min(len(hits), 5)+1 for file-level surfaces prevents large files from drowning out per-row surfaces.

Output:

Top 3 ranked matches are formatted as <prior-context> injection at ≤1024 chars and returned via stdout as the Claude Code additionalContext convention. If no matches found, no injection (the hook exits silently; the prompt proceeds unchanged). Silent recovery on any error path – the hook never blocks the operator’s prompt cycle.

Health log:

Every invocation appends one record to scripts/retrieval-health.jsonl – timestamp, session_id, gate decision, gate reasons, query terms, surfaces searched, matches found/returned, chars injected, exec_ms, result. The operator runs scripts/retrieval-review.py after ~10 sessions and applies the keep/tune/kill rules from D32 (gate hit rate <10% = too quiet; >60% = too noisy; injection size near cap = bump cap; >50% noise judgment = tighten or kill).

This is governance-by-information-flow rather than governance-by-blocking – the hook does not deny anything; it changes what the agent sees by the time it answers. The deny-side mechanical layer (Hook 1) addresses “research before producing”; the inject-side mechanical layer (Hook 5) addresses “research before agreeing” applied to the agent’s own corpus.

Hook 6: SessionStart – Orientation Injection (session-start.py)¶

Type: SessionStart (fires when Claude Code starts a session) Trigger: Session start What it does: Reads knowledge/index.md + the last 30 lines of today’s (or yesterday’s) daily log, injects as orientation context

Layer 1 of the three-layer retrieval architecture (methodology/memory-architecture.md § Retrieval Surfaces). Every session begins with the full KB index visible plus the most recent in-flight context from the daily log. Cap is ~20K chars; output truncates with ...(truncated) if exceeded.

# Knowledge base index (the core retrieval mechanism)
if INDEX_FILE.exists():
    index_content = INDEX_FILE.read_text(encoding="utf-8")
    parts.append(f"## Knowledge Base Index\n\n{index_content}")
# Recent daily log (last 30 lines of today's or yesterday's)
recent_log = get_recent_log()
parts.append(f"## Recent Daily Log\n\n{recent_log}")

This hook does no API calls – pure local file I/O. The session-orchestrator skill complements it on the agent-discipline side (CONTEXT.md reading, engine detection) but the orientation injection is what makes the KB index visible without the agent having to remember to load it.

Hook 7: SessionEnd – Session-Arc Capture (session-end.py)¶

Type: SessionEnd (fires when a Claude Code session terminates) Trigger: Session termination, transcript path provided by Claude Code What it does: Extracts the last ~60 turns / 30K chars from the JSONL transcript, writes them to a context file, spawns flush.py as a background process to extract knowledge into the daily log

This is the write-side counterpart to Hook 6 (which reads from daily/). The hook itself does NO API calls – only local file I/O for speed (<10s). The actual Agent SDK call lives in flush.py, spawned as a detached background process so the session-end event returns quickly.

# Recursion guard: if we were spawned by flush.py (which calls Agent SDK,
# which runs Claude Code, which would fire this hook again), exit immediately.
if os.environ.get("CLAUDE_INVOKED_BY"):
    sys.exit(0)

Extraction and spawn logic both live in hooks/_flush_common.py – shared with Hook 8. The recursion guard prevents infinite loops when flush.py’s internal Claude Code session would otherwise re-fire SessionEnd. Hook 3 (Stop) still fires separately and handles the CONTEXT.md update check; the two are independent. After the flush spawn, the hook also refreshes the derived caches in detached background processes – people-heat.py, capability-snapshot.py, kb-health.py, and build-dashboard.py (the living health dashboard at docs/site/dashboard.html) – isolated so capture is never affected.

Hook 8: PreCompact – Compaction-Time Capture (pre-compact.py)¶

Type: PreCompact (fires before Claude Code auto-compacts the context window) Trigger: Imminent compaction What it does: Same as SessionEnd – extracts recent transcript turns, spawns flush.py – but at the marathon-session boundary instead of at session termination

Compaction discards detail by summarizing older turns. Without this hook, marathon sessions would lose the substantive arc to summarization before SessionEnd ever fires. PreCompact captures the arc into the daily log first; SessionEnd then captures the remainder at session close. Together they cover the two boundaries where session content might be lost.

Both hooks share hooks/_flush_common.py (DECISIONS.md D29). The shared module exports extract_conversation_context(), parse_hook_input(), spawn_flush_process(), and the cap constants MAX_TURNS=90 / MAX_CONTEXT_CHARS=60_000 (30_000 → 40_000 on 2026-06-12 per fix-ledger L-V4; 40_000 → 60_000 and turns 60 → 90 on 2026-07-02 after the telemetry review found 73% of sessions cap-bound) as a single source of truth. Bumping a cap in _flush_common.py updates both firing points automatically – the anti-drift discipline that prevents the next person from forgetting one of the two hooks. The recursion guard is identical to Hook 7.

MIN_TURNS_TO_FLUSH differs: SessionEnd flushes at ≥1 turn (any real conversation is worth capturing); PreCompact requires ≥5 turns (avoid spurious flushes for incidental compactions early in a session).

Hooks 9 & 10: The Bash-Governance Surface (pre-bash-tripwire.sh + post-bash-governance.sh)¶

The PreToolUse gate (Hook 1) sees Write and Edit tool calls. It cannot see a heredoc, a sed -i, a cp, a python -c — the Bash write channel is Turing-complete and cannot be gated by a denylist. Rather than pretending otherwise, EngineOS ships two hooks (both 2026-06-13) that implement the honest version of the boundary: one named-pattern accident catch that blocks, and one detector that makes ungoverned writes loud.

Hook 9 — the destructive-rm tripwire (PreToolUse Bash, D35). DENIES a command whose rm invocation carries BOTH recursive and force flags (rm -rf, -fr, -r -f, --recursive --force, sudo-prefixed variants) — the single most common irreversible-loss fat-finger. The parsing is segment-bound: the flags must belong to the rm segment itself (pip install --force-reinstall && rm tmp does not trip), and quoted mentions (echo "rm -rf x") are stripped before testing. Escape hatch: re-run the SAME command with # eos-allow-rm appended — a legitimate deletion costs ~10 seconds of deliberateness, not a dead end. (The harness’s “ask” permission decision silently degrades to allow — verified empirically 2026-06-13 — so deny-with-escape is the design, not a preference.) It is an accident catch, NOT a guard against destructive operations: obfuscated or scripted rm, find -delete, shutil.rmtree, truncating redirects, and git clean -fd all pass through untouched. Fail-open by design — a broken tripwire must never block legitimate commands.

Hook 10 — the ungoverned-write detector (PostToolUse Bash, D34). Fires AFTER every Bash command and checks the filesystem — git porcelain, never command-string parsing (which would be the same Turing-complete trap) — for changes under watched governed prefixes (engines/, .claude/, hooks/, methodology/, patterns/, principles/, design-system/, registry/, docs/source/, operator/, templates/, scripts/; *.log churn ignored). For each changed path it applies the SAME policy the gate uses — eos_is_exempt_path plus the scope-matched active-plan check from _governance-common.sh — and when a non-exempt path changed with no active scope-matched run plan, it emits BOTH channels: a systemMessage (operator-visible, the loud half) and additionalContext (agent-visible, routing the agent to phase-controller). An incremental seen-set dedupes so the same dirty path doesn’t re-warn on every command; every invocation appends a health record to scripts/bash-detector-health.jsonl. It is DETECTION, not prevention — the write already happened — and it supplements, never replaces the human verification contract (forced skill chain + the parent verifying outputs against the active plan). It does not see external-path writes, .gitignored paths, or deliberate evasion. When it warns, the contract is: cite the active run plan the work falls under, or invoke phase-controller to classify it — never dismiss the warning silently.

The shared policy library (hooks/_governance-common.sh). The exempt list, engine-scope detection, the D2 status-filtered active-plan check, and eos_list_active_plans (the post-compact reminder’s full-list variant) live in ONE sourced file, so the gate, the detector, and the post-compact reminder can never drift into disagreement. Consumers differ in failure posture on purpose: the gate fails CLOSED if the library is unreadable; the advisory hooks fail open (a detector must never break a session).

Advisory Enforcement (Rules + CLAUDE.md)¶

The mechanical layer handles what can be blocked with a shell script. The advisory layer handles everything else – quality standards, research discipline, methodology compliance, voice consistency, and the hundreds of judgment calls that cannot be reduced to a deny JSON response.

CLAUDE.md core behaviors are the top-level instructions. They survive context compaction because CLAUDE.md is always loaded (and .claude/rules/governance-baseline.md restates them unconditionally):

  1. Research before agreeing
  2. Push back with evidence
  3. Write as you go (log every file operation)
  4. Never delete, mark outdated
  5. Constitution from reality (describe what exists, not what was planned)
  6. Govern before producing (no deliverable writes without a run plan)
  7. Verify state before reporting (re-check filesystem/state claims against disk; backed by the unconditional evidence-first-reporting rule)

Four later behaviors extend the set: close out run plans at terminal state (2026-06-20, numbered 7 in governance-baseline.md — a plan that shipped gets its Status flipped the same session; leaving EXECUTING on shipped work is the documented anti-pattern), 7.5 — conjecture under rigor; never run the production line (2026-06-26: research-before-advising even in conversation, hold the whole arc, a miss is a gap not a failure), 7.6 — stand ready; don’t pre-route (2026-06-30, D50: on a full-breadth opener, self-orient from the capability snapshot then stand ready — catalytic context is for orientation, never scope), and 7.7 — communication economy; trim the prose, never the audit trail (2026-07-02, from an outside-reviewer verbosity critique that could see only a raw terminal transcript — no CLAUDE.md, rules, or hooks). Economy applies to conversational prose: drop “I’ll now…” pre-tool-call announcements, don’t restate a run plan back at kickoff, don’t narrate what a tool result already shows, collapse per-agent status churn into one batch summary. It never applies to the audit trail — the run-plan Layer 5 log, the Stop-hook CONTEXT.md check, and disk-verify-before-report (Behaviors 3/6/7) are the filesystem recovery point, invisible in a terminal transcript, and exactly what a disk-blind observer mistakes for overhead. Bounded by feedback_async_build_transparency (>5-min async builds still get a one-line status every 2-3 min) — economy is not silence. The two files number their additions differently (CLAUDE.md’s #7 is verify-state; governance-baseline’s #7 is run-plan close-out) — an inherited numbering quirk, not a content disagreement.

8 rules in .claude/rules/ provide specific enforcement instructions. 3 are unconditional (loaded every session):

  • governance-baseline.md – restates core behaviors with operator protection clauses
  • logging.md – specifies the two-layer logging model (activity log breadcrumbs + intelligence log strategic moments)
  • evidence-first-reporting.md – requires disk verification before filesystem/state claims. Its Delegated-Work Completion Verification section (added 2026-07-02) extends the rule to dispatched/background agents: a subagent’s “finished”/”done” is a claim about its own termination, not evidence its outputs exist on disk — an agent can return confident final text having written zero files. Before treating a phase complete, disk-verify each pre-declared output (phase-controller Rule 8 is what makes this mechanical), and treat a completion that coincides with a usage/session-limit reset (or any mid-run kill) as a red alert — distrust every in-flight agent’s status and disk-verify the whole batch, because partial or zero output is the expected shape there, not the exception. Re-dispatch only the missing pieces (never-delete what landed). Backed by patterns/problems/background-agent-completion-under-usage-limit.md.

5 are path-scoped (loaded automatically when working in matching directories):

  • engagement-structure.md – engagement directory conventions
  • integrations.md – CRM/Notion integration rules
  • living-projects.md – active project management rules
  • sandbox-tier.md – posture for the personal sandbox/ tier (D44): for-fun work under the same living-agent powers, firewalled from the professional layer, with a promotion path to OS Layer 1
  • methodology-immutable.md – protects methodology documents from unauthorized modification. Rule 5 (added 2026-06-12) sets precedence when a skill and its companion methodology doc diverge on operational specifics: the skill is the operational source of truth for existing divergence (methodology carries the why, skills the how, right now). Hardened the same day with a no-backdoor clause – creating a new skill↔methodology divergence is not a license to pick either; it still requires rule-1 operator approval.

The honest acknowledgment: Advisory enforcement depends on the agent following instructions. A sufficiently confident agent can ignore every rule, skip every skill invocation, and produce output that looks professional but followed none of the governance. This is not hypothetical – it happened in three consecutive sessions (WS3-WS5) where the agent skipped planning skills entirely while producing acceptable output. The mechanical layer (hooks) exists because advisory alone demonstrably fails on confident agents. The advisory layer remains essential for everything the mechanical layer cannot reach.

Phase-Controller – The Orchestration Brain¶

The phase-controller is the central governance skill. It classifies work into one of seven operation types, builds a disk-persisted run plan, forces skill invocation at every transition, and gates on operator approval before execution begins.

Why it exists: skills exist; methodology docs exist; the agent knows about all of them. Without forced orchestration, the agent defaults to “just do the thing” — skipping depth governance, quality checks, and structured findings. The root cause is not missing methodology. It is missing orchestration. Phase-controller is the orchestrator.

7 Operation Types¶

Every piece of work gets classified into one of seven types. Classification takes 60 seconds and determines the planning weight, skill chain, and criteria intensity.

Type Name When Planning Weight
BL Build/Audit System building, ecosystem auditing, capability compositing, engine construction, major methodology evolution Heavy
EW Engine Work Work within a specific engine tenant (research, deliverables, client tasks) Heavy
EN Engagement Client engagement work within an engine (campaign execution, meeting follow-up, deliverable production) Medium
RE Research Research tasks using OS-level research capabilities (market intelligence, competitive analysis) Medium
CP Content Production Deliverable/content creation (documents, HTML, presentations, reports) Medium
IN Integration CRM/Notion/MCP integration work (data sync, schema mapping, pipeline operations) Light
MT Maintenance OS-level maintenance, pattern updates, methodology review, skill refinement Light

Classification rules resolve ambiguity: multiple types classify by the heaviest type (an engagement requiring research is EN, not RE). If classification is unclear, the agent asks the operator rather than guessing. The key distinction between BL and MT: BL changes what the system IS; MT changes what the system HAS.

The 4-Step Flow¶

Step 1: Classify (60 seconds)¶

Read the intake context and classify. No brainstorming. No research. Just classify and present:

**Classification**

Type: CP -- Content Production
Basis: Primary deliverable is a document; operator provided structure and source files.
Engine: on-demand-curriculum
Scope signal: medium

Correct?

Gate: Do not proceed until the operator confirms.

Step 2: Build the Run Plan (write to disk)¶

Create the run plan artifact at a canonical path:

  • Engine work: engines/[name]/run-plans/[YYYY-MM-DD]-[short-name].md
  • OS-level work: run-plans/[YYYY-MM-DD]-[short-name].md

The run plan has a fixed 6-layer structure:

Layer Purpose When populated
Layer 0: Raw Intake Operator’s original input, captured verbatim At plan creation
Layer 1: Classification + Context Confirmed type, basis, current state, staleness check At plan creation
Layer 2: Skill Chain + Depth Ordered skill chain, depth assessment, gates, anti-pattern lint points, hardened criteria At plan creation
Layer 3: Research Findings Structured findings from research phases Appended during execution
Layer 4: Design + Plan Architecture, approach, implementation plan Appended after research; required before production
Layer 5: Execution Log Timestamped record of what was done Appended at every transition

Plus Not-Scope (what is explicitly excluded, never empty) and Deliverables (specific files with paths that will exist when the work is done).

This structure is not decorative. Layer 4 is a structural dependency for production steps (see Contract Hardening below). Layer 5 is the compaction recovery mechanism – if context compacts mid-execution, the run plan on disk shows what has been done and what remains.

Step 2.5: Contract Hardening¶

Before presenting the plan, the agent self-hardens its success criteria with three questions per criterion:

  1. Is this measurable? “High quality” is not a criterion. “All citations trace to Tier 2+ sources per credibility-tiers.md” is. If you cannot define a mechanical pass/fail check, the criterion is aspirational, not testable.

  2. What would a hostile reviewer add? For each criterion, imagine an evaluator whose job is to break the deliverable. What edge case would they check? What is the likeliest way to technically pass but miss the intent?

  3. Is the pass_definition specific enough to score? When someone later evaluates this work, can they answer YES or NO based on the pass_definition alone?

Criteria use structured JSON – not markdown – because models are less likely to tamper with structured JSON (per Anthropic’s research on contract formats):

[
  {
    "id": "C1",
    "criterion": "Control plane truth matches disk exactly",
    "threshold": 8,
    "pass_definition": "Grep verification passes: skill count = 28 (matches ls .claude/skills/ | wc -l), hook status = 'deployed' not 'planned' in CLAUDE.md",
    "fail_definition": "Any count in any control plane doc disagrees with disk reality after edits",
    "edge_cases": [
      "Skill count drift if new skill added mid-session",
      "Trailing newline counting differences"
    ]
  }
]

Criteria intensity scales by operation type: BL operations get 5-10 criteria; MT operations get 2-4.

Step 3: Present for Approval¶

The run plan summary is presented to the operator:

**Run Plan Written** -> engines/on-demand-curriculum/run-plans/2026-04-06-governance-doc.md

**Type:** CP -- Content Production
**Scope:** Governance reference documentation for EngineOS
**Skill chain:** [numbered steps]
**Gates:** [which steps require approval]
**Hardened Criteria:** 6 criteria -- sharpest: all hook code excerpts verified against disk
**Not-scope:** Modifying hooks or governance infrastructure
**Deliverables:** docs/governance.md

Approve to begin execution?

Gate: Do not proceed until the operator approves. Not silence. Not implied consent. Explicit approval.

Step 4: Execute with Forced Skill Invocation¶

Once approved, the run plan executes step by step under 11 forcing function rules.

11 Forcing Function Rules¶

# Rule Why it matters
1 Every skill in the chain gets invoked. Not referenced, not “kept in mind” – actually loaded and executed. Prevents the agent from skipping skills it considers unnecessary.
2 Sanity-check runs at every lint point. 2-minute spot-check against 11 known failure modes. Catches drift before it compounds.
3 Output-self-test runs before any “done” declaration. Binary YES/NO gates. NO means fix it before proceeding.
4 Gates are non-negotiable – but the operator may pre-authorize collapse. Work does not proceed past a gate without the operator’s explicit approval. Not silence. Not implied consent. The ratified collapse clause — its two narrow triggers, what never collapses, and its retroactive revocability — is spelled out once, in the Rule 4 emphasis below this table. The operator is the final enforcement layer. The collapse trigger is ALWAYS the operator’s explicit reduced-gating words or an approved disk plan – never the agent’s confidence, and never a detailed prompt on its own.
5 Every skill invocation gets logged in Layer 5. Audit trail for compaction recovery and post-session review.
6 The run plan is updated at every transition. Disk is the source of truth. If context compacts, the run plan is the recovery point.
6.5 Infrastructure updates happen BEFORE content presentation. Prevents drift between what the operator sees and what the files say.
7 Skipping a chain step requires justification. The chain is a minimum. You can add skills. You cannot silently skip them.
8 Subagent outputs are pre-declared in the run plan. Hook firing in subagent context is harness-version-dependent (fired as of 2026-06-12, falsifying the earlier “subagents don’t inherit hooks” reading) – the run plan, not the hook, is the durable governance contract for subagent work. After a subagent returns, the parent verifies each pre-declared output exists on disk and falls within the active plan’s scope.
9 Rendered artifacts require render-validate before COMPLETE. Visual verification via Puppeteer. QA scorecard must include a render verification row with PASS/FAIL.
10 Mandatory planning steps require explicit engagement or skip-justification. Steps tagged [MANDATORY] must be invoked or have a written justification visible to the operator. Silent skipping is a governance violation. Steps tagged [MANDATORY - structural] additionally require their output to exist in Layer 4 before production begins.
11 Evidence-before-reporting at phase transitions. Before writing results to Layer 5, CONTEXT.md, or any gate presentation, re-verify filesystem/state claims against disk. Counts, file existence, edit landings – verified via ls, wc -l, grep, Read, not from working context.

Rules 4, 10, and 11 deserve emphasis:

Rule 4 is why the operator matters. Every gate is a human judgment checkpoint. The system does not auto-approve. The operator reviews the work, asks questions, redirects if needed, and explicitly says “proceed.” This is not a rubber stamp – in production, the operator has caught the evaluator validating against the wrong baseline, redirected scope that was drifting, and rejected plans that were over-engineered for the task. The ratified collapse clause (2026-06-12, tightened the same day at guided review) formalizes a standing production practice under a deliberately narrow trigger: internal sub-phase gates collapse into logged self-reviews plus phase-boundary status updates ONLY when (a) the operator explicitly authorizes reduced gating in their own words, or (b) the operator approved a pre-existing disk plan and instructs its execution. A detailed task description alone – however thorough – is NEVER a collapse trigger; it authorizes the work, not reduced scrutiny. Two gates never collapse – Gate 0 (scope/classification approval; the operator’s prompt itself can satisfy it) and Gate Final (operator reviews the deliverable). Collapse is revocable retroactively: the operator may reopen any collapsed gate and re-review item by item, so collapsed-gate decisions are provisional until Gate Final passes. Every collapsed gate gets a Layer 5 log entry naming the verbatim pre-approval it rests on. (The original wording triggered collapse whenever a prompt “pre-approves scope, plan, and deliverables” – tightened after that breadth was found to license reduced scrutiny on a detailed prompt alone. Operator authorization may collapse gates; it never collapses diligence.)

Rule 10 addresses the demonstrated failure pattern where agents skip planning. In three consecutive sessions (WS3-WS5), the agent skipped both brainstorming and writing-plans skills entirely – while producing acceptable output. The enforcement model is two-tiered: [MANDATORY - structural] steps (writing-plans) create artifacts that the production step reads as a required input – empty Layer 4 means production cannot proceed. [MANDATORY] steps (brainstorming) use advisory enforcement with transparency – if skipped, the agent must write a justification visible to the operator at the approval gate. This asymmetry is intentional: structural enforcement works where artifacts are concrete; advisory enforcement with transparency works where artifacts are fuzzy.

Rule 11 addresses the verified-state-claim failure pattern. An agent declared a directory did not exist after 4 glob attempts. The actual path was WONDA-STUFF (all-caps, hyphens instead of spaces). That wrong negative propagated into an audit conclusion that an entire capability “never existed in sources” – structurally invalidating a quadrant of a capability audit. The operator found the path with one case-insensitive ls. Rule 11 requires re-verification against disk before any state claim at a phase transition.

The Iteration Envelope¶

The iteration envelope is a produce-evaluate-retry loop that wraps the production steps in skill chains. It’s the mechanism that turns independent evaluation from a concept into a repeating process: produce → evaluate → if criteria pass, advance; if not, fix the specific gaps and retry; max three retries before escalation. Quality gets enforced through repetition rather than through a single “did you check?” prompt that a confident agent can confidently skip.

How It Works¶

OUTSIDE ENVELOPE (runs once):
  depth-governor, brainstorming, writing-plans, operator approval gates

INSIDE ENVELOPE (iterates on failure):
  Produce deliverable
  -> adversarial-evaluator (independent context, scored JSON)
  -> IF PASS: exit envelope, proceed to next chain step
  -> IF FAIL: inject evaluation feedback -> re-produce -> re-evaluate
  -> After max retries: OPERATOR GATE with full iteration history

AFTER ENVELOPE (runs once on final version):
  qa-pipeline (if external-facing), operator approval, audit-logging

Configuration: - Max retries: 3. Matches the adversarial-dev and Anthropic guidance defaults. - Evaluator turn budget: 20 turns per evaluation, 3 iterations max = 60 evaluator turns per run plan. - Feedback injection: On failure, the evaluator’s critical_issues array and per-criterion feedback for failed criteria become additional context for the next produce attempt. - Operator escalation: When retries exhaust, the operator receives the full iteration history – all attempts, all scores, all feedback – and decides: accept as-is, give specific guidance, or take over manually. - Skip condition: The operator can say “skip evaluation” at any approval gate. This is the only way to bypass the envelope. The agent cannot skip it on confidence.

Run plan logging per iteration:

[timestamp] Iteration 1: adversarial-evaluator scored avg 6.2. Failures: [C2: 5/10, C4: 6/10]. Feeding back.
[timestamp] Iteration 2: adversarial-evaluator scored avg 7.8. PASSED (all criteria >= threshold).

Adversarial Evaluator¶

The adversarial evaluator is a subagent with three architectural properties that make it structurally different from self-evaluation:

Independent context. The evaluator subagent does NOT share the executor’s session. It receives only deliverable paths, criteria JSON, pass threshold, and a one-line task description. It cannot see the executor’s reasoning, run plan, or conversation history. This independence is why agent judges disagree with humans only 0.3% of the time, versus 31% for single LLM self-judges (Agent-as-a-Judge, arxiv:2508.02994).

Tool asymmetry. The evaluator has Read, Bash, Glob, and Grep tools. It does NOT have Write or Edit. It can read files and run verification commands. It cannot fix what it finds. This is adapted from the adversarial-dev evaluator pattern – the evaluator’s job is to find problems, not to solve them.

Mechanical distrust. The executor does NOT trust the evaluator’s self-reported passed field. It recalculates:

passed = ALL criteria scores >= their individual thresholds

If the evaluator says "passed": true but any criterion scores below threshold, the executor overrides to false. The evaluator is an LLM – it can misjudge its own summary. The scores are the source of truth.

If the evaluator’s output cannot be parsed as JSON (all three parsing strategies fail), the result is a hard fail: all scores = 0, passed = false. Parse failure is treated as evaluation failure. This is the punitive default – a malformed evaluation does not silently pass.

Real Example: Planning-Enforcement Methodology Doc¶

The production of methodology/planning-enforcement.md (WS6) required 3 iterations through the envelope. The adversarial evaluator caught fabricated citations in the first two attempts – the concepts being cited were real (Cole’s adversarial-dev, Anthropic’s guidance), but the specific quotes attributed to those sources were generated from training data rather than verified against the actual documents. The output-self-test skill passed both times – self-evaluation cannot detect fabricated citations because the agent that wrote them believes they are correct.

Iteration 1: avg 6.8 — C3 (source fidelity) scored 5/10.
    Evaluator feedback: "Quotes attributed to Cole's harness.ts are plausible but not
    verifiable from the codebase. Specific line numbers cited but content doesn't match."
Iteration 2: avg 7.2 — C3 scored 6/10.
    Evaluator feedback: "Training-data citations removed but replaced with paraphrases
    still attributed as direct quotes."
Iteration 3: avg 8.1 — PASSED. All criteria >= threshold.
    Citations restructured as summaries with explicit source-type markers.

This example demonstrates the core value of independent evaluation: the agent was confident its citations were accurate. Self-tests confirmed that confidence. Only an independent context – one that read the actual source files and compared them against the cited content – caught the discrepancy.

Retrieval Architecture¶

The mechanical-enforcement layer described above is governance-by-blocking: hooks deny tool calls, force run plans, and re-inject behaviors after compaction. The retrieval architecture is the sister mechanism – governance-by-information-flow. It does not block; it changes what the agent sees by the time it acts. Where mechanical enforcement closes “research before producing,” retrieval closes “research before agreeing” applied to the agent’s own corpus.

The architecture was added 2026-06-04 per DECISIONS.md D32. The trigger was an audit finding (D32 Context): EngineOS had strong CAPTURE – flush.py + compile.py + 216 KB articles + 70+ intel-log entries + 18 daily logs + 27 run plans at the time – but weak RETRIEVAL. During normal work the agent rarely read concept articles or queried the intel log. Mid-task focus suppresses reflexive internal-archive lookup. Capture without retrieval was a write-only system. For full architecture detail, decision rationale, and the why-not-vector-DB analysis, see docs/source/second-brain.md and methodology/memory-architecture.md § Retrieval Surfaces. This section covers the governance-relevant slice.

Three Layers¶

Layer Mechanism Fires when Coverage target
1. Session-start injection hooks/session-start.py (Hook 6) Every session start Orientation – full KB index + last 30 lines of today’s daily log at ~20K cap
2. Mid-work retrieval hook hooks/prompt-retrieval.py (Hook 5, UserPromptSubmit) Every prompt matching the heuristic gate ~90% – silent, mechanical, ≤1024 chars, ≤1s, top-3 from 6-surface corpus
3. Manual escalation .claude/skills/recall/ (/recall <query>) Operator or agent invocation when hook missed or deeper sweep needed ~10% – explicit, ranked, no cap

Layer 1 establishes orientation. Layer 2 fills in mid-work context mechanically. Layer 3 escalates when the hook misses or the decision is load-bearing.

Six-Surface Priority Corpus¶

All three layers read the same six surfaces in the same priority order:

# Surface Density of value Best for
1 logs/intelligence-log.md Highest (curated strategic moments) “What did we learn / decide / observe?”
2 knowledge/index.md High (catalog with summaries) “Do we have an article on X?”
3 knowledge/concepts/*.md + connections/*.md High in single article “Read the article on X”
4 daily/*.md (last 30 days) Medium (recent in-flight context) “What were we doing recently on Y?”
5 run-plans/*.md (last 60 days) High in single plan “Recent plan-and-execution for Z”
6 methodology/*.md Highest in matched doc “Official approach to W”

Higher surfaces have higher signal-to-noise. Stopping rule: when surfaces 1-2 yield 3+ strong hits, lower surfaces are skipped. The whole corpus is markdown – structured KB index + ripgrep + LLM-reads-relevant-files outperforms vector retrieval on precision at personal-KB scale (currently 454 notes, against a <500-article research threshold). Vector DB / GraphRAG / Mem0-style frameworks are Phase C deferred with explicit revisit conditions in D32 (corpus >2000 articles, sustained semantic-miss complaints, etc.).

Discipline + Pattern Pairing¶

The mechanical layer is paired with an advisory discipline so retrieval still fires when the hook’s heuristic gate misses:

  • Framework pattern retrieval-before-decide – the read-side discipline. Before making an architecture/methodology decision in a domain where prior intelligence likely exists, query the second brain first. The discipline names the moments where the hook’s word-based gate isn’t reliable (the prompt may not contain “we” or start with “what” yet the decision is load-bearing).
  • Sister discipline session-end-audit-before-flush – the write-side discipline. For multi-day or multi-deliverable sessions, run a coverage audit before flush.py to ensure marathon-session content gets captured.
  • Feedback memory feedback_lookup_before_decide.md – auto-fire trigger phrases that the agent learns to recognize as discipline-invocation moments.
  • Companion skill recall – the manual escalation, pure Read/Grep/Glob, zero API cost. Invoked via /recall <query> or when the agent recognizes a discipline moment.

Together the four pieces close both halves of the loop: capture (write-side) + retrieval (read-side), mechanical (hook + skill) + advisory (discipline + feedback).

Measurement¶

The retrieval layer is governance-grade because it is measured. scripts/retrieval-health.jsonl is append-only, one record per UserPromptSubmit invocation. Schema: ts, session_id, prompt_chars, query_terms, gate_triggered, gate_reasons, corpus_searched, matches_found, matches_returned, chars_injected, exec_ms, result. The operator runs scripts/retrieval-review.py after ~10 sessions and applies the keep/tune/kill rules from D32:

  • Gate hit rate <10% sustained → too quiet; loosen triggers or kill hook (rely on /recall only)
  • Gate hit rate >60% sustained → too noisy; tighten triggers or keep if injections useful
  • Mean chars_injected near 1024 cap → consider bumping cap
  • Operator marks injections subjectively; if >50% noise → tighten or kill

This is the same evidence-based keep/tune/kill cadence used by the capture-side health log (see Observability below). Three new binary tests added to memory-architecture (#10-#12) verify the layer fires per session.

Observability¶

Both the capture-side and retrieval-side mechanical layers emit structured health logs. The operator reviews them periodically – the system does not silently degrade.

  • scripts/hook-health.jsonl (DECISIONS.md D30) – one record per flush.py invocation. Schema includes attempt count, retry success/failure, exec time, cap hits, response size. scripts/health-review.py summarizes failure rate, retry rate, cap-hit distribution, recent-records table.
  • scripts/retrieval-health.jsonl (DECISIONS.md D32) – one record per UserPromptSubmit invocation (see Measurement above). scripts/retrieval-review.py summarizes gate hit rate, injection size distribution, top query terms, top gate-fire reasons, exec-time distribution.
  • scripts/bash-detector-health.jsonl (D34) – one record per firing of the ungoverned-write detector (Hook 10): changed/ungoverned/newly-warned counts, warned flag, exec time. Fire-rate instrumentation for the detection-not-prevention surface.

A telemetry layer also sits above the hooks: scripts/reviewer-health.jsonl (D36) records every federated-reviewer firing — sanity-check, output-self-test, adversarial-evaluator, independent reviewers — with reviewer, surface, verdict, flagged count, and leads_surfaced. It is a LIVENESS instrument, not an impact scoreboard: all-pass is its architecturally expected shape, because real catches route to run-plan Layer 5 and the intelligence log (Category=Review) per D36. scripts/reviewer-review.py runs the periodic keep/tune/kill review over it. The ladder itself is patterns/frameworks/federated-reviewer.md.

D30 also added a 2-attempt retry loop (3s sleep) wrapping query() calls in both flush.py:run_flush() and compile.py:compile_daily_log(). The retry absorbs transient SDK errors (concurrent-session lock, rate, OAuth refresh) cheaply; the health log captures evidence about whether deeper investigation is warranted. If retry-success-rate stays high, the layered fix IS the answer; if flush_error rate stays >5% after retries, that’s the real signal to escalate. The operator runs health-review.py ad hoc when suspecting drift – not on a fixed cadence. Operator-driven keep/tune/kill.

A related operational fix is captured in DECISIONS.md D31: Python’s print() uses block buffering when stdout is a file, which had made compile.py look silently broken for ~3 weeks (compile.log mtime froze) when it was actually running fine intermittently. Fix is one line – sys.stdout.reconfigure(line_buffering=True) at the top of compile.py:main(). Also added: propagation of CLAUDE_INVOKED_BY=knowledge_compile BEFORE imports that could trigger Claude Code, preventing recursive SessionEnd → flush.py → compile.py → SessionEnd loops from spawning noise daily-log entries. The buffering insight is captured as an intelligence-log entry and as the block-buffered-stdout-masks-progress pattern – reusable across any future background-spawn pattern.

Quality Gates – How They Layer¶

EngineOS has four quality gate mechanisms. They are not interchangeable — each catches a different class of failure, and they layer in a specific order. output-self-test is the fast binary gate (seconds, YES/NO per output type). qa-pipeline is the structural+content+visual sweep. sanity-check is the periodic spot-check against known failure modes. adversarial-evaluator is the independent-context judge that scores against hardened criteria. Layered, they catch what any single check would miss.

output-self-test (Fast Binary Gate)¶

Binary YES/NO questions per output type. Runs before any “done” declaration. Takes seconds per test. 5 test batteries: Research Output (RS), Content/Deliverable (CD), Integration Output (IO), HTML Output (HD), and Cross-Cutting (XC, always runs).

Each test has a quick version (for scan-depth work) and a thorough version (for deep-dive work). Every test follows four design rules: answerable YES/NO in under 5 seconds, references specific parts of the output, a NO implies a specific fix, and paired quick/thorough versions.

What it catches: Structural problems – missing citations, placeholder text, generic output, voice mismatch, broken formatting. What it misses: Fabricated citations that look correct, criteria that technically pass but miss the intent, quality issues invisible in a quick skim.

sanity-check (Periodic Spot-Check)¶

11 known failure modes, each with a binary test. Runs at natural pause points during execution – not at every commit, not mid-sentence, but at phase boundaries and after producing substantial output. Takes under 2 minutes.

The 11 failure modes (the gallery is honest about provenance: an entry either cites a real production incident or carries an explicit declared-seed note awaiting its first observed instance — 3 are incident-grounded so far, and seeds get grounded or culled as the gallery is touched):

# Failure Mode Quick Check
1 Premature Confidence Am I calling something settled based on thin evidence?
2 Staleness Blindness Am I acting on intel older than 2 weeks without checking?
3 Scope Ratchet Has what we’re targeting changed without deliberate decision?
4 Generic Output Am I producing generic output instead of specific output?
5 Claim Hallucination Is every claim traceable to documented evidence?
6 Missing Source Trail Can I trace each claim to a specific source?
7 Contradictory Frame Does this output hold conflicting assumptions?
8 Agent Hallucinated Success Did an agent report success but the data didn’t change?
9 Depth Miscalibration Am I doing deep-dives on everything or scans on everything?
10 Cross-Engine Contamination Is research from one engine bleeding into another?
11 Unverified State Claim Am I reporting from memory instead of re-verifying?

What it catches: Drift patterns that accumulate during execution. What it misses: Novel failure modes not yet in the gallery. Quality issues that require independent context to detect.

adversarial-evaluator (Independent Evaluation)¶

Scored evaluation by an independent-context subagent. Runs inside the iteration envelope during production. 20-turn budget per evaluation. Evaluates against the run plan’s hardened criteria.

What it catches: Self-evaluation blind spots – fabricated citations, criteria gaming, quality issues that the producing agent cannot see because it shares context with the reasoning that produced the work. What it misses: Failure modes outside the hardened criteria. Visual/rendering defects that require a browser.

qa-pipeline (Final Comprehensive Gate)¶

4-stage composited verification for external-facing deliverables:

  1. Stage 1: Programmatic Checks – Citation compliance (find all numeric claims, verify citations exist), marketing language detection (5 categories of promotional language), cross-document consistency (track data points across files, flag discrepancies), source freshness (flag citations older than 12 months), faithfulness (verify cited sources actually support claims – dispatches independent subagent at Comprehensive depth).
  2. Stage 2: Binary Self-Tests – Invokes output-self-test batteries in the context of the full pipeline. Cross-references with Stage 1 findings.
  3. Stage 3: Visual Verification – HTML outputs only. Renders in a real browser via Puppeteer. Screenshots every section. Audits against a checklist covering diagrams, interactivity, layout, typography, and color. Catches four defect classes invisible in source: hidden elements, broken interactivity, missing enhancements, non-persisting state.
  4. Stage 4: Domain-Specific Standards – Professional checklists by deliverable type (reports, campaigns, lead lists, one-pagers, presentations, HTML interactives). Severity classification (Critical/High/Medium/Low) for every issue found across all stages.

What it catches: Everything the previous gates might miss when the deliverable is going to an external audience. What it misses: Nothing in scope – this is the comprehensive final gate.

The Layering Order¶

output-self-test  (fast, every "done" declaration)
    |
sanity-check  (periodic, at natural pause points)
    |
adversarial-evaluator  (inside iteration envelope, scored against criteria)
    |
qa-pipeline  (final gate, external-facing deliverables only)

Each layer is progressively more expensive and catches progressively subtler failures. output-self-test runs in seconds and catches structural problems. sanity-check runs in 2 minutes and catches drift patterns. adversarial-evaluator runs a full subagent and catches self-evaluation blind spots. qa-pipeline runs programmatic scans, self-tests, browser rendering, and domain checklists – it is the comprehensive gate that only fires for work going outside the system.

Run Plans – Planning Artifacts AND Gate Keys¶

The key architectural insight: run plans serve two purposes simultaneously.

1. Planning artifact (advisory). The phase-controller creates a run plan that captures the raw intake, classifies the work, specifies the skill chain, hardens the success criteria, and persists execution state across compaction boundaries. The plan guides execution.

2. Mechanical gate key (blocking). The PreToolUse hook checks for the run plan’s existence on disk before allowing deliverable writes. No run plan at the canonical path = no writes. The plan unlocks execution.

This is the bridge between advisory and mechanical enforcement. The run plan is created by the advisory system (phase-controller skill) and consumed by the mechanical system (pre-write-governance.sh hook). Without the bridge, the two layers would be independent — the agent could ignore advisory governance and have its writes blocked, or the hook could be permissive while advisory governance went unenforced. The run plan makes them interdependent.

Canonical paths (enforced by hook v2 scope-matching): - Engine work: engines/[name]/run-plans/[YYYY-MM-DD]-[short-name].md - OS-level work: run-plans/[YYYY-MM-DD]-[short-name].md

No nested subdirectories. The hook scans at -maxdepth 1. Legacy paths like engines/X/pipeline/run-plans/ are deprecated.

The Operator as Final Enforcement Layer¶

EngineOS does not claim to be self-governing. The operator is the final enforcement layer.

Gates require explicit approval. Not silence, not implied consent, not “I think they would want…” The agent stops and waits. In production, this means the operator reviews the work, asks questions, pushes back on scope, redirects approach, and says “proceed” only when satisfied. The operator has caught the evaluator validating against the wrong baseline, redirected substrate work that was drifting toward feature scope, and collapsed gate boundaries when the plan was well-designed and pre-approved.

Operator overrides advisory guidance. The operator’s explicit instructions override all guidance except safety constraints. If the operator says “skip evaluation,” the iteration envelope is bypassed. If the operator says “proceed without a full plan,” the agent proceeds. The governance exists to serve the operator, not to constrain them.

Cross-engine scope requires confirmation. If a task would modify files in multiple engines, the agent confirms scope with the operator first. This prevents unintended cross-engine contamination.

Iteration exhaustion escalates to operator. When the adversarial evaluator fails a deliverable 3 times, the agent does not decide what to do. It presents the full iteration history – all attempts, all scores, all feedback – and the operator decides: accept as-is, provide specific guidance for another attempt, or take over manually.

The operator can skip the iteration envelope by saying “skip evaluation” at any approval gate. This is the only way to bypass the envelope. The agent cannot skip it on its own confidence – that is the advisory-governance-failure pattern, the exact behavior the enforcement stack was built to prevent.

The system works because the operator is engaged. This is stated plainly in CLAUDE.md and repeated here without apology: methodology-as-infrastructure for a single engaged operator is not the same as deterministic enforcement, and it does not claim to be. What it claims – and what the evidence from 100+ days of production use supports – is that mechanical hooks catch what advisory governance misses, advisory governance covers what mechanical hooks cannot reach, and the operator catches what both miss.
