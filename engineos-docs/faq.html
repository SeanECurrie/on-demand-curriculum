FAQ — Technical Peer Questions¶

Questions a developer, systems architect, or technical reviewer would actually ask about EngineOS.

Architecture¶

“Why not just use a monolithic prompt?”¶

Because context is finite and expensive.

The Sales Enablement Engine (SEE), EngineOS’s primary donor, started with a monolithic approach: load all 49 skills, all patterns, all templates at session start. It worked when the system was small. At scale, it consumed so much of Claude Code’s context window that there was barely room for the actual work.

EngineOS’s four-tier context budget (D11) reduced context consumption by 68%. Tier 1 loads ~340 lines unconditionally (the constitution). Tier 2 adds rules only when you touch files in matching paths. Tier 3 loads skill descriptions passively at ~2% and full content only on invocation. Tier 4 (methodology, patterns, templates) loads only when explicitly needed.

A session that uses 3 of 29 skills loads 3 skills, not 29. The savings compound with every additional skill that doesn’t need to load.

See Architecture for the full four-tier model.

“How does context not explode with 29 skills, 70 patterns, and 15 methodology docs?”¶

The four-tier loading model means most of that content never enters context during a typical session. Skills are discovered via one-liner descriptions (~2% of context); their full content (sometimes 700+ lines) loads only when invoked. Patterns are loaded only when a failure mode is detected. Methodology docs load only when a skill chain mandates them (e.g., the BL chain requires ecosystem-build.md).

The key design decision (D12) was making CLAUDE.md a short routing layer, not a reference manual. SEE’s 918-line CLAUDE.md tried to be comprehensive. EngineOS’s CLAUDE.md (currently ~160 lines) points to detail stored elsewhere, loaded on demand.

“What happens when the context window fills up?”¶

Claude Code compacts older context. EngineOS is designed for this:

  1. PostCompact hook fires and re-injects core governance behaviors, active run plan awareness, and engine tenant list.
  2. Run plans on disk are the primary recovery mechanism. The run plan shows what’s been done (populated layers) and what’s next. Execution resumes from the last completed step.
  3. CONTEXT.md is always current (the Stop hook warns if it wasn’t updated). It’s the handoff mechanism.
  4. Tier 1 files are re-read on every interaction after compaction.

The design principle: anything that must survive compaction lives on disk at a predictable path. The context window is a working space, not a storage system.

“How is this different from just having a really good CLAUDE.md?”¶

A CLAUDE.md gives you instructions. EngineOS gives you infrastructure.

The difference is enforcement. A CLAUDE.md says “always run quality checks before declaring done.” EngineOS has a PreToolUse hook that mechanically blocks deliverable writes without an active run plan, a phase-controller that forces quality skills into every production chain, an adversarial evaluator that scores output with independent context, and iteration envelopes that automatically retry on failure.

When a confident AI agent judges that it doesn’t need the planning step (documented across 3 consecutive sessions — WS3-WS5), the CLAUDE.md instruction gets skipped. The hook doesn’t care how confident the agent is.

Governance¶

“What does the enforcement actually do? Can’t the AI just ignore it?”¶

The enforcement has two layers, and they’re honestly different in how hard they are to ignore.

Mechanical enforcement (hooks) cannot be bypassed by the agent. The PreToolUse hook intercepts every Write and Edit tool call. If there’s no recent run plan at the correct scope-matched path, it returns permissionDecision: "deny" and the tool call doesn’t execute. The agent can’t write the file. Period.

Advisory enforcement (rules, CLAUDE.md, skill chains) depends on the agent following instructions. It works most of the time — ~90% — but fails predictably when the agent is confident about a straightforward task (the advisory-governance-failure pattern, documented from the J3 “Sardine resume” incident).

EngineOS is honest about this gap. From CLAUDE.md: “This is methodology-as-infrastructure for a single operator. It works because the operator is engaged. It does not claim to be deterministic enforcement.” The mechanical hooks catch the cases where advisory enforcement fails. The operator catches everything else.

See Governance for the full enforcement stack.

“Why not make everything mechanical?”¶

Because you can’t mechanize judgment.

A hook can check “does a run plan exist?” (binary, deterministic). It can’t check “is this research synthesis well-reasoned?” or “does this campaign match the client’s voice?” Those require semantic evaluation, which is what the advisory layer (rules, skill chains, adversarial evaluator) provides.

The split is deliberate: mechanical enforcement for deterministic operations (logging every write, checking for run plans), advisory enforcement for semantic operations (quality assessment, depth classification, research credibility). The operator is the final layer for everything else.

“What happens when the adversarial evaluator disagrees with the output?”¶

The iteration envelope retries. The deliverable is reproduced with the evaluator’s feedback injected (specifically, the critical_issues array and per-criterion feedback for failed criteria). The evaluator scores again. If it passes, the envelope exits. If it fails again, another retry. After 3 failed attempts, the system stops and escalates to the operator with the full iteration history — all attempts, all scores, all feedback.

The evaluator runs in independent context (a subagent with no access to the executor’s working state). It receives only the deliverable and the success criteria JSON. This prevents the evaluator from being influenced by the executor’s reasoning. Mechanical distrust is built in: the system recalculates pass/fail from the raw scores rather than trusting the evaluator’s self-reported passed field.

Real example: During the WS6 planning-enforcement.md production, the evaluator caught fabricated citations in iterations 1 and 2. The agent had generated plausible quotes attributed to specific source locations that didn’t exist. The self-tests (output-self-test) passed both times — confirming that self-evaluation has structural blind spots that only independent evaluation catches.

“What’s in a run plan? Why disk-persist it?”¶

A run plan is a 6-layer markdown artifact: - Layer 0: Raw intake (what the operator said, uninterpreted) - Layer 1: Classification + context (operation type, current state, staleness check) - Layer 2: Skill chain + depth (ordered sequence of skills, gates, hardened success criteria) - Layer 3: Research findings (appended during execution) - Layer 4: Design + plan (appended after research — structural enforcement requires this to be populated before production begins) - Layer 5: Execution log (timestamped skill invocations and results)

It’s disk-persisted for two reasons: 1. Compaction resilience. If the context window fills and compacts, the run plan on disk is the recovery point. Read it, find the last completed step, resume. 2. Mechanical gate key. The PreToolUse hook checks for a recent .md file at the canonical run-plans path. The run plan’s existence is what unlocks deliverable writes. This bridges the advisory enforcement (phase-controller creates the plan) and mechanical enforcement (the hook checks for it).

See Governance for a real run plan example.

Methodology¶

“Why patterns over more rules?”¶

Patterns and rules serve different purposes.

Rules encode process: “always log file operations,” “verify state before reporting,” “don’t modify methodology without approval.” They’re about what to DO.

Patterns encode experience: “here’s a failure mode we observed, here’s the incident that produced it, here’s how to recognize it, here’s how to prevent it.” They’re about what to WATCH FOR.

EngineOS has 7 rules and 70 patterns. The rules are few because process should be minimal. The patterns are many because the system has encountered many failure modes across 105+ days of production work. Every pattern comes from a real incident — none are hypothetical.

The sanity-check skill’s 11 spot-check tests are the bridge: they encode specific pattern-derived failure modes as quick binary checks that run periodically during work.

See Patterns Reference for 10 key patterns with their incident stories.

“Why ‘never-delete’? Doesn’t that just create bloat?”¶

The cost of losing history is asymmetric.

Three failure modes that never-delete prevents: 1. The vanished rationale. A decision was made six weeks ago. Why? If the context was deleted, you pay the full cost of re-researching it. If it was marked outdated with a reason, the rationale is still there. 2. The repeated experiment. A configuration was tried and failed. Without a trace, you’ll try it again. With a trace, you skip it. 3. Undetectable drift. Small deletions accumulate. After 20 sessions, the system has quietly changed and nobody noticed. Append-only history makes drift visible.

In practice, the mechanism is lightweight: outdated content gets a date and reason stamp. Active content stays clean. CONTEXT-HISTORY.md archives older context entries so CONTEXT.md stays focused. Logs are append-only by nature.

“What’s the difference between sanity-check and output-self-test?”¶

Output-self-test runs before declaring work complete. It’s a battery of binary YES/NO tests calibrated by output type (Research, Content, Integration, HTML, Cross-Cutting). “Does every recommendation have evidence behind it?” YES or NO. A NO means fix it before proceeding. It’s fast — 30-60 seconds.

Sanity-check runs periodically at natural pause points during work. It checks for 11 known failure modes: Premature Confidence, Staleness Blindness, Scope Ratchet, Generic Output, Claim Hallucination, Missing Source Trail, Contradictory Frame, Agent Hallucinated Success, Depth Miscalibration, Cross-Engine Contamination, Unverified State Claim. Each failure mode has a binary test and a citation to the real production incident that created it. It takes about 2 minutes.

Output-self-test asks “is this output ready?” Sanity-check asks “am I making known mistakes right now?”

Memory and Retrieval¶

“How does EngineOS find prior context during work?”¶

Three layers, none of them a vector database.

  1. SessionStart injection – when a session opens, the hook reads recent CONTEXT.md, recent daily logs, and the active run plan (if any) into the prompt. Prior-session continuity is automatic, not on-demand.
  2. UserPromptSubmit retrieval hook – when the operator submits a prompt, a lightweight ripgrep pass across KB articles, intelligence log, recent daily logs, and active run plans surfaces matching prior context and injects it as a <prior-context> block before the agent sees the prompt. This is the “did we already think about this” guardrail.
  3. /recall skill (manual) – when the operator (or the agent) wants to query the second brain explicitly, the recall skill runs Read/Grep/Glob across knowledge index, intelligence log, KB articles, recent daily logs, and recent run plans. Pure filesystem search, zero API cost.

See Second Brain for the full architecture.

“What’s the second brain?”¶

EngineOS’s persistent memory layer. Five components:

  • knowledge/ – distilled KB articles (the durable lessons)
  • daily/ – per-day session journals (the rolling stream)
  • logs/intelligence-log.md – strategic moments (insights, not actions)
  • knowledge/concepts/ – named concepts the operator and OS share vocabulary on
  • Capture pipeline (scripts/flush.py, scripts/compile.py) + retrieval surface (/recall skill, prompt-retrieval hook, SessionStart injection)

Everything is markdown on disk. Nothing requires a running service. See Second Brain for the full pipeline.

“Why no vector DB?”¶

D32 answered this explicitly: at the current scale (well under 500 KB articles), ripgrep over markdown beats a vector index on three axes – speed, simplicity, and trustworthiness of the results. There is no embedding drift, no index staleness, no separate service to keep alive. The operator can read the same files the retrieval layer reads.

The decision is not permanent. D32 sets a revisit threshold: if the KB exceeds roughly 2000 articles, or if cross-domain semantic queries start missing matches that obviously should hit, the architecture gets re-evaluated. Until then, ripgrep wins.

Engines¶

“Could someone else use this system?”¶

Yes. EngineOS is operator-agnostic by design.

The operator/ directory personalizes the system through a structured Phase 0 onboarding process (37-question intake via the profile-builder skill). The OS and its engines work for anyone. Nothing in the governance, methodology, skills, or patterns assumes a specific person. The operator identity is layered on top, not baked in.

A new user would: 1. Clone the system 2. Run the session-orchestrator (detects missing PROFILE.md, triggers Phase 0) 3. Complete the 37-question intake (the skill generates tailored questions from any source material provided) 4. The system generates PROFILE.md, COLLABORATION-STYLE.md, and WRITING-STYLE.md 5. Everything personalizes around the new operator

The engine tenant model means domain-specific work lives in isolated tenants. A new user could create their own engines without touching the existing ones.

“How do you add a new engine?”¶

Four steps: 1. Create engines/<engine-name>/ with README.md, CONTEXT.md, DECISIONS.md 2. Add domain-specific directories as needed (engagements, knowledge, projects, skills) 3. Register the engine in registry/engines.md 4. Domain-specific skills that don’t generalize stay in the engine directory at engines/<engine-name>/.claude/skills/

The engine inherits all OS-level capabilities automatically. It references OS skills, methodology, patterns, and the design system. It doesn’t duplicate them.

See Engine Model for the full tenant architecture.

Process¶

“What’s the biggest thing that went wrong during the build?”¶

Four candidates:

  1. Advisory governance failure (J3). The phase-controller was designed to classify every operation and create a run plan. During the J3 session, the agent was asked to create a resume (straightforward task). It skipped phase-controller entirely — went straight to file loading, resume writing, DOCX generation, inline QA. The resume was 9.8/10 quality. But governance failed completely. This led to D22: mechanical enforcement via PreToolUse hook.

  2. Act 3 lift regression. When building EngineOS from 11 source projects, the capability lift systematically missed top-level scripts/ directories and variant script locations. SEE’s 891-line Attio direct API suite, notion-mapper’s 43KB of Python scripts — all missing. Discovered accidentally during a JSE pipeline operation. Required a dedicated restoration operation (D26).

  3. The WONDA-STUFF incident. During an audit, an agent declared ~/Desktop/wonda stuff/ doesn’t exist after 4 glob-variant attempts. The actual path was WONDA-STUFF (all-caps, hyphens). That strong negative propagated into “Attio direct-API never existed in sources” — invalidating an entire audit quadrant. Led to the evidence-first-reporting unconditional rule, the confident-negative-finding pattern, and sanity-check spot-check #11.

  4. Capture without retrieval. For the first several weeks of EngineOS production, the second brain accumulated KB articles, daily logs, and intelligence entries reliably – but nothing surfaced them back to the agent during work. The operator kept catching the OS re-deriving conclusions it had already reached and written down. The gap was retrieval: capture was solved, lookup was not. D32 closed the loop with the three-layer retrieval architecture (SessionStart injection, UserPromptSubmit hook, /recall skill) and explicitly rejected vector-DB infrastructure at current scale.

Each failure produced concrete infrastructure improvements. The system learned from its mistakes in a way that prevents recurrence.

“How was this documentation produced?”¶

By EngineOS itself, using the On-Demand Curriculum engine.

The operation was classified as Type A (New Output from Scratch) by the ODC’s pipeline-start skill. A design doc was produced through the brainstorming process. Three parallel audit agents read every source file in the system (all 29 skills, 15 methodology docs, 70 patterns, 8 wired hook events, 7 rules, 4 engine tenants, design system, templates, decisions, intelligence log). 13 reference docs were produced by parallel subagents reading source files directly. This FAQ was written last because it draws from all other docs. The HTML walkthrough was built section-by-section using the section-construction methodology.

The operation was governed by a disk-persisted run plan at engines/on-demand-curriculum/outputs/engineos-documentation/run-plans/2026-04-06-engineos-documentation.md. The PreToolUse hook verified the run plan existed before every file write. The meta-demonstration is real: this documentation is a product of the system it describes.
