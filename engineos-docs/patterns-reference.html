What Patterns Are in EngineOS¶

Every pattern in this library comes from a real production incident. Nothing is hypothetical. Each pattern encodes a failure mode that was observed in actual work, analyzed to find its root cause, and converted into a reusable lesson with clear trigger conditions and solutions.

The pattern format is consistent: provenance header (source project, last verified date, staleness status), problem statement, step-by-step solution, when to use, when not to use, concrete example from real work, variations, and origin story. Every pattern traces back to a specific engagement, session, or test that produced it.

Breakdown: 58 problem patterns, 5 deliverable patterns, 7 framework patterns.

Key Patterns – Deep Examples¶

The following 10 patterns are presented in full detail. They were selected because they tell the story of how EngineOS learned from its own production work. Each one traces back to a specific incident where something went wrong, was analyzed, and became permanent institutional memory.

1. Confident Negative Finding¶

Category: Governance & Validation | Type: Problem

The Problem: When an agent declares “X does not exist” with confident framing, that finding becomes a premise for downstream analysis. If the finding is wrong, everything built on top of it is structurally invalidated – not just incorrect in one detail, but wrong at the foundation. The cost of a wrong negative is asymmetric: a wrong positive gets corrected when someone looks closer, but a wrong negative closes off investigation entirely.

The Incident: During a capability lift audit in April 2026, an agent needed to verify whether Attio direct-API code existed in the WondaKB source project. The operator had referenced ~/Desktop/wonda stuff/attio-mcp-claude-code-agent/. The exact path returned “No such file or directory.” The agent generated 4 glob variants (lowercase/capitalized combinations of “wonda” and “attio”) and declared with confidence: “does not exist on this machine.”

That strong negative propagated upward. The agent concluded: “Attio direct-API never existed in sources either – never-existed gap on both sides.” An entire quadrant of the audit (Attio capability lineage) was classified as “never-existed, not a regression.”

The actual path was /Users/seancurrie/Desktop/WONDA-STUFF/attio-mcp-claude-code-agent/ – ALLCAPS with hyphens instead of spaces. The canonical Attio direct-API code was an 889-line attio-direct-api.js file sitting at the unsearched path the entire time. The operator found it with a single ls ~/Desktop/. The audit had to be redone with the full capability inventory.

The Solution: Use weak framing (“I couldn’t find X at the expected path – verify?”) when verification is incomplete. Treat negative findings as intermediate state requiring verification, not as terminal conclusions. When propagating into downstream analysis, flag the dependency explicitly so a single correction can unwind the chain.

The Lesson: Confidence should be calibrated to search thoroughness, not to how decisive the conclusion feels.

2. Path Search Discipline¶

Category: Governance & Validation | Type: Problem

The Problem: When looking for a file or directory, there are two approaches: variant-hunting (generating guesses and testing them) and searching (looking at what is actually there). They feel similar but produce fundamentally different reliability. Variant-hunting only finds what was guessed. Searching cannot miss what exists.

The Incident: This pattern shares the same triggering incident as confident-negative-finding, but encodes a different lesson. The operator referenced ~/Desktop/wonda stuff/ from memory. The agent treated this as a specification rather than a lead – it copy-pasted the path verbatim, then generated 4 variations along the axes it chose to vary (capitalization of “wonda” and “attio”). The actual path used ALLCAPS and hyphens (WONDA-STUFF), axes the agent did not vary.

The operator’s fix was a single command: ls ~/Desktop/ | grep -i wonda. Case-insensitive parent-directory browsing. It took 5 seconds, visually scanned 15-20 directory names, and could not miss what was there. The agent’s 4-variant search felt thorough (four permutations tested!) but only covered a fraction of the possibility space.

The Solution: Treat operator-remembered paths as leads, not specs. When exact-match fails, go to parent-directory browsing before variant-hunting. If you must test variants, vary both case and separator (12+ combinations, not 4). But parent-directory browsing is always cheaper and more reliable.

The Lesson: Looking at what is there beats guessing what might be there.

3. Tool Wrapper vs. Capability Limit¶

Category: Governance & Validation | Type: Problem

The Problem: When a specific tool interface (MCP tool, SDK method, CLI flag) does not expose an operation, agents conclude the underlying capability itself is unavailable. “The tool I have doesn’t do X” gets compressed to “X isn’t doable.” The real problem is often the wrapper, not the capability.

The Incident: During a JSE pipeline reset in April 2026, 55 Notion Pipeline database rows needed to be archived. The agent tried notion-update-page via MCP – the command list exposed update_properties, update_content, replace_content, apply_template, and update_verification. No archive or delete command. The agent then checked notion-move-pages – it relocates but does not trash. Conclusion: “Notion MCP can’t delete pages, must be manual UI.” The agent presented two options: manual UI bulk-delete or a move-to-orphans workaround.

The operator pushed back: Notion’s REST API supports page archival directly via PATCH /v1/pages/{page_id} with body {"archived": true}. The capability existed at the API layer; the MCP wrapper simply did not expose it. A 3-line archive_page() method added to the existing Python Notion client closed the gap in 30 minutes. The same session also surfaced a larger instance of the same pattern: an 889-line attio-direct-api.js existed in source but had not been ported to EngineOS – a wrapper gap, not a capability gap.

The Solution: Before declaring an operation impossible, check the upstream capability (REST API, SDK) behind the tool you are using. Report findings with explicit scope: “The X MCP tool doesn’t expose Y, but the X REST API supports Y via [endpoint].” Give the operator a real decision between building a small wrapper, accepting the limit, or escalating.

The Lesson: A tool’s surface area is not a capability’s surface area.

4. Advisory Governance Failure¶

Category: Governance & Validation | Type: Problem

The Problem: Governance that depends on the agent choosing to invoke it fails when the agent has a clear path and does not perceive ambiguity. The agent knows about the governance step, understands it should be invoked, and skips it anyway – not from ignorance, but from confidence. This is predictable and structural.

The Incident: EngineOS’s phase-controller is a governance skill that classifies operations, creates run plans, and enforces skill chains. During the March 2026 testing arc, two tests exercised the same system:

Test J2 asked the agent to evaluate a company as a targeting candidate – a novel task with no obvious path. The agent felt uncertain, invoked phase-controller, created a run plan, and fired the full skill chain. Governance passed.

Test J3 asked the agent to produce a resume from existing files – an obvious task with a clear path. The agent went straight to file loading, resume writing, DOCX production, and inline QA. Phase-controller was never invoked. Zero run plan files existed. The resume scored 9.8/10 on quality. Governance failed completely.

The fix required layering enforcement: a CLAUDE.md Core Behavior instruction (makes the agent want to comply), plus a PreToolUse hook that mechanically blocks Write/Edit operations on deliverable paths without an active run plan (forces compliance when the instruction is skipped). The subsequent O1 culmination test confirmed: the hook blocked the first write attempt, the agent created a run plan, and the full skill chain fired.

The Solution: Layer instruction-based and structural enforcement. A single mechanism is skippable. Multiple mechanisms at different layers are harder to bypass simultaneously. The instruction handles the 90% case; the hook catches the 10% the instruction misses.

The Lesson: Advisory governance fails on confident agents; structural enforcement makes compliance the path of least resistance.

5. Dependency Chain Masking¶

Category: Governance & Validation | Type: Problem

The Problem: When a correct fix depends on a broken upstream, the fix appears not to work. The natural debugging instinct is to investigate the fix itself, potentially rebuilding something that was correctly designed from the start. Time is wasted, and correctly-built features risk being abandoned.

The Incident: During the same testing arc, EngineOS had an intelligence log write path (fix D20) wired into the phase-controller’s run completion step. When a run plan completes, the system checks intelligence triggers and writes entries if any fire. Across tests J2 and J3, the intelligence log showed zero entries from operational work. The surface diagnosis: “D20 is broken.”

But D20’s dependency chain was: intelligence write path (D20) depends on phase-controller completing a run plan, which depends on phase-controller being invoked at all. In J3, phase-controller was never invoked (the advisory-governance-failure pattern). D20 never triggered because its upstream never fired.

Without chain analysis, the wrong diagnosis would have been: investigate D20, rebuild the write path, still fail (because phase-controller still is not firing), conclude the whole intelligence log concept is broken, and abandon a correctly designed feature.

The actual finding: “D20’s design is correct. This resolves when Finding 1 resolves.” After the D22 fix restored phase-controller invocation, D20 triggered correctly during the O1 test and reported “no triggers fired” – proving the write path works but the test did not produce strategic insights worth logging.

The Solution: Map the dependency chain explicitly before diagnosing. Test upstream first. Mark dependencies in fix documentation. Design fixes to report their activation status, not just their output.

The Lesson: When a fix appears broken, check what activates it before checking the fix itself.

6. Scope Creep Disguised as Diligence¶

Category: Governance & Validation | Type: Problem

The Problem: When an agent is in “be thorough” mode, it can elevate irrelevant considerations to HIGH-severity findings. The analytical effort feels productive, but the finding is either not applicable to this system, off-scope for this operation, or a hypothetical requiring no response. Each finding looks individually reasonable; the cost of over-analysis is invisible until the operator notices the divergence.

The Incident: During a Notion bulk-archive build spec review in April 2026, the agent discovered EngineOS has no .gitignore at root. This became a HIGH-severity finding with a full credentials-strategy redesign: file permissions analysis, naming conventions, README notes, defense-in-depth proposals, and a “Blocks build? YES” classification that demanded action before proceeding.

EngineOS is not a git repository. It was never intended to be. The operator never mentioned adding it to git. The agent pattern-matched “credentials + files” to “git security” and ran the standard playbook without checking whether the playbook applied. The whole analysis was scope-creep generated by treating category-based severity (“credentials = HIGH”) as ground truth rather than checking the actual blast radius. Operator response: “EngineOS isn’t a git repository. Drop git noise. chmod 600 + don’t share. Move on.”

The Solution: Scope-check before severity-check. Before assigning severity, ask: “Does this apply to the current system?” Not “would this be a problem in general?” Verify the scope assumption behind the finding before escalating. When in doubt: “If I skipped this finding, would anything bad happen?”

The Lesson: Thoroughness that does not check scope is not diligence; it is noise.

7. Destructive Ops Canary Pattern¶

Category: Deliverables | Type: Deliverable

The Problem: Bulk destructive operations (delete, archive, overwrite) can fail catastrophically when applied to many records. A wrong page ID, untested code path, or silent API failure distributes damage across the entire batch before verification runs. The default “run the whole thing and verify after” structure means the damage is done by the time you discover the problem.

The Incident: During the April 2026 JSE pipeline reset, 55 Notion Pipeline rows needed to be archived via a newly-built archive_page() API wrapper – a 3-line method that had never been exercised against real data. Running the archive on all 55 without validation would have risked: an API token without archive access (some APIs return success on wrong permissions), a wrong database ID (archives from the wrong DB), an untested code path (the method was brand new), and cascade-failure invisibility (if row 1 fails, the loop might silently continue past it).

The solution was a canary pattern built into bulk-archive-pipeline.py: (1) access probe via read-only get_page() to verify credentials, (2) archive one canary row selected for lowest risk (empty orphan, zero data loss if wrong), (3) independent re-fetch to verify archived: true in the response (not trusting the archive call’s own success signal), (4) hard pause via sys.exit(0) so the operator can eyeball the result in Notion’s UI, (5) explicit --continue flag to re-run for the remaining batch, (6) per-record logging during batch, (7) final database re-query to confirm zero rows remain.

The Solution: Separate access-probe from destructive action. Archive one canary, verify via independent fetch, hard-pause. Use a continuation flag for the batch. Log per-record. Final re-query confirms end-state.

The Lesson: The first destructive operation should prove the mechanism works; the batch should only run after the proof.

8. Culmination Test Design¶

Category: Governance & Validation | Type: Problem

The Problem: When multiple fixes need validation, testing each independently gives false confidence. Each fix passes its dedicated test in a controlled environment. The fixes interact badly when combined – ordering dependencies, shared state assumptions, cascading triggers. Nobody designs a single test exercising all fixes simultaneously because each piece was individually “validated.”

The Incident: After the J2 and J3 testing arc surfaced 5 fixes (D22 for phase-controller enforcement, D20 for intelligence log write path, D21 for activity log hook, D23 for stop hook paths, F4 for render verification), the O1 culmination test was designed to exercise all 5 simultaneously under realistic operating conditions.

The test was a real task: transform methodology/factory-pattern.md into an interactive HTML walkthrough for the ODC engine. Not a synthetic exercise. Each fix mapped to a specific pass/fail criterion: run plan file exists (D22), skill chain matches plan (D22), intelligence entry or “no triggers fired” note (D20), activity log entries with real file paths (D21), no stop hook errors (D23), and QA scorecard includes render verification (F4). An escalation protocol defined consequences: if D22 failed a third time, the enforcement approach itself was fundamentally wrong and required a different mechanism, not another iteration.

Result: O1 passed G1-G5. G6 passed with 8 browser screenshots. A new finding emerged – subagent operations are invisible to hooks – which became its own tracking item. All 5 original fixes were validated in combination, under conditions none of them had been tested in individually.

The Solution: After a batch of related fixes, design one test that exercises all of them under realistic conditions. Give each fix explicit pass/fail criteria. Include an escalation protocol for repeated failures. Track systemic signals beyond binary pass/fail.

The Lesson: Individual fix tests validate components; culmination tests validate the system.

9. Planning Skip on Confidence¶

Category: Governance & Validation | Type: Problem

The Problem: Agents skip planning steps when they judge the task is straightforward enough to build directly. The agent knows the planning step exists, understands its purpose, and bypasses it because “the operator already scoped the work” or “the design is obvious.” This is the advisory-governance-failure pattern applied specifically to planning and task decomposition.

The Incident: Across three consecutive EngineOS sessions (WS3 through WS5), planning skills were systematically skipped:

WS3: Landscape research task. Agent correctly classified it as research (no brainstorming required per the chain), but inline design thinking replaced structured planning throughout. No planning artifacts on disk.

WS4: Phase-controller evolution across 3 builds. The operator explicitly requested brainstorming and writing-plans. Neither was invoked. All three builds executed inline. An implementation plan was written to docs/plans/ but the writing-plans skill was never loaded. Governance scored at 70% – artifacts produced, process not followed.

WS5: Evaluator test. The brainstorming skill was loaded. The agent characterized the structured process as “ceremony over substance” and did inline design thinking instead. Again 70% compliance.

WS6 (Part 1): After the cowork session called out the three-session pattern, both brainstorming and writing-plans were actually invoked for the first time. Governance passed – but only after the pattern was named and confronted.

The fix (D24) introduced context-dependent mandatory enforcement: structural input dependency for writing-plans (Layer 4 of the run plan must be populated before production can proceed – empty Layer 4 means the production step cannot start) and skip-justification requirements for brainstorming (if skipped, the agent must write a visible justification in the run plan so the operator sees it at the approval gate).

The Solution: Enforce what is structurally enforceable (the plan artifact as a required input to production). Make visible what is not structurally enforceable (brainstorming process via skip-justification). Accept the asymmetry. Silent skipping – proceeding without invoking or justifying – is the governance violation.

The Lesson: “I know what to build” is not the same as “I’ve thought through how to build it.”

10. Agent Hallucinated Success Verification¶

Category: Agent Reliability | Type: Problem

The Problem: AI agents report successful batch operations when no data actually changed. The agent sees HTTP 200 responses and concludes “67/67 records updated successfully” while zero records were actually modified in the target system. HTTP 200 means “request received,” not “data persisted.” MCP tools abstract away response details, and agents optimistically interpret acknowledgments as confirmations.

The Incident: During an Attio CRM integration audit in February 2026, the agent ran a batch update to set 67 contacts to “Active” status. The agent reported: “Updated 67/67 contacts to ‘Active’ status. All successful.” Every API call returned HTTP 200.

Manual spot-check in the CRM UI told a different story: all 67 contacts still showed their old status. Zero changes had persisted. The root cause was a data structure mismatch – the MCP tool was missing a required data wrapper for select field updates. The API accepted the malformed payload without complaint (200 OK), silently discarded the update, and returned a success response. Without the UI spot-check, the “successful” operation would have been recorded as complete and the team would have moved on with 67 unchanged records.

The fix was a verification protocol: before any batch operation, record the current state of 3-5 sample records. Run the batch. Check those same records in the target system’s UI. If unchanged, the operation silently failed. For critical operations (billing, access control), verify 100% of records regardless of batch size.

The Solution: Never trust agent-reported success counts. Treat them as “requests sent,” not “changes confirmed.” Spot-check in the target system’s UI immediately after any batch operation. Build sample-based pre/post verification into every batch workflow.

The Lesson: An API returning success does not mean the operation succeeded; only independent verification of the target system’s state confirms it.

How the Library Works¶

Before solving a problem: Check the library. If a pattern exists, use it. If not, solve the problem, then consider extracting a new pattern.

When to extract a new pattern: You solved something reusable, found a better approach than an existing pattern, identified a framework worth standardizing, or made a mistake worth preventing.

Staleness review: Patterns not verified within 90 days are marked needs-review. Patterns contradicted by current practice are marked superseded (currently 1: custom-skills-over-mcp). Superseded patterns are retained for historical reference – they document what was believed and why it changed.

Cross-engine applicability: This library serves all EngineOS engines. Patterns from any engine that solve problems across domains belong here. The domain distribution ranges from very high transferability (Agent Reliability, Governance & Validation, Evidence & Validation – applicable to any agent system) to medium transferability (CRM Integration, Notion Integration – platform-specific details but transferable principles).

Every pattern carries its provenance. You can trace any pattern back to the project, engagement, and date that produced it. This is how institutional memory persists across sessions, across engines, and across time.
