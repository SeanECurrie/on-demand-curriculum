04

Architecture & data model — the philosophical split

9 min read · §03 row 1

The architecture comparison is not "which is better." It's a philosophical split that determines which client AI postures fit which platform. Salesforce is "open ecosystem" — extensibility via metadata + Apex + LWC + Flow, cross-cloud agent orchestration as the architectural bet. Veeva is "vertical integration" — Vault Platform configuration-first, Java SDK with allowlisted classes, X-Pages for UI, LS-specific AI agents application-embedded.

Both extend into agentic AI in 2025-2026, each bolted to its own native substrate F3.19. The architecture row in the matrix is the single highest-weight criterion for predicting long-term client lock-in direction.

Veeva Vault Platform

Vertical-integration architecture

Tenancy model
Multi-tenant SaaS, but architected with separate Vault instances per business domain inside a customer "domain" F3.2. Per-Vault data isolation at instance level F3.18.
Data store
NOT a SQL database with queryable tables. "A managed application platform with controlled APIs and an object/document model" F3.3. Vault Object Framework supports up to ~500 custom objects with 500 fields each; document references natively as first-class field type F3.10.
Customization paradigm
Configuration-first via MDL (Metadata Definition Language) — text-based scriptable config language; Veeva's equivalent of DDL for platform metadata F3.6 F3.7. Java SDK with allowlisted classes, executed as a service account with Vault Owner privileges F3.5.
UI layer
X-Pages — HTML/JS dashboards delivered via secure embedded frames, with a no-code Studio. The Vault equivalent of LWC F3.8. MyInsights launched 2017 for in-CRM custom dashboards F1.14.
Custom-field convention
Uses __v suffix for custom fields. "Custom settings" are objects (records), not Salesforce-style static configuration F3.9.
Integration surface
Versioned REST API with burst rate limits. SAML/SSO and OAuth bypass burst limits; username/password is throttled F3.12. Vault Direct Data API is a separate, non-CRUD, high-speed bulk extraction surface — "up to 100x faster than traditional APIs" for analytics / AI / warehouse loads F3.13. Nine integration types including Vault-to-Vault Connections — a substrate feature with no direct Salesforce-platform analog F3.14.
Release cadence
Three General Releases per year (R1, R2, R3); all customers on the same latest version simultaneously F3.16.
AI architecture
Veeva AI: application-embedded agents in CRM, PromoMats, Safety, Quality. Each agent bolted to a specific LS application context F3.19 F4.32.
Salesforce Platform / LSC

Open-ecosystem architecture

Tenancy model
Single shared multitenant database with metadata-driven kernel; sObjects are virtual, not physical tables F3.1. Every record stamped with OrgID; partitioning by OrgID F3.18.
Data store
sObjects (virtual). Hierarchical, encrypted, Salesforce-specific lookups do not all map cleanly to Vault — requires transformation or loss on migration F3.11.
Customization paradigm
Apex (code) + Lightning Web Components (UI) + Flow (declarative) F3.6. Apex enforces hard per-transaction governor limits (100 SOQL, 150 DML, 10s CPU sync) precisely because of multitenancy F3.4. Apex unit tests must cover ≥75% of code to promote to production — a built-in quality gate from substrate F3.17.
UI layer
Lightning Web Components (LWC) + Flow Builder. Standard Salesforce Platform UI primitives. LSC customer-engagement SKU runs iPad-first; AWS Marketplace later F2.14.
Custom-field convention
Uses __c suffix for custom fields. Static "Custom Settings" object type for configuration F3.9.
Integration surface
Salesforce Platform REST/SOAP APIs, Bulk API, Streaming API. LSC substrate components explicitly named in product page F2.21. AppExchange is the third-party extension marketplace.
Release cadence
Three Salesforce Platform releases per year (Spring, Summer, Winter). Salesforce LSC is built ON TOP of Sales/Service Cloud, not as a separate platform F2.5.
AI architecture
Agentforce LS: broader, platform-level AI architecture F4.36. Agent-to-agent collaboration across the platform as the architectural bet, explicitly contrasted with Veeva's vertical-integration F2.17 F2.23 F3.19.

What this means in practice for migrations

The architecture split is what makes the migration "complete re-implementation" rather than a config-port. Apex code does not run on Vault Platform. Lightning Web Components do not run on Vault Platform. Custom Visualforce pages do not run on Vault Platform. Integrations built against the Salesforce REST API need new endpoints on the Vault REST API F3.15. Vault's release cadence (R1/R2/R3 with all customers on the same version) is structurally different from Salesforce Platform's three seasonal releases F3.16.

None of this is a Veeva-criticism or a Salesforce-criticism — it's the philosophical split working as designed. Veeva's bet is that LS-specific vertical integration produces better LS-CRM outcomes than horizontal cross-cloud extensibility. Salesforce's bet is the opposite F2.17 F2.23. Neither bet has been settled by the evidence base.

▸ The single highest-leverage architecture cue for client conversations

The cleanest way to triangulate which architecture fits a buyer: look at where the buyer's AI ambitions actually live.

  • "We want agents inside MLR review, inside sample drop workflows, inside the call report" → Veeva-lean. LS-specific application-embedded agents are Veeva AI's named bet F4.32 F4.34 F4.35.
  • "We want agents that work across Service Cloud, Marketing Cloud, our internal HR cloud, AND LS-CRM" → Salesforce-lean. Cross-cloud agent orchestration is Agentforce's architectural bet F2.23 F4.36.
  • "We want both, and we want them talking to each other" → Dual-vendor architectures are emerging as a real pattern (Boehringer Ingelheim is the public example) F7.10. The integration cost is real but bounded.

The Veeva data-API moat — and the Salesforce platform-AI moat

Each platform has a substrate-level moat the other can't easily replicate:

Vault Direct Data API is non-CRUD, high-speed bulk extraction — "up to 100x faster than traditional APIs" — designed specifically for analytics / AI / warehouse loads F3.13. For clients building data-lake-fed AI on top of LS-CRM data, this is a real performance/cost differentiator. Vault-to-Vault Connections (cross-Vault data flows) add a substrate feature with no direct Salesforce-platform analog F3.14.

Salesforce Platform's metadata-driven kernel with sObjects-as-virtual-records is the architectural foundation enabling AppExchange's marketplace scale and cross-cloud agent orchestration F3.1 F2.23. The 75% Apex unit-test coverage requirement F3.17 is an ecosystem-quality gate Vault doesn't have an equivalent of. For clients running multi-cloud Salesforce stacks already, the integration model is structurally tighter than going cross-vendor to Veeva.

▸ Reading the architecture row

The most common buyer question on this row — "which is more flexible?" — has an honest answer: they're flexible in different directions. The Veeva Direct Data API is a Vault Platform advantage for AI / analytics-heavy use cases F3.13. Salesforce's cross-cloud agent orchestration is a Salesforce Platform advantage for multi-cloud stacks F2.23. Neither is "more flexible" in the abstract — the architecture-philosophy direction precedes the feature-coverage read in §05.
