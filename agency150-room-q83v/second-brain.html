The second brain — how it remembers

That hypnotic galaxy of dots Sean showed you has a simple meaning. Here's what you're actually looking at, and why it's the part that matters most.

The short version: EngineOS doesn't just do the work — it learns from every job it does, and remembers. The graph is that memory, made visible.

What you're looking at

Each bright dot is one idea the system distilled from real work — a lesson, a method, a decision. The lines between them are connections it drew itself between related ideas.
The faint outer ring is the raw material — the sessions, plans, and logs it learned from. The bright connected middle is what it has actually digested into knowledge.

A dense, glowing, interconnected core surrounded by the raw record it grew out of. The denser a neighborhood, the more the system has thought about that topic.

What it actually is

Most AI tools start every conversation from a blank slate — they're brilliant in the moment and forget it instantly. EngineOS has an exocortex: a private, growing memory of this operator's work. After every session, it writes down what it figured out as small, single-idea notes, and links each one to the related ideas already there. Over months, those notes wire themselves into the web you see — a brain it built out of its own experience.

It's the same instinct behind a researcher's Zettelkasten or Karpathy's "LLM operating system" — but auto-built, by the system, from real work, and queryable on demand.

Under the hood · for the technically inclined

How it actually works

The plain-English version is above. This part is for a reader who wants the architecture — what runs, when, and what we changed to make it hold up. If you know Karpathy's wiki-loop, you already know the shape; the interesting part is the engineering around it.

The core idea: logs are source, the knowledge base is the compiled binary

The mental model is a compiler. Raw conversation logs are source code; an LLM reads them and emits structured, linked knowledge articles — the compiled artifact. You don't hand-write the wiki; you write the logs by working, and a compile pass builds the wiki from them.

# the pipeline, in one line
daily/YYYY-MM-DD.md ──(LLM compile)──▶ knowledge/concepts/*.md + connections/*.md + index.md
# source (what happened) # executable (what was learned, linked)

That framing is Karpathy's "LLM as the kernel of a new kind of OS," made literal: the daily log is the program, the compile step is the build, the graph is the linked binary. The base we started from is Cole Medin's compiler repo (which runs on that wiki-loop idea — keyword/index retrieval, deliberately no vector DB or embeddings). We took that, built our own first version on it, and then spent most of the effort on everything around the loop.

The loop, in mechanism

01 · Capture
Flush on session close
A separate agent reads the conversation and writes down what's worth keeping.
flush.py — a Claude Agent SDK subprocess spawned by the SessionEnd / PreCompact hooks. Extracts a structured summary (decisions, lessons, action items) → appends to today's daily log. Runs headless, out of band.
02 · Compile
Logs become linked notes
The compiler turns the day's logs into atomic, cross-linked concept notes.
compile.py — an SDK agent with Read/Write/Grep. Emits one-idea articles with YAML frontmatter and [[wikilinks]], updates the index. Fires per session-close, so what you just closed lands in the KB immediately.
03 · Retrieve
The right notes come back
Two paths put relevant memory back into context — one at startup, one per prompt.
session-start.py injects the KB index + recent log at every session start. prompt-retrieval.py (a UserPromptSubmit hook) scans the corpus on relevant prompts and injects the top 3 hits as <prior-context>.

The whole thing is wired into the harness lifecycle — 8 hook events (SessionStart, SessionEnd, PreCompact, PostCompact, UserPromptSubmit, PreToolUse, PostToolUse, Stop). It isn't a script you remember to run; capture fires when a session ends or compacts, recall fires when you start one or ask a question. Nothing depends on the agent choosing to remember — which, under context pressure, it reliably won't.

What we changed (the part that took the work)

The wiki-loop is the easy 20%. A loop that survives daily use for months is the other 80%. The improvements below are each a small build of their own, on disk as run plans and audits:

Lean compile token economy
The original full-send inlined the entire KB into every compile prompt, so cost scaled with KB size, not session size — fine at zero articles, brutal at a few hundred. Now each compile sends the index plus only the top-K=20 articles most relevant to the log, and the agent pulls anything else on demand. Context per compile is now flat as the graph grows instead of climbing with it.
The retrieval layer closed the real gap
Capture was always strong; retrieval was the hole — in one ~30-hour session the agent read zero concept files on its own. The UserPromptSubmit hook fixed that mechanically: a heuristic gate, query-term extraction, a multi-surface scan, top-3 injected. Hard-capped at 1,024 chars / 1,000 ms / silent-fail so it can never stall or bloat a prompt.
Per-close compile + debounce lock freshness
Compile fires on every session-close that saved something (the old 18:00–06:00 window let overnight closes pile into a 4-day backlog). A pid-liveness lock with a TTL serializes concurrent compiles and debounces clustered closes into one run of accumulated changes.
Observability + safety nets don't lose memory
Every flush and retrieval emits a JSONL health record with review scripts on a cadence. A failed flush no longer records its dedup state — so the next close retries instead of silently skipping (a real bug that nearly dropped a whole session's capture). Retry-once on transient SDK failures; a recursion guard stops compile-spawned sessions from flushing noise back in.

All of it is logged: the cost-architecture fix, the retrieval build, the silent-loss patch, the cap tuning — each has a dated run plan and, in most cases, an adversarial review pass on the diff.

Why this pairs with session-maxing

This is the part that connects to actually getting more done in a window. A model starts every session cold. The second brain de-loads working memory to disk and pushes the relevant slice back in at startup and per-prompt — so a session opens already oriented instead of spending its first stretch re-deriving what was already figured out. Paired with EngineOS's tiered context budget (only load what the work needs), the effect is less of a finite context window spent on re-warming and more of it spent on the work.

  • Concrete, on disk: 35 days of logs have compiled into 320 linked notes (260 concepts + 60 connection notes) with ~2,800 internal links — a working memory the model can stand on.
  • Recall in action: the Agency150 dossier above wasn't built cold. It recalled the shape of past company briefings (Trinity, Fresha) and reused the proven structure — that "recall" is this loop firing during real work.
  • The honest version of the payoff: the mechanism is the defensible part — a session opens already holding what past sessions figured out, so it stops re-deriving solved problems. The operator's subjective read is that it's a substantial lift; quantifying that honestly (logging session-usage deltas) is still on the list — there's no instrumented number yet.
◆ The honest engineering tradeoffs

It's deliberately lossy and bounded, and that's a feature, not an apology. Capture is an LLM's judgment of what mattered (it misses things). Retrieval is a heuristic gate over a keyword index with a top-K cut — no embeddings, by design — so it trades some recall for being fast, cheap, and debuggable. Some guards are detection, not prevention (they make a failure loud rather than impossible). The reason the system is trustworthy isn't that it's flawless — it's that every limit here is a stated, measured one with a health log behind it.

A footnote that wrote itself

★ the most EngineOS thing on this page

Quick personal note from Sean, because it's the most EngineOS thing here. The feature in the card below didn't exist when I started writing this.

I was talking the second brain through with someone who'd actually want the architecture — building this explainer for them — and writing the "it doubled my output" line is what surfaced the problem: I was making a claim I had no way to measure. No usage instrumentation existed anywhere. So I cut the claim (you'll spot the hedge a few sections up).

Then the part that's the actual point. Right there in the conversation, EngineOS could reason the fix through with me — what even counts as a "second-brain" session (turns out the retrieval hook already leaves fingerprints we could read), where to capture it without endangering the memory-capture it sits beside, and what to honestly measure versus what not to overclaim.

And then we just built it, in order: scoped it in a run plan → wrote the logger and a review script → wired it as one isolated spawn onto a hook that already existed → tested it on a live session → shipped it, pending real data. Same night.

That's what I actually want you to take from this, more than any single feature: me noticing a gap mid-conversation is enough to set it off, and the system is wired well enough that considering the design and building it was an afternoon, not a project. The thing I built to remember just started learning to measure itself. The loop ate its own tail — and you're reading the part where it noticed.

The usage logNew · pending data

What it is: at every session close, EngineOS now records that session's token footprint and whether it actually drew on the second brain — pulled prior context, read the knowledge base, or hit /recall — or worked cold. It rides the same observability pattern as the health logs above, and it's isolated so it can never interfere with the memory-capture it sits next to.

What it's for: once enough sessions stack up, an engaged-vs-cold comparison — does the brain make a session leaner, longer, higher-output? The honest answer right now: we don't know yet. It shipped today; the log is empty until sessions accumulate. There's no number to show you — which is exactly the point of building the instrument instead of repeating the claim.
